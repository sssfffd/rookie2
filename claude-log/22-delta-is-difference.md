# 22 — 0–1 정규화를 없애고, 변화량을 진짜 차분으로

> 요청: "그리고 0-1 정규화는 필요없을 것 같아
> 변화량의 경우에는 (차분)쓰고 두 io값의 차이를 나타내야 하는거야
> 변화가 없으면 0, 1 증가하면 1 -1이면 -1"

---

## 1. 0–1 정규화를 없앴습니다

두 화면에서 모두 쓸모가 없었습니다.

- **레인 보기**에서는 값과 눈금에 **똑같은 변환**이 걸립니다. 값을
  `(v − 최소) / (최대 − 최소)` 로 펴면서 눈금도 0~1 로 바꾸니까, 화면
  좌표가 하나도 안 바뀝니다. 7 번 문서에서 "그래프가 안 변한다" 고
  적어 뒀던 그 자리입니다.
- **겹쳐보기**에서는 그림이 달라지긴 했는데, 나오는 숫자가
  "이 채널의 최소~최대 안에서 몇 %" 였습니다. 로그를 읽을 때 쓸 데가
  없는 수입니다.

없애면서 코드도 꽤 줄었습니다 — 자세한 것은 3 번에.

---

## 2. 변화량 = 이웃한 두 표본의 차이

### 무엇이 바뀌었나

전에는 **첫 값을 빼는 것**이었습니다.

```
값     6466.3  6466.3  6466.6  6466.6  6466.4
예전   0       0       +0.3    +0.3    +0.1     ← 첫 값(6466.3)을 뺀 것
지금   0       0       +0.3    0       -0.2     ← 직전 표본과의 차이
```

요청대로 **차분**입니다. 안 바뀌면 0, 1 오르면 +1, 1 내리면 −1.

값이 얼마인지가 아니라 **언제 얼마나 움직였는지**를 보는 눈금입니다.
6466.3 에서 6466.6 으로 가는 변화는 값 눈금으로는 직선이나 다름없지만,
여기서는 +0.3 짜리 막대로 또렷하게 섭니다.

### 모르는 자리는 0 입니다

```
값     5   5   -   -   100  101
변화량 0   0   NaN NaN 0    +1
                       ↑
                 여기를 +95 로 하면 없던 계단이 생깁니다
```

- **첫 표본**은 직전이 없으니 0.
- **값이 빈 자리**는 변화량도 없습니다(NaN). 거기서 선이 끊깁니다.
- **빈 구간 뒤 첫 표본**도 0. 그 사이에 무슨 일이 있었는지 모르는데,
  건너뛴 값의 차이를 "변화" 라고 그리면 거짓말입니다.

### 계단으로 그립니다

변화는 **그 표본에서 일어난 일**입니다. 비스듬히 이으면 표본 사이에 없던
중간 변화를 그린 셈이 됩니다.

```
비스듬히 이으면              계단으로 그리면
      /\                          ┌─┐
     /  \                         │ │
 ───/    \───                 ────┘ └────
   여기에 없던                  변화가 일어난 그 자리에만
   중간 변화가 보임
```

### 눈금에 0 이 반드시 들어갑니다

안 바뀌는 동안은 계속 0 이라, 0 이 눈금 범위 밖이면 **어디가 "변화 없음"
인지 알 수가 없습니다.** 세로 범위를 잡을 때 0 을 억지로 끌어들입니다.

### 커서는 값과 변화량을 같이 적습니다

```
이전 6466.6  (Δ +0.3)     이후 6466.3  (Δ 0)
```

값만 적으면 커서가 가리키는 숫자와 화면에 그려진 선이 서로 다른 것을
말하게 됩니다. 그렇다고 변화량만 적으면 지금 값이 얼마인지 알 수 없어서,
둘 다 적습니다.

변화량은 **가장 가까운 표본**의 것을 씁니다. 이어 읽지 않습니다 —
표본과 표본 사이에는 일어난 변화가 없습니다.

## 3. 왜 "그릴 때 값 하나 바꾸기" 로는 안 됐나

이게 이번 작업에서 제일 손이 많이 간 부분입니다.

예전 구조는 값 하나를 받아 바꿔 주는 함수였습니다.

```csharp
private double Transform(double v, double chLo, double chHi, double baseline)
{
    switch (_scale)
    {
        case Normalized: return (v - chLo) / (chHi - chLo);
        case Delta:      return v - baseline;     // 첫 값 빼기 — 한 점만 알면 됨
        default:         return v;
    }
}
```

두 모드 다 **그 값 하나만 알면** 계산이 됐습니다. 그래서 그리기 직전에
끼워 넣으면 그만이었습니다.

**차분은 직전 표본을 알아야 합니다.** 그리고 더 나쁜 것은 — 그리기
직전은 이미 **늦습니다.**

### 접은 뒤에 빼면 늦습니다

표본이 픽셀보다 촘촘하면 열마다 최소/최대만 남기고 접습니다(Decimator).

```
한 열에 든 표본      100, 101, 100, 99, 100
접으면               최소 99, 최대 101
```

여기서 "차이" 를 구하면 101 − 99 = 2 인데, 실제로 일어난 변화는
+1, −1, −1, +1 입니다. **그 열 안에서 얼마나 움직였는지가 접는 순간
이미 사라집니다.**

### 그래서 차이를 데이터로 만들었습니다

`Channel` 에 값 배열과 나란한 **차이 배열**을 둡니다.

```csharp
public float[] Diff { get { EnsureDiff(); return _diff; } }
```

- **처음 필요할 때만** 만듭니다. 읽을 때 미리 다 만들면 채널마다 메모리가
  두 배가 되는데, 변화량으로 실제로 보는 채널은 몇 개뿐입니다.
- 한 번 만들면 **계속 씁니다.** 값 배열은 읽은 뒤 바뀌지 않으니 다시
  계산할 일이 없습니다. 프레임마다 수백만 표본을 다시 빼면 못 씁니다.

그리고 접기 · 범위 · 그리기가 전부 "값 배열이냐 차이 배열이냐" 만 고르게
했습니다.

```csharp
public static float[] Series(Channel c, bool diff)
{
    return diff ? c.Diff : c.Values;
}
```

`Transform` 과 `Baseline` 은 통째로 사라졌고, 그리기 함수들이 들고
다니던 `chLo, chHi, baseline` 세 개도 같이 없어졌습니다.

## 4. 차이 음영은 어느 눈금에서든 값으로 가립니다

[차이 구간 음영] 은 이전 로그와 이후 로그가 어긋난 자리를 칠합니다.
여기서 갈림길이 하나 있었습니다 — **변화량 눈금일 때 무엇을 견줄 것인가.**

차이끼리 견주면 안 됩니다. 허용 오차는 `|이후 − 이전| / |이전| × 100`
인데, 변화량은 안 바뀌는 동안 0 이라 **분모가 0 이 되어 거의 모든 자리가
100% 로 뜹니다.** 온 화면이 칠해집니다.

그리고 더 중요한 이유가 있습니다. 눈금은 보는 방식일 뿐인데, 눈금을
바꿨다고 "다르다" 의 뜻이 달라지면 안 됩니다. 대시보드 · 히트맵과도
어긋납니다.

그래서 이렇게 나눴습니다.

| 무엇 | 무엇으로 |
|---|---|
| **다르다는 판정** | 언제나 **값** |
| **칠하는 자리** | 지금 화면에 그려진 선 (변화량 눈금이면 변화량) |

열마다 뽑는 배열을 한 쌍 더 뒀습니다.

## 5. 옛 설정 파일

`valueScaleMode` 에 `normalized` 가 적힌 설정 파일이 남아 있을 수 있습니다.
그대로 들고 있으면 **어느 단추도 안 켜진 채**로 뜹니다. 읽을 때
`delta` 가 아니면 전부 `raw` 로 되돌립니다.

## 6. 자체 테스트

컴파일하고 실제로 돌려서 확인했습니다 (268개 통과, 이번에 25개 늘었습니다).

| 테스트 | 확인하는 것 |
|---|---|
| `DiffSeries` | `0,0,1,1,2,1,0,0` 에서 차이가 `0,0,1,0,1,-1,-1,0` 으로 나오는지, DiffMin/DiffMax 가 −1/+1 인지, 두 번 불러도 같은 배열인지(갈무리), 접기와 범위가 `diff` 를 따르는지 |
| `DiffAcrossGaps` | 빈 자리는 NaN 이고 그 뒤 첫 표본이 0 인지, 5 에서 끊겼다 100 으로 돌아온 로그에 +95 가 안 생기는지 |
| `SettingsRoundTrip` | `normalized` 가 `raw` 로 되돌아오는지, `delta` 는 그대로 남는지 |

### 아직 확인 못 한 것

화면에서 실제로 어떻게 보이는지는 여전히 윈도우에서 돌려 봐야 압니다.
특히 변화량 눈금에서 **세로 범위**가 쓸 만하게 잡히는지 — 튀는 표본이
하나 있으면 그것 때문에 나머지가 납작해질 수 있습니다. 그때는
[구간 맞춤] 이나 [계속 맞춤] 으로 지금 보이는 구간에만 맞출 수 있습니다.
