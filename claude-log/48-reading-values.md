# 48. 값은 어떻게 읽나 (0.58)

> 그럼 값은 어케 읽어?

## 한 줄 답

**서버를 한 번은 거쳐야 합니다.** `.frm` + `.ibd` 폴더만으로는 값을 못
읽습니다 — 정확히는, 읽을 수는 있어도 **맞다고 보증할 수가 없습니다.**

## 왜 `.ibd` 를 직접 안 읽나 (0.57 에서 모양은 읽게 됐는데도)

0.57 로 막혀 있던 것 하나는 풀렸습니다. 전에는 "SDI 가 없으니 **열 타입을 알
방법이 없다**" 가 선행 문제였는데, 이제 `.frm` 에서 타입을 읽습니다. 그러니
값을 읽는 일이 **더 가까워진 것은 사실**입니다.

그런데 남은 문제는 타입이 아니었습니다.

- **되돌리기 기록(undo)이 `.ibd` 안에 없습니다.** 다른 파일에 있습니다. 누가
  고치는 중인 행의 "원래 값" 은 거기 있고, 되돌려질지 아닐지는 `.ibd` 만 봐서는
  모릅니다.
- **지워졌다고 표시만 된 행이 페이지에 남아 있습니다.** 언제 실제로 치워지는지는
  정해져 있지 않습니다.
- **돌고 있는 서버의 폴더를 그냥 복사한 파일은 일관성이 보장되지 않습니다.**
- `COMPRESSED` 는 수정 기록을 되재생해야 하고, **암호화된 것은 못 읽습니다.**

조건을 갖추면 됩니다 — 서버를 끈 복사, `FLUSH TABLES ... FOR EXPORT`, 준비된
백업. **문제는 그 조건이 맞는지를 파일만 보고 확인할 방법이 없다는 것입니다.**

그리고 이 프로그램이 하는 일을 생각해야 합니다. 우리는 **견주는** 도구이고,
견준 결과로 **`UPDATE` 글까지 만들어 줍니다.** 값이 하나 틀리면 없는 차이를
만들거나 있는 차이를 가리고, 그 틀린 값이 SQL 에 박혀 나갑니다. **못 읽는
것보다 틀리게 읽는 쪽이 훨씬 나쁩니다.**

모양은 다릅니다. 표 정의는 `ALTER` 를 돌리지 않는 동안 바뀌지 않으니, 돌고
있는 폴더의 `.frm` 을 읽어도 됩니다. 그래서 0.57 은 하고 0.58 은 안 합니다.

## 네 가지 길 — 싼 것부터

| 길 | 손 | 믿을 수 있나 |
|---|---|---|
| **1. 필요한 표만 CSV 로** | 가장 적음 | **네** |
| **2. `mysqldump`** (`db.dump.*`) | 적음 | **네** |
| **3. 폴더를 MySQL 5.6 에 붙여 한 번 뽑기** | 중간 | **네** |
| **4. 표마다 `.ibd` 를 옮겨 붙이기** | 많음 | **네** |

**1 번을 권합니다.** 견주려는 것이 레시피·파라미터 같은 **설정 표 몇 개**라면
이력·로그 표까지 다 받을 이유가 없습니다. `.csv` 는 이미 읽습니다 (파일 이름이
표 이름). 설비 PC 에서 그 표들만 내보내 폴더에 두면 끝입니다.

**3 번은 판을 맞춰야 합니다.** 5.6 폴더는 **5.6 에** 붙입니다. 8.0 에 바로
붙지 않습니다. `ibdata1` 과 `ib_logfile*` 도 함께 있어야 합니다 — 5.6 은
InnoDB 의 내부 사전이 `ibdata1` 에 있어서 `.ibd` 만 옮기면 tablespace id 가
안 맞습니다.

**4 번은 받는 쪽에 같은 표가 먼저 있어야 합니다.** 그래서 이번에 그 출발점을
만들어 뒀습니다.

## 만든 것 — [표 정의 저장]

읽은 표의 모양을 `CREATE TABLE` 글로 저장합니다. 두 쪽을 한 파일에.

```sql
-- recipe  (.frm 에서 모양만 읽었습니다.)
-- 값은 읽지 못했습니다 (모양만).
CREATE TABLE `recipe` (
  `id` int(11) NOT NULL,
  `name` varchar(64) /* 기본값 모름 */,
  `온도` decimal(6,2) /* 기본값 모름 */,
  PRIMARY KEY (`id`)
);
```

**첫째 쓰임은 확인입니다.** 지금 열려 있는 숙제가 "제 `.frm` 읽기가 진짜 MySQL
파일과 맞는가" 인데, 이 글이 그 답을 가장 빨리 줍니다. 서버에서
`SHOW CREATE TABLE recipe;` 를 찍어 나란히 놓으면 열 이름·타입·순서가 맞는지
한눈에 보입니다. 열 목록을 화면에서 하나씩 짚어 보는 것보다 훨씬 빠릅니다.

**둘째 쓰임은 4 번 길의 출발점입니다.**

### 모르는 것을 아는 척 적지 않기

이 글에서 가장 조심한 자리입니다. 기본값을 모르는 열에 `DEFAULT NULL` 을
적으면 안 됩니다.

```
-- 적어서는 안 되는 글
`name` varchar(64) DEFAULT NULL      ← 모르는데 "기본값은 NULL" 이라고 단정
```

이 글을 믿고 돌리면 **없던 기본값이 생깁니다.** 그래서
`/* 기본값 모름 */` 으로 적습니다. 보기엔 덜 깔끔하지만, 덜 깔끔한 쪽이
맞습니다.

같은 이유로 글 머리에 **빠진 것을 전부 적어 둡니다** — 기본값,
`AUTO_INCREMENT`, 문자셋/`COLLATE`, 외래 키, **기본 키가 아닌 색인**(우리는
`PRIMARY` 만 읽습니다), 엔진과 행 포맷. "그대로 돌리지 마세요" 를 첫 줄에
적었습니다. 이 글만 보고 표를 만들면 4 번 길의 `IMPORT TABLESPACE` 가
거부될 수 있습니다 (받는 쪽 정의가 정확히 같아야 합니다).

## 검사

테스트 **581 통과 / 0 실패** (18 개 새로 더함). 모르는 기본값에
`DEFAULT NULL` 을 적지 않는지, 역따옴표가 든 이름을 두 번으로 적는지, 키가
없으면 `PRIMARY KEY` 줄이 아예 없는지, 빠진 것을 머리에 밝히는지, 두 쪽
경로를 적는지, null 을 줘도 견디는지.
