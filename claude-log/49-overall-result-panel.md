# 49. 메인 맨 위를 종합 분석 결과로 (0.59)

> 지금 메인 화면에 열어둔 로그들 위치에다가 종합 분석 결과라는 창 만들어주고
> 열어둔 로그는 뺄꺼임
> 그리고 분석 1 2 3칸 세로로 더 길게해서 요약들 보기 더 편하게 만들고
> 그리고 분석 1에 io개수들더 빼줘
> 지금 열어둔 로그 ui들은 분석 1에 작게 포함되면 될 것 같아

## 바뀐 자리

```
전                                지금
┌──────────────────────────┐      ┌──────────────────────────┐
│ 열어 둔 로그             │      │ 종합 분석 결과           │
│  [이전 크게][이후 크게]  │      │  ● 달라진 데가 있습니다  │
└──────────────────────────┘      │  비교 123  달라짐 12     │
                                   │  한쪽에만 2              │
분석 결과                          │  허용 오차 0.1% …        │
┌──────┬──────┬──────┐           └──────────────────────────┘
│분석1 │분석2 │분석3 │
│ 점수 │      │      │            분석 결과
│ IO수 │      │      │            ┌──────┬──────┬──────┐
│ 요약 │      │      │            │분석1 │분석2 │분석3 │
│(짧음)│      │      │            │ 점수 │ 점수 │ 점수 │
└──────┴──────┴──────┘            │[이전][이후]  │      │
                                   │ 요약 │ 요약 │ 요약 │
                                   │ (길게)      │      │
                                   └──────┴──────┴──────┘
```

## 왜 이 순서가 맞나

메인 화면이 먼저 답해야 하는 것은 **"그래서 결과가 어떤가"** 입니다. 전에는
맨 위가 "무슨 파일을 열었나" 였습니다. 그건 **분석 1 의 준비**이지 결과가
아닙니다. 그래서 로그 칸이 분석 1 안으로 들어간 것이 자리로도 맞습니다 —
로그를 쓰는 분석이 거기 하나뿐입니다.

## IO 개수를 뺀 이유는 "세 군데에 있었다" 입니다

전에는 같은 수가 세 군데 적혀 있었습니다.

```
분석 1 칸      비교한 IO 123개 · 달라진 IO 12개
대시보드        같은 수
(종합 칸)      ← 새로 생김
```

**세는 자리는 한 곳이면 됩니다.** 여러 군데 적히면, 하나가 틀렸을 때 어느
쪽이 맞는지 알 수가 없습니다. 칸은 "요약" 을 보는 자리로 비우고, 수는 종합
칸에서 셉니다. 종합 칸은 가로로 넓어서 **"한쪽에만"** 까지 셋이 들어갑니다 —
칸이 좁아서 뺐던 그 항목입니다.

채우는 길(`SetStats`)은 남겨 뒀습니다. 분석 2(DB)가 "표 12 개 중 3 개
달라짐" 을 적을 자리입니다. 비어 있으면 칸 자체가 사라지므로 빈 자리가
보이지는 않습니다.

## 기준을 함께 적습니다

종합 칸에 **허용 오차 · 시간 맞추기 · 가로축**을 한 줄로 적습니다. 숫자만
있고 기준이 없으면 무엇과 견준 수인지 알 수 없습니다. 허용 오차를 바꾸고 다시
견주는 일이 잦은 화면입니다.

저장된 분석에 적는 글과 **같은 틀**(`AnalysisRecord.BasisText`)을 씁니다.
따로 만들면 두 글이 갈라져서, 지난 분석과 지금 분석의 기준이 같은지 눈으로
견줄 수가 없게 됩니다.

판정 옆의 점 색은 점수 색과 **같은 뜻**입니다. **안 견준 상태는 회색 그대로**
둡니다 — 안 재 본 것에 색을 칠하면 재 본 것으로 읽힙니다.

## 칸을 세로로 늘린 방법

칸 테두리에 `MinHeight="480"` 을 주고, 요약 목록의 상한을 130 → 300 으로
올렸습니다. `UniformGrid` 가 셋의 높이를 맞추므로 한 칸만 커져도 셋이 같이
커집니다 — 분석 2·3 은 아직 요약이 없어 아래가 비지만, 셋이 나란히 같은
크기여야 견줘 보입니다 (26 에서 `WrapPanel` 을 버린 것과 같은 이유입니다).

## 가는 길에 잡은 고장

**끌어다 놓은 칸의 색이 달라지는 것.** 로그 칸이 분석 1 안으로 들어가면서
배경이 `Brush.Panel` 에서 `Brush.Window` 로 바뀌었습니다. 그런데 칸을 밝혔다가
되돌리는 코드가 **`Brush.Panel` 로 되돌리고 있었습니다.** 그러면 파일을 한 번
끌어다 놓은 칸만 색이 달라진 채 남습니다.

0.42 에서 칸이 사라지던 것과 **같은 종류**입니다. 그때는 `ClearValue` 로
지워서 칸이 없어졌고, 이번엔 되돌릴 값을 코드에 박아서 색이 틀어졌습니다.
둘의 뿌리는 하나입니다 — **칸이 어떤 모습이어야 하는지는 XAML 이 알고 코드는
모릅니다.**

그래서 되돌릴 열쇠를 XAML 의 `Tag` 에 함께 적게 했습니다.

```xml
Tag="before|Brush.Window"
     ↑어느 쪽  ↑되돌릴 배경
```

**그리고 검사를 하나 더 만들었습니다.** 놓는 칸의 `Background` 와 `Tag` 의
되돌릴 열쇠가 **다르면 웁니다.** 컴파일도 되고 XAML 파싱도 되는 어긋남이라,
검사가 없으면 윈도우에서 파일을 한 번 끌어다 놓아 봐야 압니다. 일부러
어긋나게 해서 우는 것까지 확인했습니다.

검사를 만들다가 **놓는 칸이 두 군데 더 있는 것**을 알았습니다. 그래프 화면의
그룹 줄과 창 전체입니다. 둘은 뷰모델 깃발과 XAML 트리거로 색을 바꿔서 XAML
혼자 주인이고 어긋날 데가 없습니다. 그래서 검사는 **코드가 배경을 되거는
화면**만 봅니다.

## 검사

- 테마 · 핸들러 · 이름 겹침 · 놓는 칸 배경 검사 넷 다 통과.
- 테스트 **581 통과 / 0 실패** (이번 변경은 화면 쪽이라 테스트가 늘지
  않았습니다).

**못 해 본 것**: 화면 모양입니다. XAML 은 이 컨테이너에서 컴파일되지 않아,
칸 높이 480 이 적당한지, 작아진 로그 칸에 파일 이름이 들어가는지, 종합 칸의
숫자 셋이 좁은 화면에서 어떻게 보이는지는 윈도우에서 봐 주셔야 합니다.
칸이 너무 길거나 짧으면 숫자 하나만 고치면 됩니다.

## 뒷이야기 — IO 개수를 아예 뺐습니다 (0.63)

> 종합 분석결과에 io개수 뜨는거 지워줘

0.59 에 분석 1 칸에서 종합 칸으로 **옮긴** 것을, 0.63 에 **뺐습니다.**

옮긴 이유는 "세 군데에 적혀 있으니 한 곳으로" 였습니다. 그 한 곳이 종합
칸이어야 할 이유는 없었습니다 — **대시보드(분석 1 화면)가 원래 그 수를 세는
자리**이고, 거기에는 IO 목록까지 함께 있습니다. 메인 화면은 "그래서 어떤가" 를
한 줄로 답하는 자리입니다.

지금 종합 칸에 남은 것은 넷입니다.

```
● 달라진 데가 있습니다
허용 오차 0.1% (IO 별 3개)   시간 맞추기 "RUN"
비교 실행  2026-10-06 14:20
칸을 누르면 그 분석 화면으로 넘어갑니다
```

기준과 시각은 남겼습니다. **"달라진 데가 있다" 는 말은 기준이 없으면 무엇을
넘었다는 뜻인지 알 수 없습니다.** 허용 오차를 바꾸고 다시 견주는 일이 잦은
화면이라, 판정과 기준은 붙어 있어야 합니다.

`OverallStats` · `HasOverallStats` 는 지웠습니다. 쓰지 않는 속성을 남겨 두면
다음에 읽는 사람이 "어디에 쓰이나" 를 찾습니다.

테스트 **599 통과 / 0 실패**, 검사 넷 다 통과.

## 뒷이야기 2 — 위 줄 차례와 메인 화면 높이 (0.65)

> 버전이랑 fullname 서로 위치 바꿔줘
> 지금 메인화면 세로가 조금 길어서 스크롤 생기는데 분석결과들 길이 조금씩 줄여주셈

### 위 줄

```
전   LogScope  v0.64  Log 비교 · 분석 도구
지금 LogScope  Log 비교 · 분석 도구  v0.65
```

이름 다음에 이름이 이어지고 숫자가 끝에 붙는 쪽이 읽기 순서에 맞습니다.
`fullname` 을 비워 두면 그 칸이 사라져 이름 바로 뒤에 판 번호가 옵니다 —
차례를 바꿨어도 그건 그대로입니다.

### 높이

0.59 에서 "칸을 세로로 더 길게" 를 480 으로 맞췄는데, 1080 짜리 화면에서
메인 화면에 스크롤이 생겼습니다. **한 화면에 다 들어오는 쪽이 "한눈에 본다"
는 이 화면의 뜻에 맞습니다.** 세 군데를 조금씩 줄였습니다.

| | 전 | 지금 | 아끼는 높이 |
|---|---|---|---|
| 칸 바닥 높이 | 480 | **390** | 90 |
| 칸 안쪽 여백 | 18,14 | **16,12** | 4 |
| 점수 글자 | 40 | **34** | 6 |
| 요약 목록 상한 | 300 | **230** | (그룹이 많을 때) 70 |

요약 목록 230 은 두 줄짜리 그룹 줄(38) 여섯 개입니다. 일곱 번째가 살짝 보여
**더 있다는 것이 드러납니다** — 딱 잘라 놓으면 그게 전부인 줄 압니다.

줄인 것은 **칸의 바닥 높이**일 뿐이라, 요약이 길면 칸이 다시 늘지 않고 칸
안에서 굴립니다.

**못 해 본 것**: 390 이 적당한지입니다. XAML 이 이 컨테이너에서 돌지 않아
화면 높이를 재 볼 수가 없습니다. 아직 스크롤이 생기거나 반대로 아래가 너무
비면 `MainView.xaml` 의 `MinHeight` 한 숫자만 고치면 됩니다 (그 자리에 왜
그 값인지 적어 뒀습니다).
