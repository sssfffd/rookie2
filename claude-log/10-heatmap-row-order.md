# 10 — 칸 폭을 바꾸면 IO 차례가 바뀌던 것

> 요청: "아 그리고 히트맵에서 5분으로 할때랑 1분으로 할 때 io순서가 바뀌던데 뭐임?"

버그가 맞습니다. **줄 차례를 칸 폭에 딸린 값으로 매기고 있었습니다.**

---

## 무엇이 잘못됐나

줄을 세우는 코드가 이랬습니다.

```csharp
res.Rows.Sort(delegate (HeatRow a, HeatRow b)
{
    int c = b.PeakMean.CompareTo(a.PeakMean);      // 칸들 중 가장 큰 값
    if (c != 0) return c;
    c = b.OverBuckets.CompareTo(a.OverBuckets);    // 차이 난 칸 수
    ...
});
```

두 값 **모두** 칸을 어떻게 잘랐는지에 딸려 있습니다.

| 값 | 1 분으로 볼 때 | 5 분으로 볼 때 |
|---|---|---|
| `OverBuckets` (차이 난 칸 수) | 5 | **1** — 다섯 칸이 한 칸이 되니까 |
| `PeakMean` (칸들 중 가장 큰 값) | 그 1 분의 값 | **더 작아짐** — 이웃한 조용한 4 분과 같이 평균되니까 |

칸 폭을 바꾸는 것은 **같은 로그를 다른 눈금으로 보는 것**일 뿐인데, 보는
눈금이 순위를 바꿔 버렸습니다. 특히 짧고 굵게 튄 IO 는 폭을 넓힐수록
아래로 밀려 내려갔습니다 — 정작 제일 봐야 할 IO 인데요.

---

## 어떻게 고쳤나

줄 차례는 **칸 폭과 무관한 값**으로만 매깁니다.

```csharp
int c = b.Severity.CompareTo(a.Severity);               // 1순위
if (c != 0) return c;
c = b.TotalOverSamples.CompareTo(a.TotalOverSamples);   // 2순위
if (c != 0) return c;
return 이름순;                                           // 3순위
```

| 값 | 무엇인가 | 왜 폭과 무관한가 |
|---|---|---|
| `Severity` | 가장 크게 벌어진 순간 ÷ 값 범위 | 표본 <b>하나하나</b>에서 나온 값이라, 칸을 어떻게 묶든 최대는 최대입니다 |
| `TotalOverSamples` | 기준을 넘은 표본의 총 개수 | 표본을 세는 것이지 칸을 세는 것이 아닙니다 |

### 왜 값 범위로 나누나

값 그대로 줄을 세우면 **값이 큰 채널만 위로 몰립니다.** 0~5 를 오가는
유량계가 3 벌어진 것(60%)이, 0~4000 인 압력계가 3 벌어진 것(0.075%)보다
아래에 놓입니다. 범위로 나누면 "이 채널 기준으로 얼마나 벌어졌나" 가 되어
IO 끼리 견줄 수 있습니다. 허용 오차·히트맵의 % 표시와 같은 밑값입니다.

### PeakMean 은 그대로 둡니다

칸을 **얼마나 빨갛게 칠할지**에는 계속 씁니다. 그건 "이 줄 안에서 어느
시간대가 제일 심한가" 라는 뜻이고, 그 질문에는 지금 보고 있는 칸 폭이
기준인 게 맞습니다. 쓰는 자리를 헷갈리지 않도록 주석에 못박아 뒀습니다.

---

## 새로 넣은 자체 테스트

`HeatmapOrderIsSameForEveryBucketWidth` — 벌어지는 모양이 다른 세 채널을
만들어 놓고 1 분과 5 분으로 각각 돌립니다.

| 채널 | 벌어지는 모양 | 최대 차이 | 벌어진 표본 |
|---|---|---|---|
| `SPIKE` | 한 표본만 크게 | 40 | 1 |
| `WIDE` | 5 분 동안 조금씩 | 8 | 300 |
| `SMALL` | 1 분 동안 아주 조금 | 2 | 60 |

- 두 폭에서 IO 차례가 **같은지**
- 제일 크게 튄 `SPIKE` 가 맨 위인지 (표본 수는 `WIDE` 가 300 배 많습니다)
- `PeakMax` 와 `TotalOverSamples` 가 두 폭에서 같은 값인지
- 반대로 `OverBuckets` 는 실제로 달라지는지 — 그래서 정렬에 쓰면 안 된다는
  것을 못박아 둡니다
