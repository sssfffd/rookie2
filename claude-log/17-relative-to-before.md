# 17 — 오차를 "이전 값 대비 %" 로 통일

> 요청: "허용오차나 %값으로 오차 보는건 그 시간대에 이전 log값 대비 이후
> 로그값의 차이를 %로 보는게 좋을 것 같네 지금 보면 히트맵에서 허용오차
> 바꿀때마다 뜨는 퍼센트가 매번 달라져
> 내가 설정하는 허용오차 퍼센트랑 히트맵이나 다른 곳에 오차 퍼센트를 쓰는
> 곳은 같게 맞춰줘야함"

두 가지를 지적하셨고, 둘 다 제가 만든 것입니다.

---

## 1. 왜 퍼센트가 허용 오차를 따라 움직였나

[08번](08-heatmap-tolerance-mismatch.md)에서 "빨간 칸인데 숫자가 허용 오차보다
작다" 는 문제를 고치면서, 칸에 적는 값을 **"기준을 넘은 표본만의 평균"** 으로
바꿨습니다.

```csharp
if (diff > row.Threshold) { cell.OverSamples++; overSum[k] += diff; }
...
cell.OverMean = overSum[k] / cell.OverSamples;
```

기준을 바꾸면 **평균 낼 표본이 바뀝니다.** 그러니 숫자가 따라 움직입니다.
빨간 칸의 숫자가 늘 기준보다 크다는 성질은 얻었지만, 대신 **재는 값이 재는
잣대에 딸려 버렸습니다.** 온도계 눈금을 바꿨더니 온도가 바뀌는 격입니다.

---

## 2. 왜 설정한 %와 화면의 %가 달랐나

더 뿌리 깊은 문제였습니다. 예전에는 퍼센트의 **밑값이 채널마다 달랐습니다.**

```
기준값 = 그 채널의 값 범위 x 설정한 퍼센트
```

- 같은 "1%" 가 채널마다 다른 숫자를 뜻했고,
- 화면에 적는 퍼센트의 밑값도 그 값 범위여서 설정한 퍼센트와 잣대가 달랐고,
- 로그를 언제 떴느냐(값이 얼마나 오르내렸느냐)에 따라 기준이 흔들렸습니다.

---

## 3. 어떻게 바꿨나

**그 순간의 값끼리 견줍니다.**

```
오차(%) = |이후 − 이전| / |이전| x 100
```

설정에 적는 퍼센트가 **바로 이 값**입니다. 화면에 적히는 퍼센트도 같은
값입니다. 채널마다 기준을 따로 만들지 않습니다.

| 이전 | 이후 | 오차 |
|---|---|---|
| 100 | 101 | 1% |
| 5000 | 5050 | 1% |
| 5 | 5.05 | 1% |
| 6466 | 6467 | 0.015% |
| 200 | 100 | 50% |
| 0 | 1 | 100% |
| 0 | 0 | 0% |

3~4 번째 줄이 요점입니다. 값 크기가 1000 배 차이 나는 두 채널이 **같은 1%**
로 판정됩니다. 예전 규칙에서는 이 둘이 달랐습니다.

### 이전 값이 0 이면

나눌 수가 없습니다. 0 에서 벗어난 것은 값이 통째로 달라진 것이므로
**100%** 로 봅니다 (0 → 0 은 0%). 상태(문자열) 채널도 이름이 다르면 100%
이고, 이쪽은 허용 오차와 상관없이 늘 차이입니다.

### 0 언저리의 약점과 탈출구

솔직히 말씀드리면 이 방식에는 약점이 하나 있습니다. **0 근처에서는 작은
흔들림도 퍼센트가 크게 나옵니다.** 0.001 → 0.002 는 100% 입니다.

그래서 **절대 오차**를 남겨 두었습니다. 그 값 이하로 벌어진 것은 퍼센트와
상관없이 같은 것으로 봅니다.

```
차이로 셈  ⟺  |이후 − 이전| > 절대 오차   그리고   오차(%) > 허용 오차(%)
```

0 근처를 오가는 채널이 섞여 있으면 절대 오차를 함께 걸어 두시면 됩니다.
계기 사양에서 "읽은 값의 몇 %, 단 최소 몇 이상" 이라고 적는 것과 같은 얘기입니다.

---

## 4. 칸에 적히는 숫자도 잣대와 끊었습니다

이제 칸에는 그 구간에서 **가장 크게 벌어진 순간**을 적습니다.

| | 예전 | 지금 |
|---|---|---|
| 칸의 숫자 | 기준을 넘은 표본만의 평균 | 가장 크게 벌어진 순간 |
| 기준을 바꾸면 | **숫자가 따라 움직임** | **그대로** |
| 빨간 칸 ⟺ 숫자 > 허용 오차 | 맞음 | 맞음 |

"가장 크게 벌어진 순간" 은 판정에 쓰는 값과 같습니다. 한 순간이라도 넘으면
빨간 칸인데, 그 "가장 크게 넘은 순간" 이 곧 적히는 숫자이기 때문입니다.
그래서 **숫자와 판정과 색이 모두 한 값에서 나옵니다.**

[04번](04-heatmap.md)에서 평균을 고른 이유(합계는 구간이 길수록 커지고,
부호 있는 합계는 진동하면 0)는 최대값도 그대로 만족합니다. 덤으로 평균이
가지고 있던 약점 — 잠깐 크게 튄 것이 묻히는 것 — 도 없습니다. 구간 평균은
설명 줄에 그대로 남겨 두었습니다.

값으로 볼 때와 퍼센트로 볼 때는 **같은 표본**의 두 가지 표현입니다.
보기를 바꿔도 가리키는 자리가 달라지지 않습니다.

---

## 5. 대시보드에도 같은 잣대를 넣었습니다

목록 맨 앞에 **[최대 오차 %]** 칸이 생겼습니다. 그 IO 에서 가장 크게 벌어진
순간의 오차이고, 설정한 허용 오차와 같은 잣대입니다. 제목을 누르면 그 기준으로
정렬됩니다.

예전의 [기준값] 칸은 없앴습니다. 기준이 채널마다 다르지 않으니 적을 것이
없습니다 — 설정에 적은 퍼센트 하나가 전부입니다.

---

## 6. 새로 쓴 자체 테스트

| 테스트 | 확인하는 것 |
|---|---|
| `ToleranceIsPercentOfBefore` | 계산식 자체(0 처리 포함)와, 값 크기가 1000 배 다른 두 채널이 같은 %로 판정되는지, 절대 오차가 탈출구로 동작하는지 |
| `ChangedMatchesMaxPercent` | 목록의 숫자와 "차이 났다" 판정이 어긋나지 않는지. **기준을 바꿔도 숫자는 그대로**인지 |
| `HeatmapRelativeTolerance` | 히트맵도 이전 값 대비 %로 판정하는지 |
| `HeatmapCellNumberDoesNotFollowTolerance` | **이번에 지적하신 그것.** 기준 0.1% 와 1% 에서 넘은 표본 수는 60 개와 1 개로 달라지지만, 칸에 적히는 숫자는 양쪽 다 5% 로 같은지 |
| `HeatmapStateNamesIgnoreTolerance` | 허용 오차를 최대로 키워도 상태 이름 차이는 잡히는지 |

기존 테스트 중 밑값(`BaseRange`)을 전제하던 셋은 지웠습니다. 더 이상
그런 개념이 없습니다.

---

## 7. 바뀐 것 요약

읽으시는 숫자가 달라 보일 수 있어서 적어 둡니다.

- **같은 로그에서도 "차이 난 IO" 목록이 달라질 수 있습니다.** 판정 잣대가
  바뀌었으니 당연합니다. 값이 크고 잔잔한 채널은 예전보다 덜 잡히고,
  값이 작은 채널은 더 잡힐 수 있습니다.
- 대시보드에 **[최대 오차 %]** 칸이 생기고 [기준값] 칸이 없어졌습니다.
- 히트맵 칸의 숫자가 "구간 평균" 에서 "가장 크게 벌어진 순간" 으로 바뀌었습니다.
- 저장된 설정의 퍼센트 값은 그대로 쓰입니다. 다만 **뜻이 달라졌으므로**
  한 번은 다시 맞춰 보셔야 할 수 있습니다.

이 컨테이너에는 .NET 이 없어 **컴파일도 실행도 못 해봤습니다.** 정적 검사는
모두 통과했고, 새 테스트의 기대값은 손으로 따라가 확인했습니다.
