# 23 — 변화량은 두 로그의 차이입니다 (앞 문서를 바로잡음)

> 요청: "너 변화량을 이전과 이후 로그 분석한게 아니라 그냥 개별의 로그로
> 분석했잖아 / 변화량은 2개의 log에서 하나가 나와야지 / 두 로그에서 동일한
> io의 차이값이 변화량으로 나와야한다고"

---

## 제가 잘못 읽었습니다

앞 요청의 "변화가 없으면 0, 1 증가하면 1, -1이면 -1" 을 **한 로그 안에서
시간에 따른 차분**으로 읽었습니다. 그게 아니라 **두 로그 사이의 차이**였습니다.

```
제가 만든 것 (틀림)              원하신 것 (맞음)
한 로그 안에서                   두 로그 사이에서
v[i] − v[i−1]                    이후[t] − 이전[t]
선 두 개 (이전 차분, 이후 차분)   선 하나
```

"2개의 log에서 하나가 나와야지" 가 정확히 이 말이었습니다. 선이 **하나**여야
했습니다.

앞 문서([22](22-delta-is-difference.md))의 2·3 장은 틀렸습니다. `Channel.Diff`
와 `Decimator` 의 `diff` 갈래는 도로 걷어냈습니다.

---

## 1. 무엇을 그리나

```
차이(t) = 이후 로그의 값 − 이전 로그의 값
```

같으면 0, 이후가 1 크면 +1, 1 작으면 −1.

이전과 이후를 나란히 그려 놓고 눈으로 견주는 대신 **벌어진 만큼만** 봅니다.

```
기존 값                        변화량
 6466.6 ┤ ╭──── 이후           +0.3 ┤   ╭───
 6466.3 ┤━╯──── 이전            0.0 ┤━━━╯
        두 선이 거의 겹침            벌어진 만큼만
```

값 눈금에서는 두 선이 겹쳐 보여 0.3 짜리 차이를 못 봅니다. 차이 눈금에서는
그것만 보입니다.

---

## 2. 어려운 자리는 시간 격자였습니다

두 로그가 **같은 시각에 찍혔다는 보장이 없습니다.** 이전이 0.1 초마다,
이후가 0.25 초마다일 수 있습니다. 게다가 [시간 맞추기] 로 한쪽을 밀어 둔
상태입니다.

### 한쪽 격자에 맞추면 놓칩니다

가장 쉬운 방법은 이전 로그의 표본마다 이후 값을 읽어 빼는 것입니다.
그런데 그러면 **이후 로그에서만 튄 자리가 통째로 사라집니다.**

```
이전   ●     ●     ●     ●        (2 초마다)
이후   ●  ●  ●  ●  ●  ●  ●        (1 초마다)
             ↑
          여기서만 105 로 튐 — 이전 격자에는 이 시각이 없음
```

그래서 **두 격자를 합쳐** 훑습니다. 어느 쪽 표본이든 그 시각에서 양쪽 값을
읽어 뺍니다.

### 표본마다 이진 탐색을 하면 안 됩니다

시각 하나마다 `SampleAt` 을 부르면 그 안에서 이진 탐색이 돕니다. 한 화면에
표본이 수십만 개면 프레임마다 수십만 번입니다.

두 로그 다 시간 순서라 **값을 읽을 자리가 뒤로 가지 않습니다.** 그래서
손가락 두 개를 앞으로만 밀면서 읽습니다. 표본 수에 비례하는 한 번의 훑기로
끝납니다.

```csharp
while (pb + 1 < nb && bt[pb + 1] <= t) pb++;
while (pa + 1 < na && at[pa + 1] + shift <= t) pa++;
```

### 겹치지 않는 구간에서는 아무것도 안 만듭니다

한쪽 기록이 없는 자리에서 없는 값을 지어내면, **로그가 짧은 쪽 끝에 가짜
차이가 생깁니다.** 기록 구간 밖은 NaN 이고, 거기서 선이 끊깁니다.

---

## 3. 접고 나서 빼면 늦습니다 (이건 앞 문서와 같음)

표본이 픽셀보다 촘촘하면 열마다 최소/최대만 남기고 접습니다.

```
이전 한 열      100, 100, 100
이후 한 열      100, 105, 100
접은 뒤 빼면    최대 105 − 최대 100 = 5,  최소 100 − 최소 100 = 0
실제 차이       0, +5, 0
```

이 예는 어쩌다 맞지만, 최대와 최소가 서로 다른 시각에 있으면 곧장 틀립니다.
**빼는 것이 먼저, 접는 것이 나중**이어야 합니다. 그래서 훑으면서 그 자리에서
빼고, 나온 차이를 열에 모읍니다.

### 성길 때와 촘촘할 때

한쪽 로그를 그릴 때처럼 갈림길이 있습니다 — 표본이 픽셀보다 성기면 그대로
잇고, 촘촘하면 접습니다. 접어서 그리면 표본이 없는 열에서 선이 끊겨
점만 찍힙니다(전에 겪은 그 증상).

그런데 두 격자를 합치면 표본이 몇 개가 될지 미리 알 수 없습니다. 그래서
**한 번 훑으면서 둘 다 채우고**, 표본 자리가 모자라면 접은 쪽을 씁니다.

---

## 4. 상태(문자열) 채널은 빼면 안 됩니다

상태 번호는 **로그마다 따로 매겨집니다.** 이전 로그에서 `RUN` 이 1 번이어도
이후 로그에서는 0 번일 수 있습니다. 빼면 뜻 없는 수가 나옵니다.

이름이 같으면 0, 다르면 1 로 봅니다. 대시보드·히트맵이 쓰는 규칙과 같게
맞췄습니다.

커서에도 숫자 대신 `차이 없음` / `상태 다름` 으로 적습니다.

---

## 5. 그 밖에 정한 것

| 무엇 | 어떻게 | 왜 |
|---|---|---|
| 선 색 | 강조색, 조금 굵게 | 이전/이후 어느 쪽 색도 아니어야 "두 로그를 뺀 선" 인 게 보입니다 |
| 0 선 | 눈금선으로 같이 긋고, 세로 범위에 0 을 반드시 넣음 | 어디가 "차이 없음" 인지 보여야 합니다 |
| 한쪽에만 있는 IO | 비워 둠 | 견줄 상대가 없습니다. 이유는 레인 머리글의 `이전에만`/`이후에만` |
| 차이 음영 | 차이 선과 0 선 사이를 칠함 | 이 눈금에는 선이 하나라 "두 선 사이" 가 없습니다 |
| "다르다" 판정 | **어느 눈금에서든 값으로** | 눈금을 바꿨다고 허용 오차의 뜻이 달라지면 대시보드·히트맵과 어긋납니다 |
| 세로 범위 | 겹치는 구간 전체를 한 번 재고 들고 있음 | 프레임마다 로그를 통째로 훑을 수는 없습니다. 밀기 값이 바뀌면 버립니다 |
| 커서 | `이전 6466.3  이후 6466.6  차이 +0.3` | 값만 적으면 커서와 선이 다른 말을 하고, 차이만 적으면 값을 알 수 없습니다 |

---

## 6. 자체 테스트

컴파일하고 실제로 돌려서 확인했습니다 (272개 통과).

| 테스트 | 확인하는 것 |
|---|---|
| `DifferenceOfTwoLogs` | 같으면 0, +1, −1, +2 가 그대로 나오는지. 차이 폭이 −1~+2 로 잡히는지. 표본 그대로 뽑기와, 자리가 모자랄 때 −1 을 돌려주면서도 접은 쪽은 채워지는지 |
| `DifferenceAcrossGrids` | 2 초 격자와 1 초 격자를 1000 초 밀어 맞췄을 때, **이후에만 있는 표본에서 튄 +5** 를 놓치지 않는지. 안 맞추면 겹치는 자리가 없다고 하는지 |
| `DifferenceOfStateChannels` | 상태 번호가 서로 어긋나는 두 로그에서 이름으로 견주는지 (같으면 0, 다르면 1) |
| `DifferenceOutsideOverlap` | 겹치기 전·후에는 값을 만들지 않는지, 한쪽에만 있는 IO 도 그런지 |

### 아직 확인 못 한 것

화면에서 실제로 어떻게 보이는지는 여전히 윈도우에서 돌려 봐야 압니다.
특히 차이 선의 **세로 범위** — 튀는 자리가 하나 있으면 그것 때문에 나머지가
납작해집니다. 그때는 [구간 맞춤] 이나 [계속 맞춤] 으로 지금 보이는 구간에만
맞출 수 있습니다.
