# 13 — jump 가 선언 안 됐다는 오류

> 요청: "jump라는 local이나 parameter가 선언 안되었다는데"

제가 낸 컴파일 오류가 맞습니다. 바로 앞 커밋에서 넣은 테스트에 있었습니다.

---

## 1. 무엇이 틀렸나

`ToleranceUsesValueSizeNotJustSpan` 테스트 안에서 `jump` 라는 이름을
**한 메서드에서 두 번** 선언했습니다.

```csharp
for (int i = 0; i < 200; i++)
{
    int jump = i >= 150 ? 6600 : baseline;     // ← 안쪽 블록
    ...
}
...
ChannelDiff jump = r.Items.Find(d => d.Name == "JUMP");   // ← 바깥 수준
```

C# 은 이것을 `CS0136` 으로 막습니다. 안쪽 블록에서 쓴 이름을 그 블록을
감싸는 바깥 범위에서 또 선언하면, 같은 글자 `jump` 가 메서드 안에서 두 가지를
가리키게 되기 때문입니다.

형제 블록끼리는 괜찮습니다 — `for` 문 두 개가 각각 `int i` 를 쓰는 것은
아무 문제 없습니다. 문제가 되는 것은 **한쪽이 다른 쪽을 감쌀 때**뿐입니다.

이름을 갈랐습니다.

```csharp
int vNear = ...;   // 이후 로그 쪽 값 (반복문 안)
int vJump = ...;
...
ChannelDiff near = ...;   // 결과 (메서드 수준)
ChannelDiff jump = ...;
```

앞서 `near_` 라고 밑줄을 붙여 뒀던 것도 같은 이유로 피해 간 이름이었는데,
이참에 `near` 로 되돌렸습니다.

---

## 2. 더 중요한 것 — 왜 못 잡았나

컴파일러가 없는 환경에서 만들다 보니, 매번 손으로 만든 검사를 돌립니다.
XAML 유효성, 리소스 열쇠, 이벤트 처리기, 바인딩 경로, 괄호 균형, csproj
파일 목록. 그런데 **이름 겹침을 보는 검사가 없었습니다.**

이런 오류를 낸 것이 이번이 두 번째입니다(첫 번째는 `RelayCommand` 생성자
모호성이었습니다). 그때마다 "다음부터 조심하겠다" 로 넘어갔는데, 사람이
조심해서 될 일이 아니라 기계가 볼 일이었습니다.

그래서 검사를 하나 더 만들어 **저장소에 넣었습니다.**

```
python scripts\check_shadowing.py
```

한 메서드 안에서 바깥 수준과 안쪽 블록이 같은 이름을 선언했는지 봅니다.
이번에 깨진 판본에 돌려서 `jump` 를 정확히 집어내는 것까지 확인했습니다.

### 만들면서 걸린 것들

처음 판본은 헛경보를 130 건 넘게 냈습니다. 쓸모가 없으니 세 가지를 고쳤습니다.

| 헛경보 | 원인 | 고침 |
|---|---|---|
| 온갖 변수가 다 걸림 | 닫는 괄호 직전의 내용을 바깥 수준으로 넣고 있었음 | 그 내용은 **지금 깊이**의 것 |
| `captured`, `start` | `try { x = 1; }` 에서 `try` 를 **타입 이름**으로 읽음 | `try` `catch` 등 낱말 목록 보강 |
| `i` | 중괄호 없는 `for (int i = 0; ...) 문장;` | 괄호 짝을 세어 머리 부분을 **항상** 안쪽으로 |

지금은 저장소 전체에서 지적이 0 건이고, 깨진 판본에서는 `jump` 하나를
정확히 잡습니다.

기존 검사도 `scripts/check_sources.py` 로 같이 옮겨 뒀습니다. 이제 저만
돌리는 게 아니라 언제든 돌려 보실 수 있습니다. **빌드에는 필요 없습니다** —
`build.bat` 은 이 폴더를 쓰지 않고, 파이썬이 없어도 프로그램은 그대로
빌드됩니다.

## 3. 그래도 남는 한계

이 검사들은 컴파일러가 아닙니다. 타입이 안 맞는다거나, 메서드 이름을 잘못
적었다거나, 오버로드가 모호하다거나 하는 것은 못 잡습니다. **여전히 처음
F5 에서 오류가 날 수 있습니다.** 나면 그 내용을 그대로 알려 주세요 —
이번처럼 한 줄만 보여 주셔도 충분합니다.
