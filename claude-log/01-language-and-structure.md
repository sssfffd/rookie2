언어는 이미 정해 주셨으니, 실제로 갈리는 건 **"C# 의 어느 런타임과 어느 UI
기술이냐"** 였습니다. 여기가 제일 크게 걸리는 부분이라 먼저 적습니다.

## 1. 런타임: .NET Framework 4.6.1 로 갔습니다

| 후보 | 윈도우 7 | VS2017 로 빌드 | 복사만 해서 실행 | 판단 |
|---|---|---|---|---|
| **.NET Framework 4.6.1** | ✅ SP1 에서 동작 | ✅ 기본 지원 | ✅ exe + dll 만 복사 | **고름** |
| .NET Framework 4.8 | ✅ SP1 | ⚠️ VS2017 15.9 이상 | ✅ | 4.6.1 로도 충분 |
| .NET 8 (자체 포함) | ❌ **지원 안 함** | ❌ VS2022 필요 | ✅ (단 ~70MB) | 윈도우 7 때문에 탈락 |
| .NET Core 3.1 | ❌ 지원 안 함 | ❌ | ✅ | 탈락 |

윈도우 7 을 지원해야 한다는 조건이 사실상 답을 정합니다. **.NET 5 이상은
윈도우 7 을 지원하지 않고, VS2017 로는 빌드할 수도 없습니다.**

4.6.1 을 고른 이유는 VS2017 이 기본으로 들고 있는 대상 버전이라 추가 설치가
없기 때문입니다. 4.8 로 올려도 되지만 얻는 게 없습니다.

### 미리 알아야 할 런타임 (요구사항에 있던 부분)

- **윈도우 10 / 11**: .NET Framework 4.8 이 운영체제에 들어 있습니다. **따로 깔 것 없음.**
- **윈도우 7 SP1**: .NET Framework 4.6.1 이상이 필요합니다. 윈도우 업데이트를 받은
  PC 면 대개 이미 있습니다. 없으면 .NET Framework 4.8 오프라인 설치 파일을
  **한 번만** 설치하면 됩니다. 프로그램 자체는 그대로 복사해서 씁니다.
- 윈도우 7 SP1 **이전** 버전은 지원하지 않습니다.

## 2. 화면: WinForms + GDI+ 직접 그리기

| 후보 | 판단 |
|---|---|
| **WinForms + GDI+** | **고름.** 그래프를 픽셀 단위로 통제할 수 있고, 윈도우 7 에서도 같은 동작. 가벼움 |
| WPF | XAML 레이아웃은 편하지만, 수만 점을 그릴 때 결국 `WriteableBitmap` 이나 `DrawingVisual` 로 직접 그리게 됩니다. 그러면 WinForms 대비 이득이 별로 없고 덩치만 커집니다 |

그래프가 이 프로그램의 본체이고, 그 부분은 어느 쪽을 고르든 직접 그려야
합니다. 그러면 나머지(창, 버튼, 목록)가 가벼운 쪽이 낫습니다.

## 3. 구조: DLL 하나 + EXE 하나 (그대로 유지)

```
LogScope.exe  ──참조──▶  LogScope.Core.dll
 (WinForms)                (파싱 / 데이터 / 비교 / 설정)
```

C++ 때와 나눈 지점은 같지만, **C ABI 를 따로 만들지 않았습니다.**
C++ 에서는 EXE 와 DLL 이 다른 CRT 로 빌드되면 힙이 깨지므로 `extern "C"` 로
납작하게 펴야 했습니다. .NET 어셈블리끼리는 그 문제가 없어서, 그 계층
(`logcore.h` 의 `lc_*` 함수 200여 줄)이 통째로 사라졌습니다.

`LogScope.Core` 는 `System.Windows.Forms` 를 참조하지 않습니다. 그래서 콘솔
테스트로 파싱 로직만 따로 돌릴 수 있습니다.

## 4. 바깥 라이브러리: **하나도 안 썼습니다**

이게 C# 으로 옮기면서 제일 크게 이득 본 부분입니다.

| 필요한 것 | C++ 때 | C# 에서 |
|---|---|---|
| .xlsx 압축 풀기 | zip inflate 직접 구현 | `System.IO.Compression` (.NET 기본) |
| XML 읽기 | 직접 구현 | `System.Xml.XmlReader` (.NET 기본) |
| CSV | 직접 구현 | 직접 구현 (145줄 → 비슷) |
| JSON 설정 | 직접 구현 | 직접 구현 (약 200줄) |
| 그리기 | Direct2D | `System.Drawing` (.NET 기본) |

NuGet 패키지가 **하나도 없습니다.** `packages.config` 도 `PackageReference` 도
없어서, 빌드할 때 네트워크에 나가지 않습니다.

### 위험해 보이는 부분 (요구사항에서 설명하라고 하신 것)

1. **XML 외부 실체 참조(XXE)** — 남이 준 .xlsx 안의 XML 이 로컬 파일을 읽게
   만들 수 있습니다. `XlsxReader.SafeSettings()` 에서 `DtdProcessing.Prohibit`
   와 `XmlResolver = null` 로 막아 뒀습니다. **이 두 줄을 지우면 안 됩니다.**
2. **압축 폭탄** — 작은 zip 이 수십 GB 로 풀릴 수 있습니다. 상한을 걸 수 있게
   해 뒀지만 **기본은 무제한**입니다. "파일 크기 상한은 없게" 라는 요구를
   따른 것입니다. 남이 준 파일을 자주 열게 되면 켜는 편이 낫습니다.
3. **파이썬 AI 모듈(선택 기능)** — 켜면 지정한 실행 파일을 자식 프로세스로
   띄웁니다. 이게 이 프로그램에서 가장 위험한 자리입니다. 기본은 꺼져 있고,
   사람이 경로를 직접 지정해야만 동작합니다. 자세한 것은
   [docs/SECURITY.md](../docs/SECURITY.md).

## 5. CMake 는 어떻게 넣었나

C# 은 `.csproj` 가 사실상 표준이고, CMake 의 C# 지원은 Visual Studio 생성기에서만
동작하면서 파일 목록을 CMake 문법으로 다시 적어야 합니다. 그래서 **손으로 쓴
`.csproj` 를 그대로 두고, CMake 는 그것들을 묶어 VS 솔루션을 만들어 주는
역할**로 넣었습니다 (`include_external_msproject`).

```
cmake -S . -B build -G "Visual Studio 15 2017" -A x64
cmake --build build --config Release
```

CMake 가 없는 PC 에서도 `build.bat` 하나로 빌드됩니다. 둘 중 아무 쪽으로
빌드해도 결과는 같습니다.

## 6. 1000만 칸을 감당하는 방법

요구사항에서 "언어 선택에 제일 크게 걸리는 부분" 이라고 하신 곳입니다.
C# 이라고 못 할 이유는 없는데, **어떻게 담느냐**가 전부입니다.

| 방법 | 1000만 칸 메모리 | 판단 |
|---|---|---|
| `double[]` 채널마다 | 80 MB | 무난 |
| **`float[]` 채널마다** | **40 MB** | **고름.** 로그 값은 소수점 몇 자리라 float 로 충분 |
| `List<double>` | 80 MB + 증가 중 최대 2배 | 증가할 때 복사가 큼 |
| `object[]` / `Cell[]` | 240 MB + GC 부담 | 안 됨 |

추가로:

- **표를 통째로 메모리에 올리지 않습니다.** 한 줄씩 흘려 읽으면서 바로
  채널 배열에 씁니다.
- **전치(transpose)를 하지 않습니다.** C++ 때는 "행이 IO" 배치를 전치했는데,
  1000만 칸 복사가 여는 시간의 큰 부분이었습니다.
- 배치를 판별하려면 앞부분을 붙들어야 하는데, 그 양을 **줄 수와 칸 수 둘 다**로
  제한합니다. "행이 IO" 배치는 한 줄이 표본 5만 칸이라 줄 수만 막으면
  소용없기 때문입니다.
- **AnyCPU + Prefer32Bit=false** 로 빌드해서 64비트 윈도우에서는 64비트로
  돕니다. 이전/이후 두 개를 동시에 열어도 2GB 벽에 걸리지 않습니다.
- 그릴 때는 픽셀 열마다 최소/최대만 뽑습니다. 표본 5만 개를 1000 픽셀에
  그릴 때 선 긋기가 5만 번에서 1000 번으로 줄어듭니다.
