# 21 — 도구 줄 3 줄로, 맞추기는 값 단위로, 가로축 다시 점검

> 요청:
> - 이거 그래프쪽에 메뉴바가 너무 줄이 길어 ~~3줄 안에 처리될 수 있게 해야되
>   메뉴바가 세로로 길면 안됨
> - 그리고 시간 맞추기 기능을 히트맵에서도 적용하고
> - 그리고 지금 시간 맞추기가 0과 1만 되어있는데 해당 io의 최댓값까지 나올 수 있게 해주고
> - 0에서 1로 바뀔때라고하면 1로 시작하는 부분도 인식할 수 있음? 인식하게끔
> - 그리고 지금 로그의 시간이라고 하면 이전엔 자동 맞춤이 됬는데 지금은 안되거든?
>   둘다 가능하게끔
> - 그리고 다른 io로 가로축 기준 잡을 때 이상하게 잡히는 거 같은데 다시확인해봐

---

## 1. 도구 줄 — 세 줄 안에

지난번에 가로축과 시간 맞추기를 도구 줄에 그대로 펴 놓은 게 잘못이었습니다.
콤보 두 개 · 입력 칸 · 단추가 한 줄을 통째로 먹었습니다.

세 가지를 했습니다.

### 글자를 줄였습니다

| 전 | 후 |
|---|---|
| 레인 (채널마다 한 줄) | 레인 |
| 겹쳐보기 (눈금 공유) | 겹쳐 |
| 0–1 정규화 | 0–1 |
| 전체 구간 보기 / 시간 확대 / 시간 축소 | 전체 / 확대 / 축소 |
| 값 확대 / 값 축소 / 보이는 구간에 맞추기 / 값 배율 되돌리기 | 확대 / 축소 / 구간 맞춤 / 되돌리기 |
| 차이 구간 음영 / 이전·이후 벌려 그리기 | 차이 음영 / 벌려 그리기 |

없앤 게 아니라 **풍선 도움말로 옮겼습니다.** 마우스를 올리면 전과 같은
설명이 나옵니다.

도구 줄 끝에 있던 `휠 = 시간 확대, Shift+휠 = …` 한 줄은 **아래 띠로**
내렸습니다. 그것만으로 도구 줄 한 줄이었습니다.

### 한 번 정해 놓고 쓰는 것은 접었습니다

가로축과 시간 맞추기는 단추 하나로 접고, 누르면 판이 내려옵니다.

```
┌ [가로축 · 시간 맞추기 ▾] ┐
└──────────────────────────┘
   ↓ 누르면
   ┌──────────────────────────────────┐
   │ 가로축                            │
   │ [(로그의 시간)              ▼]   │
   │ ──────────────────────────────── │
   │ 시간 맞추기                       │
   │ 기준 IO [(안 씀)            ▼]   │
   │ 기준 값  어느 순간   몇 번째      │
   │ [1   ▼] [그 값이 될 때 ▼] [1]    │
   │ [맞추기 해제] [닫기]              │
   └──────────────────────────────────┘
```

단추 글자는 상태를 보여 줍니다(`맞추기 켜짐`, `가로축 바꿈`). **폭은
고정**했습니다 — 글자 길이가 바뀌면 그때마다 도구 줄이 다시 접혀 줄 수가
달라집니다. 전에 겪은 그 문제입니다.

토글이 아니라 **그냥 단추**입니다. 토글로 두면 팝업이 열린 채 그 단추를
눌렀을 때, 팝업이 먼저 바깥 누름으로 닫히면서 단추는 다시 켜져
"눌러도 안 닫히는" 것처럼 보입니다. 열기만 맡기고, 닫기는 바깥 누름과
[닫기] 에 맡겼습니다. 방금 닫힌 뒤 250ms 안의 누름은 무시해서 다시 열리는
것도 막았습니다.

### 그래도 넘치면 굴립니다

창이 아주 좁으면 네 줄이 될 수 있습니다. 그래서 **높이 상한을 걸었습니다.**
줄 하나가 42 (단추 28 + 위아래 여백 6 + 묶음 테두리 2) 라 세 줄이면 126,
상한은 132 입니다. 넘치면 도구 줄 안에서 세로로 굴러갑니다.

**이게 진짜 보장입니다.** 글자를 줄인 건 "대개 두세 줄" 로 만들 뿐이고,
어떤 창 크기에서도 세로로 안 자란다는 건 상한이 지킵니다.

## 2. 히트맵에서도 시간 맞추기

히트맵 도구 줄에 **같은 단추**를 달았습니다. 판도 같은 것 하나입니다 —
뷰모델을 하나만 두고 두 화면이 나눠 씁니다.

```
ShellVm
  └ AlignVm  ←─┬── GraphVm.Align
               └── HeatmapVm.Align
```

각자 들고 있으면 한쪽에서 맞춰 놓고 다른 쪽으로 갔을 때 그 설정이 안
보이거나, 더 나쁘게는 서로 다른 값으로 그려집니다.

그리고 세 가지를 더 고쳤습니다.

- 히트맵을 **보고 있는 중에** 맞추기를 바꾸면 그 자리에서 다시 계산합니다.
  비워만 두면 화면이 텅 비고 왜 비었는지도 알 수 없습니다.
- 맞추기를 바꿨는데 아직 다시 계산하지 않았으면 **안내 줄**이 뜹니다.
  전에는 허용 오차만 보고 있어서, 옛 기준으로 그려진 칸을 새 기준인 줄
  알고 읽을 수 있었습니다.
- 요약 줄에 지금 무엇으로 맞췄는지 적습니다.

## 3. 0 과 1 말고, 그 IO 에 나온 값이면 무엇이든

전에는 무조건 0/1 로 갈랐습니다. 0~5 로 오르는 단계 신호를 "5 가 되는
순간" 으로 맞출 수가 없었습니다.

이제 그 IO 에 **실제로 나온 값**을 모아 고르게 합니다.

| 채널 | 고를 수 있는 값 |
|---|---|
| 디지털 | 0, 1 |
| 단계 신호 | 0, 1, 2, 3, 4, 5 … |
| 상태(문자열) | `IDLE`, `RUN`, `STOP` … (이름 그대로) |
| 값이 64 가지를 넘는 진짜 아날로그 | 0 / 1 (값 범위 한가운데를 문턱으로) |

값을 다 모을 수는 없으니 **64 가지**에서 끊습니다. 넘으면 진짜 아날로그로
보고 전처럼 문턱 하나로 가릅니다. 문턱값은 목록에 같이 적습니다
(`1 (문턱 49.5 위)`).

> 값 모으기는 해시로 합니다. 채널마다 부르는 함수인데 표본이 수백만 개일
> 수 있어서, 값 하나마다 목록을 훑으면 그것만으로 몇 초가 갑니다. 종류가
> 64 를 넘는 순간 바로 멈추므로, 진짜 아날로그 채널은 몇십 표본 만에
> 끝납니다.

**없는 값을 고르면 조용히 넘어가지 않습니다.** 한쪽 로그에만 있는 값으로
맞추라고 하면, 다른 값으로 바꿔치기해서 두 로그를 서로 다른 사건에
맞추는 것보다 실패하는 편이 낫습니다.

## 4. "1 로 시작하는" 로그도 잡습니다

이게 이번에서 제일 실제적인 고침입니다.

```
이전 로그  ─────┐              0 → 1 이 30 초에
           0    │1
                30

이후 로그  ┌─────────────────  처음부터 1
           1
           200
```

기록을 늦게 건 로그에서 흔합니다. 전에는 "이후 로그에서는 그 IO 가 한 번도
바뀌지 않았습니다" 로 실패했습니다. 맞출 수 있는 로그였는데요.

이제 **"1 이 되는 순간"** 으로 읽습니다. 이미 1 로 시작했다면 그 로그에서는
**첫 표본이 그 순간**입니다. 위 예에서 밀기 값은 30 − 200 = −170.

그래서 어느 순간을 잡을지의 뜻도 다시 적었습니다.

| 고르기 | 뜻 |
|---|---|
| 그 값이 될 때 | 그 값이 되는 순간. **처음부터 그 값이면 시작 지점** |
| 그 값에서 벗어날 때 | 그 값에서 다른 값으로 가는 순간 |
| 값이 바뀔 때 | 아무 변화나 |

"벗어날 때" 에는 같은 규칙을 안 넣었습니다. 그 값이 아닌 채로 시작한 로그는
**그 값에 있었던 적이 없으므로 벗어난 적도 없습니다.** 대칭으로 만들면
모든 로그가 첫 표본에서 "벗어남" 이 되어 버립니다.

빈 값(NaN) 뒤의 첫 표본도 시작으로 치지 않습니다. 직전을 모르는 자리를
사건으로 만들지 않습니다.

### 후보 목록도 같이 고쳤습니다

전에는 **양쪽 다** 바뀌는 IO 만 목록에 올렸습니다. 그러면 위 예의 IO 가
목록에서 빠집니다 — 이후 로그에서 안 바뀌니까요.

이제 **한쪽에서라도** 바뀌면 후보입니다.

## 5. "로그의 시간" 으로 되돌려도 자동 맞춤이 안 되던 것

버그였습니다. 원인은 한 줄이었습니다.

```csharp
// 예전
if (r.Ok)
{
    Settings.ManualShift = r.Shift;
    Settings.AutoAlign = false;     // ← 여기
}
```

사건으로 맞추면 자동 맞춤을 껐습니다. 둘이 겹치면 서로를 밀어내니까 그
자체는 맞습니다. 그런데 **맞추기를 해제해도 이 값이 그대로 남았습니다.**
기준 IO 만 지워지고 `AutoAlign` 은 계속 꺼진 채라, 시작 시각 자동 맞춤이
돌아오지 않았습니다.

덤으로 설정 창에서 손으로 넣어 둔 밀기 값도 덮여 사라졌습니다.

**설정을 건드리지 않게 고쳤습니다.** 사건으로 나온 밀기 값은 따로 들고
있다가 견줄 때 합칩니다.

```csharp
bool trigger = 기준 IO 가 있고 맞추기에 성공했는가;
o.Shift     = Settings.ManualShift + (trigger ? TriggerShift : 0);
o.AutoAlign = !trigger && Settings.AutoAlign;
```

그래서 이제,

- 기준 IO 를 고르면 → 사건으로 맞춤 (자동 맞춤은 비켜섬)
- `(안 씀)` 으로 되돌리면 → **설정에 적힌 대로 자동 맞춤이 돌아옴**
- 설정 창의 밀기 값은 → 어느 쪽이든 그 위에 더해지는 미세 조정

"둘 다 가능" 이 이 뜻이라고 봤습니다.

## 6. 가로축이 이상하게 잡히던 것

세 가지가 나왔습니다.

### (1) 값이 커지면 표본이 뭉개집니다 — 제일 큰 것

채널 값은 `float` 로 담습니다. 표본이 수백만 개라 `double` 이면 메모리가
두 배입니다. 유효자리는 **약 7 자리**입니다.

1970 년부터 센 밀리초 같은 열을 가로축으로 놓으면,

```
1,700,000,000,000  ← 이 크기에서 float 가 구분할 수 있는 단위는 약 131,072
    100 간격       ← 표본 간격
```

**표본 수천 개가 전부 같은 자리로 갑니다.** 그래프는 계단이 되고, 세로선만
잔뜩 그려집니다. "이상하게 잡힌다" 가 이겁니다.

읽을 때 이미 잃은 자릿수라 되살릴 수가 없습니다. 그래서 **거부하고 이유를
말합니다.**

```
"EPOCH" 는 값이 너무 커서(1,700,000,019,900) 표본을 구분하지 못합니다.
이 크기에서는 204,800 단위까지만 담기는데, 표본 간격은 100 입니다.
경과 시간처럼 0 에서 시작하는 열을 쓰거나 로그의 시간을 쓰세요.
```

목록에도 안 올립니다.

### (2) 눈금 글자가 지수 표기로 나왔습니다

가로축을 다른 IO 로 놓으면 눈금이 `TimeKind.Number` 갈래를 타는데, 거기만
`G6` 서식이 남아 있었습니다. 값이 1000 만을 넘으면 `1.7E+12` 로 적혔습니다.
지수 표기를 없애려고 만들어 둔 `NumberText.Plain` 을 쓰게 고쳤습니다.

### (3) 축을 갈아 끼울수록 로그 뒤가 잘렸습니다

```csharp
int n = Math.Min(v.Length, SampleCount);   // SampleCount = Times.Length
```

`Times` 는 **지금 걸려 있는 가로축**입니다. 축을 한 번 끼우면 그 길이가
새 기준이 되고, 다음에 다른 축으로 바꾸면 그보다 짧아질 수 있습니다.
바꿀 때마다 조금씩 짧아져 **로그 뒷부분이 말없이 사라집니다.**

원래 표본 수로 세게 고치고, 값이 모자라면 거부합니다.

### 겹치는 건 막지 않고 알려 줍니다

1 초 단위 카운터를 100ms 로그의 가로축에 놓으면 표본 10 개가 같은 자리에
겹칩니다. 이건 잘못이 아니라 그 열의 성질이라 막지 않습니다. 대신 왜
그렇게 보이는지 적어 줍니다.

```
"TICK" 는 표본 100 개 중 90 개가 직전과 같은 값입니다.
그 구간은 가로로 겹쳐 그려집니다.
```

## 7. 목록을 갈무리했습니다 (고쳐 놓고 보니 필요했던 것)

후보를 뽑으려면 채널을 전부 훑어야 합니다 — 가로축은 오름차순인지, 맞추기는
한 번이라도 바뀌는지 보려고요. 채널 200 개에 표본 5 만이면 천만 번입니다.

그런데 `ItemsSource` 로 묶인 속성은 **화면이 다시 그려질 때마다** 불립니다.
그대로 두면 콤보를 한 번 펼 때마다 로그를 통째로 훑습니다. 로그가 바뀔
때만 버리도록 갈무리했습니다.

`SelectedItem` 도 손봤습니다. 목록을 다시 채우면 WPF 가 잠깐 `null` 을
밀어 넣는데, 그걸 "안 씀" 으로 받아들이면 목록을 새로 고칠 때마다 고른
IO 가 조용히 지워집니다. `null` 은 무시합니다.

## 8. 자체 테스트

컴파일하고 실제로 돌려서 확인했습니다 (243개 통과, 이번에 12개 늘었습니다).

| 테스트 | 확인하는 것 |
|---|---|
| `TriggerAlignCountsStartAsEdge` | 처음부터 1 인 로그가 첫 표본으로 맞춰지는지(밀기 −170), `AtStart` 로 구분되는지, 한쪽만 바뀌어도 후보인지, "아무 변화" 로는 여전히 못 맞추는지 |
| `TriggerAlignOnAnyLevel` | 0~5 단계 신호에서 값이 6 개 잡히는지, 최댓값 5 로 맞춰지는지, 중간 값 3 으로도 맞고 "3 에서 벗어나는" 순간(=40)도 맞는지, 없는 값 9 는 거부하는지 |
| `TriggerAlignOnEdge` | 값이 둘뿐인 채널은 문턱을 안 쓰고 값 그대로 보는지, 값이 100 가지인 채널은 문턱(49.5)으로 가르고 그 값이 결과에 실리는지 |
| `AxisRefusesCoarseValues` | 1.7e12 열은 거부하고 이유를 말하는지, 후보에서도 빠지는지, 같은 간격이라도 0 에서 시작하는 열은 되는지 |
| `AxisWarnsOnFlatRuns` | 겹치는 열은 막지 않고 몇 개가 겹치는지 알려 주는지, 되돌리면 알림도 사라지는지 |
| `SettingsRoundTrip` | 기준 값이 저장/복원되는지, "알아서 고름"(NaN)이 0 으로 떨어지지 않는지 |

### 아직 확인 못 한 것

- **XAML 자체**는 여전히 컴파일해 보지 못했습니다. 팝업 · 높이 상한 · 새 판이
  화면에서 어떻게 보이는지는 윈도우에서 돌려 봐야 압니다.
- 5 번(자동 맞춤 되돌아오기)은 `AppState` 에 있는데 그건 App 쪽이라
  테스트가 닿지 않습니다. 코드로만 확인했습니다.
