# 47. `.frm` 을 직접 읽기 (0.57)

> datadir안에 frm이랑 ibd로 나뉘어있으면 어캄?
> mysql 5.6.19

## 왜 이 길밖에 없었나

판본이 정해지자 길이 하나로 줄었습니다.

| | MySQL 8.0 | **MySQL 5.6** |
|---|---|---|
| 표 정의가 있는 곳 | `.ibd` 안의 SDI | **`.frm`** |
| `ibd2sdi` | 통합니다 | **없는 프로그램입니다** |
| 바로 전에 제가 권한 길 | SDI 직접 읽기 | **통하지 않습니다** |

그래서 "바깥 프로그램 없이 5.6 폴더에서 표 모양을 아는 길" 은 `.frm` 을 직접
읽는 것뿐이었습니다. 제가 46 에서 "유일한 길" 이라고 적은 그 길입니다.

## 형식은 어떻게 알았나

`.frm` 은 공개 규격이 없습니다. 하지만 **같은 일을 하는 도구들이 있습니다**
(서버 없이 `.frm` 하나로 `CREATE TABLE` 을 되살리는 도구). 그 구현에 적힌
자리값을 보고 맞췄습니다.

**코드는 가져오지 않았습니다.** 그 도구들은 GPL 이라 이 프로그램에 섞으면
안 됩니다. 파일 형식 자체는 누구의 것도 아니고, 구현은 처음부터 다시 썼습니다.
이 구분을 지키는 것이 "바깥 라이브러리를 자제한다" 는 규칙의 본뜻에도 맞습니다 —
남의 코드가 들어오지 않습니다.

자리값은 이렇습니다 (작은 끝 먼저).

```
머리 64 바이트
  0x00  FE 01            표식 (뷰는 "TYPE=VIEW" 로 시작하는 글자 파일)
  0x04  uint16           이 길이를 64 에 더한 자리에 forminfo 의 자리가 적혀 있음
  0x06  uint16           키 조각의 자리
  0x0E  uint16           키 조각의 길이 (0xFFFF 면 0x2F 의 uint32)
  0x33  uint32           만든 MySQL 판 (50619 = 5.6.19)

forminfo (288 바이트)
  +258  uint16           열 수
  +260  uint16           screens 길이 (건너뜀)
  +268  uint16           열 이름 조각 길이
  +274  uint16           ENUM/SET 값 조각 길이

forminfo + 288 + screens 부터
  열 정보 17 바이트 × 열 수 → 이름 → ENUM/SET 값 → 주석

열 정보 17 바이트
  +3  uint16 길이(바이트)   +8  uint16 flags   +11,+14 문자셋 번호
  +12 uint8  ENUM 묶음 번호  +13 uint8  타입
```

## 조용히 틀릴 수 있는 자리 셋

이 작업의 어려움은 바이트를 읽는 것이 아니었습니다. **읽은 것을 어떻게
적을지**였습니다.

### 1. 기본값 — "없음" 과 "모름" 은 다릅니다

`.frm` 의 기본값은 레코드 조각을 타입마다 풀어야 나옵니다. 이번에는 읽지
않았습니다. 그러면 `Default` 가 `null` 이 되는데, 우리 모델에서 `null` 은
**"적혀 있지 않음"** 이었습니다. 그대로 두면 이렇게 됩니다.

```
이전(.frm)  기본값 모름  →  null  →  "없음"
이후(.sql)  DEFAULT '0'  →  "0"
                            ↓
          "기본값 없음 → '0' 으로 바뀜" (거짓)
                            ↓
          ALTER TABLE ... SET DEFAULT '0'  (쓸모없는 글)
```

**없는 차이를 만들고, 그걸 맞추는 SQL 까지 만들어 줍니다.** 그래서
`DbColumn.DefaultKnown` 을 두고, 한쪽이라도 모르면 기본값은 **견주지
않습니다.** 양쪽이 다 `.frm` 이면 서로 모르니 그냥 빠집니다.

대신 **기본값이 바뀐 것은 `.frm` 만으로는 알 수 없습니다.** 모르는 것을
모른다고 두는 대가입니다. 그쪽이 맞습니다.

### 2. 길이는 바이트입니다

`.frm` 의 길이는 **바이트 수**입니다. utf8 열은 글자당 3 바이트라
`varchar(64)` 가 `192` 로 적혀 있습니다. 문자셋 번호로 나눠야 `varchar(64)` 가
됩니다. 안 나누면 **모든 글자 열이 "타입이 달라졌다"** 로 보입니다.

그래서 문자셋 번호 → 글자당 바이트 표를 넣었습니다. 모르는 번호는 1 로 보고
**그렇다고 적습니다.** 다만 양쪽 `.frm` 이 같은 서버에서 나왔으면 모르는
번호여도 양쪽이 똑같이 틀리므로 차이로는 보이지 않습니다.

### 3. 문자셋은 타입 글자에 안 넣습니다

`CHARACTER SET utf8 COLLATE utf8_general_ci` 를 타입에 붙이면 보기엔
친절합니다. 그런데 덤프의 `CREATE TABLE` 은 열마다 적어 줄 때도 있고 안 적어
줄 때도 있습니다. **한쪽만 적히면 같은 열이 "타입이 달라졌다" 가 됩니다.**
없는 차이를 만드는 쪽이 더 나쁩니다.

같은 이유로 `NOT NULL` 과 `AUTO_INCREMENT` 도 타입 글자에 섞지 않습니다.
NULL 허용은 따로 들고 있어서, 섞으면 같은 것을 두 번 견주게 됩니다.

## 덤프가 이깁니다

폴더에 `recipe.frm` 과 `recipe.sql` 이 같이 있으면 **`.sql` 이 이깁니다.**
값까지 아는 쪽이 더 많이 아는 것이고, 모양만 아는 것으로 덮으면 아는 것이
줄어듭니다.

그래서 폴더를 훑을 때 **`.frm` 을 나중에** 읽습니다. 파일 차례에 맡기면 폴더를
훑는 순서에 따라 결과가 달라집니다. 안 쓴 `.frm` 이 몇 개인지 화면에 적습니다.

## 판 번호를 화면에 적는 이유

```
.frm 12 개에서 표 모양을 읽었습니다 (만든 판 5.6.19).
열 이름 · 타입 · NULL 허용 · 순서 · 기본 키입니다 —
값과 기본값(DEFAULT)은 .frm 에 없어 견주지 않습니다.
```

**이게 자체 점검입니다.** 머리 부분의 자리값을 잘못 잡았으면 판 번호부터
엉뚱하게 나옵니다. `5.6.19` 로 찍히면 적어도 머리는 제대로 읽은 것입니다.
`0.0.0` 이나 `12.34.56` 이 나오면 거기서부터 틀린 것이니 알려 주세요.

## 검사 — 그리고 못 한 검사

**한 것**

- 자리값대로 `.frm` 을 **만들어서** 읽혔습니다. `int(11)` · `varchar(64)`
  (utf8 나누기) · `decimal(6,2)` · `datetime(3)` · `enum('on','off')` · 한글
  열 이름 · NOT NULL · 기본 키 · 기본값 모름까지 봅니다.
- 어긋난 파일에서 **터지지 않고 이유를 적는지**: 짧은 파일, 표식이 다른 파일,
  뷰, 중간이 잘린 파일, 열 수가 이름 수와 안 맞는 파일.
- 기본값을 모르는 열이 **거짓 차이를 만들지 않는지** (위의 1번).
- 폴더에서 덤프가 이기는지, 안 쓴 `.frm` 을 밝히는지.
- 자리값을 **참고 구현의 식과 하나씩 맞춰** 봤습니다 — 머리 8 곳, forminfo
  6 곳, 열 17 바이트 8 곳, 키 3 곳.
- 테스트 **563 통과 / 0 실패** (41 개 새로 더함).

**못 한 것 — 이게 중요합니다**

**진짜 MySQL 이 쓴 `.frm` 으로는 못 해 봤습니다.** 이 컨테이너에 MySQL 이
없고, 공개 저장소에서 시험용 `.frm` 도 받지 못했고(PyPI·GitHub API 가 막혀
있습니다), 참고 구현을 깔아서 교차 실행하는 것도 안 됐습니다.

제가 만든 파일로 하는 시험은 **만드는 쪽과 읽는 쪽이 같은 표를 쓰므로**, 표를
잘못 옮겼다면 둘이 똑같이 틀리고 시험은 통과합니다. 그래서 지키는 것은
"표대로 읽는가" 와 "어긋난 파일에서 이유를 적는가" 까지입니다.

**실제 확인은 `.frm` 하나를 읽혀 보는 것입니다.** 판 번호가 `5.6.19` 로
찍히는지, 열 이름과 타입이 `SHOW CREATE TABLE` 과 같은지만 봐 주세요. 다르면
그 표의 `SHOW CREATE TABLE` 과 함께 알려 주시면 맞추겠습니다.
