## 넣어야 하는 코드는 한 곳입니다

`src/LogScope.Core/Io/StepRead.cs` 의 `Mine()` 입니다. 지금은 `null` 을
돌려줘서 아무것도 안 넣습니다.

```csharp
private static StepTable Mine(LogDataset ds)
{
    int ch = ds.FindChannel("STEP_NAME");
    if (ch < 0) return null;
    var names = new string[ds.SampleCount];
    Channel c = ds.Channels[ch];
    for (int i = 0; i < names.Length; i++)
        names[i] = c.TextAt(i);          // 빈 글자 = 단계 밖
    return StepTable.FromLabels(ds, names, "STEP_NAME 글자");
}
```

구간을 직접 적는 길(`FromRanges`)과 시작 시각 목록을 표본 번호로 바꿔 주는
도구(`RangesFromStarts`)도 함께 뒀습니다. 보기 셋이 그 함수 주석에 있습니다.

**그리고 단계가 IO 하나에 들어 있으면 코딩이 아예 필요 없습니다** — 설정
[비교] 탭의 **단계 IO** 칸에 이름만 적으면 됩니다. 값이 바뀌는 자리가 단계
경계가 되고, 글자 IO 면 그 글자가 단계 이름입니다.

## 왜 시각이 아니라 표본 번호로 적나

이 프로그램은 가로축을 바꿔 끼울 수 있습니다 (로그의 시간 → 다른 IO).
단계를 시각으로 적어 두면 **축을 바꾼 날 단계가 엉뚱한 자리를 가리킵니다.**

표본 번호는 축을 바꿔도 그대로입니다. 그 번호의 시각은 `StartTime(ds, i)` 가
그때그때 읽습니다. 시험에도 넣었습니다 — 축을 갈아 끼운 뒤 단계 경계가
그대로인지 봅니다.

## 히트맵 — 칸 하나가 단계 하나

도구 줄의 [가로를 단계로].

고치면서 제일 조심한 자리는 **칸 번호를 셈하는 식**이었습니다. 전에는
이랬습니다.

```csharp
int k = (int)((t - t0) / span);     // 칸은 다 같은 폭, 빈틈 없이 붙어 있다
```

단계는 그 전제를 둘 다 깹니다 — 폭이 다 다르고, **단계 사이에 빈틈이
있습니다** (공정이 멈춘 구간). 그래서 칸의 경계를 `HeatBuckets` 한 곳으로
모으고, 바깥에서는 "이 시각은 몇 번 칸이냐" 를 묻기만 합니다.

빈틈의 표본은 **어느 칸에도 넣지 않습니다.** 옆 칸으로 밀어 넣으면 그
단계에서 나지 않은 차이가 그 단계에 적히는데, 그림은 멀쩡해 보입니다.
시험이 그걸 셉니다 (표본 40 개 중 단계에 든 30 개만 세어졌는지).

`BucketStart` / `BucketEnd` / `BucketText` 도 결과가 답하게 바꿨습니다.
단계로 자르면 `BucketSpan` 이 NaN 이라 "시작 + 번호 x 폭" 이 틀립니다 —
화면 세 곳이 그 식을 쓰고 있었습니다 (가로축 글자 · 칸 설명 · 칸을 눌러
그래프로 넘어가기).

단계가 없는데 켜면 시간으로 그리고 **그렇다고 말해 줍니다.**

## 그래프 — 단계 하나만 골라 보기

도구 줄의 [단계] 묶음: `[◀] [목록] [▶] [시작을 0 으로]`.

고르면 **그 단계만 보이고, 두 로그는 그 단계의 시작끼리 맞춰집니다.**
단계마다 기준 IO·값·"몇 번째 사건"·구간을 손으로 맞출 일이 없습니다 —
단계를 한 번 읽어 두면 밀기 값은 이미 거기 있습니다
(`StepPair.Shift = 이전 시작 − 이후 시작`).

**보여 줄 구간은 두 로그 중 긴 쪽까지 덮습니다** (`StepWindow`). 이전 쪽에만
맞추면 이후 로그에서 그 단계가 더 길 때 뒷부분이 조용히 화면 밖으로
나갑니다 — 그래프만 봐서는 잘린 줄 모릅니다. 그 셈을 화면이 아니라
`LogScope.Logs` 에 둔 것도 그래서입니다 (시험이 닿습니다).

[시작을 0 으로] 는 **눈금 글자만** 바꿉니다. 선을 옮기면 커서 값·차이
음영·이후 로그 밀기가 다 어긋납니다. 날짜 로그의 경과 시간을 그 로그 모양으로
적으면 **1970 년**이 찍히므로, 경과 시간은 늘 시계 모양으로 적습니다
(`TimeText.Elapsed`).

## 짐작하지 않습니다

- 이름이 다른 단계는 **짝짓지 않습니다.** 양쪽에 하나씩 남았어도요. DB 에서
  같은 짐작을 했다가 상관 없는 표 둘이 짝지어진 일이 있습니다 (0.86).
  그래프는 더 나쁩니다 — 틀린 짝으로 맞춰 놓으면 두 로그가 나란히 그려져서
  **맞는 것처럼 보입니다.**
- 같은 이름이 여러 번이면 (가열 → 냉각 → 가열) **n 번째끼리** 맞춥니다.
- 짝 없는 단계는 그래프 목록에서 빠지지만 **몇 개가 빠졌는지 적습니다.**
- 사건 맞추기가 걸려 있으면 단계가 이기고, **비켜섰다고 적습니다.** 조용히
  덮으면 팝업에는 "맞추기 켜짐" 인데 실제로는 안 먹는 상태가 됩니다.
- 단계가 2000 개를 넘으면 자르고 말해 줍니다 (단계가 아닌 IO 를 집은 모양).

## 최적화 한 자리

`HeatmapBuilder` 가 **채널마다** 합계 배열 둘을 새로 만들고 있었습니다.
IO 200 개 x 칸 4000 개면 64 KB 두 개씩 — **25 MB 를 만들고 바로
버리는** 일이라, 세는 동안 GC 가 계속 돕니다. 한 번 만들어 돌려 쓰고
줄마다 지웁니다.

지우는 것을 빼먹으면 앞 IO 의 합계가 다음 IO 에 더해집니다. 숫자가 조금
크게 나오는 모양이라 눈으로는 못 찾습니다 — 주석에 그 말을 적어 뒀습니다.
