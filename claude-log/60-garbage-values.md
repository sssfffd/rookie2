# 60 — 목록 칸 둘 지우기 + 값이 쓰레기로 보이던 까닭 (0.79)

## 주신 말

> 이거 tttm쪽에 표 지워주고 열 지워주고 그리고 내부 값은 쓰레기가
> 들어가는 것 같은데?

DB 분석 화면의 **차이 목록**에서 `표` 칸과 `열` 칸을 빼라는 말로
읽었습니다. ("tttm" 이 다른 것을 가리키는 것이었으면 알려 주세요.)

---

## 1) 칸 둘을 뺐습니다

목록 칸이 일곱에서 **다섯**이 됐습니다.

```
전:  표 · IO명 · 이전 value · 이후 value · v1 · v2 · 열
후:  IO명 · 이전 value · 이후 value · v1 · v2
```

남은 칸을 넓혔습니다 (IO명 150→200, 값 130→170, v1·v2 90→110).

**없어진 것은 아닙니다.** 표 이름과 열 이름은

- 줄에 마우스를 올리면 뜨는 글에 그대로 있고
- `[목록 CSV 저장]` 로 뽑은 CSV 에도 칸으로 남아 있습니다

0.73 에 제가 "표 칸이 없으면 폴더에 DB 가 여럿일 때 어느 DB 값인지 알 수
없다" 고 적어 뒀는데, 그 걱정은 마우스 설명 글이 받아 줍니다.

---

## 2) 값이 쓰레기로 보이던 까닭 — 둘 찾았습니다

### (가) CP949(ANSI) 덤프를 UTF-8 로 읽고 있었습니다 ← 이게 유력합니다

`.sql` 덤프를 읽는 쪽이 이랬습니다.

```csharp
// 전
if (BOM 이 있으면) UTF-8;
return UTF-8;          // ← BOM 이 없으면 무조건
```

한국 윈도우에서 뽑은 덤프나 메모장으로 저장한 `.sql` 은 **CP949(ANSI)**
인 경우가 많습니다. 그걸 UTF-8 로 읽으면 한글이 전부 ``(U+FFFD)로
바뀝니다. **읽기는 성공하고 값만 쓰레기가 됩니다** — 그래서 아무 오류도
안 났습니다.

**로그 CSV 쪽은 처음부터 제대로 가리고 있었습니다** (BOM → ASCII →
올바른 UTF-8 인지 검사 → 아니면 CP949). 같은 일을 하는 코드가 **세 군데**
있었고 그중 덤프 쪽 하나만 틀렸습니다. 또 그 병입니다.

한 곳으로 모았습니다 — `src/LogScope.Core/Text/TextSniff.cs`. 셋이 전부
이걸 봅니다 (로그 CSV · DB 덤프 · config.txt).

### (나) 16진수로 적힌 값을 그대로 보여 주고 있었습니다

mysqldump 는 글자가 아닌 바이트가 섞인 열을 이렇게 적습니다.

```sql
INSERT INTO t VALUES (0xEAB080EC9798, X'EAB080', _binary'abc');
```

`--hex-blob` 을 주면 **글자인 열도 늘** 16진수로 적습니다. 그대로 두면
화면에 `0xEAB080EC9798…` 이 줄줄이 나옵니다 — 쓰레기로 보이는 게
당연합니다.

세 꼴(`0x…` · `X'…'` · `_binary'…'`)을 되돌립니다.

| 바이트가 | 어떻게 |
|---|---|
| 읽을 수 있는 글자 | **그 글자로** 보여 줍니다 |
| 진짜 바이너리 | `0x…` 소문자로 맞춰 둡니다 |
| 16진수가 아님 | **적힌 그대로** 둡니다 (짐작하지 않습니다) |

덤으로 **없는 차이가 하나 사라집니다.** 한쪽 덤프가 `'가열'` 로, 다른
쪽이 `0xEAB080...` 으로 같은 값을 적어 두면 전에는 "달라짐" 이 됐습니다.

진짜 바이너리를 "(바이너리 12 바이트)" 처럼 적지 않은 이유: 그러면 서로
다른 두 바이너리가 **같아 보입니다.** 견주는 도구에서 그건 거짓말입니다.

---

## 3) 시험을 짜다 제 버그를 하나 잡았습니다

`0xZZ` (16진수가 아닌 것) 를 넣었더니 `ZZ` 가 나왔습니다 — 떼어 낸 `0x`
를 돌려주지 않고 있었습니다. "모르면 적힌 그대로" 라고 주석에 써 놓고
코드는 값을 바꾸고 있었습니다. 시험이 없으면 못 봤을 자리입니다.

## 4) CP949 시험이 이 환경에서 건너뛰어집니다

리눅스의 mono 에는 CP949 코드페이지가 없어서, CP949 덤프 시험이
`(건너뜁니다)` 로 지나갑니다. **정작 고친 부분이 검증되지 않습니다.**

그래서 "어느 인코딩으로 읽을지" 라는 **결정만** 따로 시험했습니다
(`글자 — 인코딩 가리기`, 10 개). 글자로 바꾸지 않고 `CodePage` 만 보므로
어디서나 돕니다.

```
CP949 바이트는 UTF-8 로 읽지 않음
UTF-8 바이트는 UTF-8 로 읽음
BOM 셋 (UTF-8 · UTF-16 LE · BE)
ASCII 는 UTF-8
잘린 마지막 글자 때문에 CP949 로 넘어가지 않음
빈 바이트 · null 에서 터지지 않음
```

## 확인한 것 · 못 한 것

- `통과 654 / 실패 0` (638 → 654), 검사기 넷 지적 없음
- **Windows 에서 확인 못 했습니다**: 칸을 뺀 목록 모양, 그리고 **실제
  CP949 덤프가 제대로 읽히는지** (여기서는 CP949 자체가 없습니다)
- **값이 아직 쓰레기로 보이면 알려 주세요.** 위 둘이 아니라면 다음이
  남습니다 — 어느 쪽인지 알면 좁힐 수 있습니다:
  - `.frm` 만 있는 폴더를 읽으셨다면 **값은 원래 안 나옵니다**
    (`.frm` 에는 표의 모양만 있습니다). 칸이 빈 것은 맞는 동작입니다.
  - 덤프가 `latin1` 로 적혀 있는 경우 (CP949 도 UTF-8 도 아님)
  - 값이 길어 칸에서 잘려 보이는 것 (마우스를 올리면 전체가 뜹니다)

  쓰레기로 보이는 값 한 줄만 그대로 붙여 주시면 어느 경우인지 바로
  가릴 수 있습니다.
