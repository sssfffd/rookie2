# 154 — 차이 발생 = IO 수 · 단계로 나눠 생기는 오차 없애기 · 겹친 선 · 그래프에 오차 구간 (1.63)

> 분석 1 차이 발생에 IO 개수 기준으로 들어가면 좋겠네
>
> 그리고 단계별로 쪼개서 보면 오차가 사라지는 부분도 있지만 오히려 발생하는 부분도 있거든? 이런거 없어져야함
> 그리고 지금 그래프가 겹치면 너무 하나만 보이고 너무 안보이는데 알 수 있는 방법이 있을까?
> 그리고 그래프로 보면 오차 발생 지점이 너무 안보이는데 보여지게 가능?

## 1. 차이 발생 = IO 수
메인 분석 1 칸 "차이 발생 N 개" = 허용 안 된 오차가 있는 **IO 수** (JudgeResult.OpenIoCount). 1.62 까지는 오차 구간 수.
단계 오차(길이 · 차례)는 IO 가 아니라 안 셈 — 판정에는 들어가고 맨 위 "공정 단계" 줄에 보임. LLM 글에도 IO 수.

## 2. 단계로 나눠 생기는 오차 없애기
단계마다 시작을 맞추면 단계와 상관없이 움직인 IO 가 어긋나 보여 **없던 오차가 생김** (단계 경계 근처).
→ 단계가 있으면 같은 구간을 **전체 맞춤**(단계를 고르지 않았을 때의 밀기 값 — 시작 시각 · 사건 맞추기)으로도 보고,
**둘 다에서 벗어난 곳만** 오차.

| IO | 단계 맞춤 | 전체 맞춤 | 결과 |
|---|---|---|---|
| 단계와 상관없이 움직임 | 오차 (어긋나 보임) | 같음 | **오차 아님** (1.62 까지 오차) |
| 단계를 따라 움직임 | 같음 | 오차 | 오차 아님 (전과 같음) |
| 진짜 튐 | 오차 | 오차 | 오차 |

같은 튐인지는 **훑은 쪽 로그 자신의 시각**으로 견줌 (이전 로그 시간축으로 옮기면 밀기 값이 달라 같은 튐이 다른 자리).
판정이 그래프에서 고른 단계를 따라 바뀌지 않게 전체 맞춤 밀기 값을 따로 셈 (AppState.BaseShift).
단계 로그는 계산이 약 두 배.

## 3. 겹친 선
이전 · 이후를 같이 그리면 **이전 선을 굵고(×2.8, 최소 3.4 px) 옅게(42 %)** 깔고 이후 선을 가늘게 위에.
겹쳐도 이후 선 양옆으로 이전 선이 비침. 범례도 같은 펜. (예전부터 있는 [파형 분리 보기] 로 위아래로 벌릴 수도 있음)

## 4. 그래프에 오차 구간
Lane · Overlay · 갤러리 · 단계로 나눠 보기 모두, 판정 오차 구간을 레인에 칠함:
허용 안 됨 = 붉게 옅게 + 위에 굵은 띠, 허용됨 = 회색. 짧은 것(0.1 초)도 최소 3 px. 메인 칸에서 허용하면 그래프 색도 바뀜.

## 확인
- Linux: 테스트 1069 통과 (단계 분할 시험: 단계와 상관없는 IO · 단계를 따라가는 IO · 진짜 튐), 실제 csc 7.3 오류 · 경고 0, 검사 통과
- **Windows 에서 못 봄**: 굵은 이전 선 · 오차 구간 칠 모양, 갤러리 · 단계 보기에서 위치
