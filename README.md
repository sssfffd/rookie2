# LogScope — IO 로그 그래프 뷰어

엑셀(.xlsx) / CSV 로 뽑은 IO 로그를 열어 그래프로 보고, 개조 전/후 로그 두 개를
견주는 윈도우 데스크톱 프로그램입니다.

화면은 셋입니다. 위 메뉴에서 오갑니다 (**F1 / F2 / F3**).

- **대시보드** — 켜면 먼저 나옵니다. 이전/이후를 견준 요약 네모 칸과
  차이가 난 IO 목록. 목록에서 IO 를 누르면 그 IO 만 켜진 채로 그래프로 넘어갑니다.
- **그래프** — 시간에 따른 파형. 왼쪽 목록/그룹에서 직접 골라 볼 수도 있습니다.
- **히트맵** — 시간을 1 분씩 (1 초 ~ 1 시간에서 고름) 잘라 "어느 IO 가 어느 시간대에 벌어졌는지" 를
  한눈에. 칸을 누르면 그 IO 와 그 시간대로 그래프가 열립니다. 줄은 **그래프와
  같은 그룹**으로 나뉘고, IO 이름 칸 바로 위의 검색 칸으로 찾습니다 (1.07, 1.10).
  [가로를 단계로] 로 나눈 칸을 누르면 그래프에서 **그 단계를 골라** (히트맵이 견준 것과 같은
  맞춤) 그 단계 구간을 엽니다. 시간 칸은 그 구간을 로그가 있는 곳 안으로 잘라 엽니다 (1.71).

**정상 판정** (1.56, 1.59, 1.64) 은 메인 화면 분석 1 칸에 있습니다. 1.81 부터 칸에는 **점수**로 적습니다:

```
 88.3 / 100   차이 5 / 120 IO
              평균 오차율 11.7 %
```

- **오차율** (IO 하나) = 이전 로그 전체 시간을 **100 칸**으로 나눠, 허용 안 된 판정 오차가 걸친 칸 수 (%). 한쪽 로그에만 있는 IO 는 100 %.
  차이 난 IO 로 센 것은 **적어도 1 %** (1.88 — 오차가 이전 로그 시간 밖에만 있어 0 칸이어도).
- **평균 오차율** = 차이 난 IO 들의 오차율 평균 (차이 없는 IO 는 안 넣음 — 넣으면 IO 가 많을수록 묽어짐).
- **점수** (1.92) = 100 × (1 − 차이 IO 수 / 전체 IO 수) × (1 − 평균 오차율 / 100) — **몇 개가** 와 **얼마나 오래** 를 둘 다.
  차이 난 IO 가 없으면 100. (1.81 ~ 1.91 은 100 − 평균 오차율이라 IO 30 개가 2 % 씩 달라도 98 점이었습니다.)

  | 경우 (전체 IO 120) | 1.91 까지 | 1.92 |
  |---|---|---|
  | IO 5 개: 3 · 8 · 1 · 100 · 6.5 % | 76.3 | 73.1 |
  | IO 1 개: 2 % | 98.0 | 97.2 |
  | IO 30 개: 각 2 % | 98.0 | 73.5 |
- **크기 반영 (1.93)**: 오차 칸마다 **무게** = 1 + 그 오차가 벗어난 % / `score.size` (기본 50, 최대 3 배).
  허용 오차를 살짝 넘은 칸은 1 (예전과 같음), 50 % 벗어나면 2, 100 % 이상이면 3.
  **1.97 부터 "벗어난 %" 는 허용 오차를 넘은 만큼만** 셉니다 — 이전 값 대비 7 % 차이에 허용 5 % 면 2 %,
  절대 허용 (예: ±1) 은 이전 값 대비 % 로 바꿔 둘 중 큰 것을 허용으로 봅니다 (`JudgeScore.OverTolerance`). 이 무게로 센 **크기 반영 오차율**
  (IO 마다 최대 100 %) 의 평균이 점수에 들어갑니다 (칸 옆 "평균 오차율 4 % (크기 반영 9 %)").
- **로그 길이 (1.93)**: 이후 로그가 일찍 끝나거나 (공정 실패로 끊긴 로그) 늦게 시작하거나 더 길면 — 시간 여유보다 클 때 —
  판정에 **"로그 길이"** 오차 한 줄 (메인 칸 "로그 길이" 줄 · 이전 로그 길이의 20 % 넘으면 CRITICAL), 그리고
  점수에 **덮은 비율** 을 곱합니다 (이후 로그가 30 % 만 있으면 × 0.3). 이번만 허용할 수 있습니다.

  **점수 = 100 × (1 − 차이 IO / 전체 IO) × (1 − 크기 반영 평균 오차율 / 100) × 로그 길이 계수**
- **2.08 — 지금 셈 (IO 일치도 합)**:
  **공정 일치율 = 100 × (정상 IO 수 + Σ 차이 IO 일치도) / 전체 IO 수 × 공정 시간 일치율**,
  차이 IO 일치도 = **0.5 × (1 − 크기 반영 오차율 / 100)** (0 ~ 0.5, 한쪽 로그에만 있는 IO 는 0).
  - 정상 IO (차이 없음 · 허용) 는 늘 꽉 차게 셈 → **점수 ≥ 정상 비율 × 공정 시간 일치율** (200 개 중 50 개 정상이면 적어도 25).
  - IO 를 허용하면 그 IO 가 1 이 되어 점수는 늘 오름. IO 하나가 깎는 것은 100 / 전체 IO 점까지 (그래서 `score.iocap` 은 안 씀).
  - 예전 (1.92 ~ 2.07): 100 × (1 − 차이 IO / 전체) × (1 − 오차율) — 두 비율이 곱해져 정상 비율보다 낮게 (10 점 아래) 나왔고,
    1.93 ~ 2.04 는 평균 오차율이라 허용할수록 떨어지기도 했습니다.
  - 화면의 "IO별 평균 오차율" 칸은 그대로 평균 (보는 숫자).
- 1.95: 화면 이름은 **공정 일치율** (점수), **공정 시간 일치율** (로그 길이 계수).
- **판정** = 공정 일치율로: `score.good` (기본 **95**, 1.95) 이상 **정상**, `score.warn` (기본 **80**) 이상 **주의**, 그 아래 **이상**
  (`config.txt` 에서 바꿈 — 뒤집혀 있거나 0 ~ 100 밖이면 기본값). **메인 화면의 최종 판정이 이것**입니다.
- 차이 a / b = 차이 난 IO 수 / 두 로그의 IO 수 (단계 IO 뺌).

PASS · WARNING · CRITICAL 낱말 (허용 안 된 오차가 있는 IO 수로 0 · 10 이하 · 넘음) 은 LLM 입력에 그대로 남습니다. 칸 아래 그룹 줄을 누르면 바로 아래에 IO 들이 펼쳐지고, IO 를 누르면 **작은 창**에 그 IO 의
구간별 오차가 떠서 **[이번만 허용] · [앞으로도 허용]** 을 고릅니다 (1.62). 앞으로도 허용한 것은 설정 창
[허용한 오차] 에서 지웁니다. 허용한 것은 LLM 종합 분석 입력에도 "사용자가 허용한 오차" 로 실립니다
(`LlmRequest.Analysis1Judgement` — 분석기가 이 글을 넣어야 함). 판정 기준은 `docs/ANALYSIS1-JUDGEMENT-GUIDE.md` (입문자용).

그룹 줄 위의 **알림 줄** (1.74):
- **공정 단계 (IO 아님)** — 단계 길이 다름 · 이후에 없음 · 이후에만 있음 · 차례 바뀜. 누르면 단계 오차 창. (예전에는 그룹 줄
  사이에 "공정 단계" 로 끼어 IO 처럼 보였음)
- **파형은 같고 조금 어긋난 IO** — 시간만 조금 밀렸거나 (예: "이후가 8초 늦음"), 높이만 조금 다르거나 ("이후 값이 0.3 높음"),
  둘 다인 IO. 판정은 오차로 셉니다. 누르면 IO 마다 한 줄인 창이 떠서, 골라 **[고른 것 이번만 허용] · [고른 것 앞으로도 허용]**
  으로 한꺼번에 정합니다. 허용하는 것은 그 제안이 붙은 오차 구간만입니다 (같은 IO 의 튐 같은 다른 오차는 그대로).

## 1. 빠르게 쓰기

```
build.bat
out\LogScope.exe
```

(실행 파일 이름은 `config.txt` 의 `name` 을 따라갑니다. 기본이 `LogScope` 입니다.)

`out` 폴더를 통째로 복사하면 다른 PC 에서도 그대로 실행됩니다.
설치 프로그램이 없고, 레지스트리도 건드리지 않습니다.

켜면 **빈 화면**으로 시작합니다. 지난번에 보던 로그를 저절로 열지 않습니다 —
로그가 1000 만 칸까지 가는데, 켤 때마다 몇십 초씩 읽고 앉아 있을 이유가
없습니다. 위 줄의 **[이전 로그 열기] / [이후 로그 열기]** 를 누르거나 파일을
메인 화면의 칸에 **끌어다 놓으면** 됩니다. 명령줄로 넘긴 파일
(`LogScope.exe a.xlsx b.xlsx`) 은 그대로 엽니다.

## 1-1. 화면 구성

화면이 넷입니다. 켜면 **메인**부터 나옵니다.

```
메인 ─── 분석 1  ── 대시보드 / 그래프 / 히트맵   ← 지금까지 만든 것
     ├── 분석 2  ── (아직 없음)
     └── 분석 3  ── (아직 없음)
```

- **메인** (1.94 대시보드 — Grafana · Splunk · WhaTap · 장비 모니터링 참고, 시안 claude-log/189): 위쪽이 **대시보드**,
  그 아래 **분석별 상세요약** (1.97 이름, 예전 분석 칸 — 파일 넣기 · [분석] · 그룹 줄), **종합 Report** (LLM — 2.07, 예전 이름 "종합 분석 결과"), **저장된 분석**.

  ```
  [최종 판정 (!) 주의 ────][공정 일치율 게이지][차이 IO 5/120][IO별 평균 오차율][공정 시간 일치율][분석 2 ✔][분석 3 ○]
  [시간대별 차이  ▁▁▃▇█▇▃▁▁▂▁ … (이전 로그 100 칸)                                       ]
  [               [대기][승온][가열 유지][압력 조정][냉각]   12:00 … 13:02            ]
  [차이 발생 IO List 먼저 발생한 순 [1초▼] ▆ 최대 오차 비율  12개 중 먼저 발생한 8개 ][그룹 상태 ──]
  [ 이상 TEMP_ZONE2  가열부  ███░░ 18 % (41 %)  최대 340 %  12:18 ~ 12:31 ][ 가열부 이상 2 / 18 ]
  분석별 상세요약 — 분석 1 (넓게) · 분석 2 · 분석 3 칸 (1.83 배치 그대로)
  ```

  | 패널 | 무엇 |
  |---|---|
  | 최종 판정 | **결과가 있는 분석의 가중 종합 점수** (2.02 — 예전 "가장 나쁜 판정"). 가중치 `final.weights` 기본 **54 · 30 · 16** (AHP 쌍대비교 — 분석 1 실제 동작이 분석 2 설정의 2 배 · 분석 3 보조의 3 배, 분석 2 가 분석 3 의 2 배 중요 → 고유벡터 0.540 · 0.297 · 0.163, 일관성 비율 0.008). 분석 1 은 공정 일치율, 분석 2 · 3 은 판정 구간의 가운데 (정상 97.5 · 주의 87.5 · 이상 40), 종합 점수를 95 · 80 경계로 판정. **넉아웃** (`final.gate`): 분석 1 이 이상이면 최종 이상, 다른 분석이 이상이면 적어도 주의. 판정 낱말 오른쪽에 종합 점수 (2.04 — 정상 · 주의일 때만, 예: "정상 95.1"), 마우스를 올리면 셈법, 넉아웃이면 아래에 까닭. 돌리지 않은 분석은 빼고 나머지 가중치로 다시 나눔. 아래에 결과가 있는 분석마다 두 줄 (2.00): [색 점] **분석 이름** / 무엇이 있었나 — 분석 1 "차이 IO 5개 — 이상 2 · 주의 3", 분석 2 "바뀐 값 3 개", 분석 3 모듈이 적은 유의점. 줄바꿈 없이 넘치면 … (마우스를 올리면 전체) |
  | 공정 일치율 게이지 | 반원 — 바탕이 이상 · 주의 · 정상 구간 (config.txt 경계, 기본 95 · 80), 그 위에 공정 일치율 % |
  | 차이 IO | a / 전체, 막대, "이상 n · 주의 m" (IO 판정 등급). 칸 이름은 `config.txt` 의 `label.diff` (1.95) |
  | IO별 평균 오차율 | 시간 오차율 평균 · 기준 설명 (칸 안에서 줄바꿈). 2.00 — "크기 반영" 글은 뺌 |
  | 공정 시간 일치율 | 이후 로그가 이전 로그 시간을 덮은 비율, 다르면 그 까닭 |
  | 분석 2 · 3 | 그 분석의 이름 (config.txt) 과 판정 등만 (1.95 — 아래 줄은 뺌). **분석 3 판정 (2.03)**: 모듈이 낱말 · 등급 · 점수를 올리면 그것, 아니면 요약 줄로 — [오류] (빨강) 하나라도 이상, [경고] (노랑) 있으면 주의, 그 밖은 정상. 분석 칸 머리 줄은 그대로 숨기고 판정 등 · 최종 판정 (가중 16) · History 에만 들어감 (예전: 머리 줄을 숨기면서 판정도 늘 "결과 없음") |
  | 시간대별 차이 | **점수와 같은 100 칸**. 막대 높이 = 그 칸에서 차이 난 IO 수, 빨강 = 그 칸에서 이전 값보다 100 % 넘게 벌어짐 (무게 3), 옅은 빨강 바탕 = 이후 로그 없음. 아래에 공정 단계 띠 · 시각. 2.00 — 짧은 단계라 이름 (번호) 이 칸에 안 들어가면 띠 아래 두 줄에 겹치지 않게 내려 적고 선으로 이음 |
  | 차이 발생 IO List | **먼저 발생한 순** 8 개 (2.04) — 오차가 처음 난 시각을 고른 단위 (**0.1초 · 1초 · 10초**, 제목 옆에서 고름 · 저장) 로 묶어 차례, 같은 단위 안이면 최대 오차가 큰 IO 먼저, 한쪽 로그에만 있는 IO 는 맨 앞. 열: 판정 · IO · 그룹 · **최대 오차율 막대** (이전 값 대비 가장 크게 벗어난 %, 100 % 넘으면 꽉 참) · 오차 시간 (허용 오차 밖 시간 비율) · 언제. "N개 중 먼저 발생한 M개" |
  | 그룹 상태 | 그룹마다 차이 IO / 전체 (로그에 있는 IO 만), 색 = 그룹 안 가장 나쁜 IO |

  - 숫자는 모두 **점수와 같은 셈** (`JudgeScore`) 에서 — 패널마다 따로 세지 않습니다 (`Main/MainDashVm.cs`).
  - 게이지 · 막대는 그래프처럼 **직접 그림** (`Main/DashVisuals.cs` — 바깥 라이브러리 없음), 색은 테마 (밝게 / 어둡게).
  - History 를 펼쳐 보는 중에는 대시보드를 비우고 그렇다고 적습니다 (그때의 대시보드는 저장하지 않으므로).
  - 결과가 없는 자리는 모두 **"결과 없음"** (1.95 — 대시보드 숫자 · 판정 · 분석 칸 요약 · History 칸. 예전에 저장된
    "아직 읽지 않았습니다" 같은 글도 History 에서는 "결과 없음" 으로 보입니다). 분석 칸 머리의 판정 배지는 뺐습니다.
  - History 한 줄의 칸 셋은 분석 2 를 가장 넓게 (2.00 — 1.25 : 1.85 : 0.9), 이름 · 판정 · 요약 모두 한 줄
    (2.00 — 글 안에 들어 있던 줄바꿈 때문에 분석 2 칸이 두 줄로 나오던 것. 줄바꿈은 " · ").
  - **칸 셋이 같은 말** (1.92): **정상** · **주의** · **이상** · **결과 없음**. 분석 3 을 못 쓸 때 (LLM 서버에 안 닿음) 도
    맨 위 칸은 "결과 없음" (1.98 — 예전 "못 씀"), 까닭은 아래 분석 칸에 적힙니다.
    1.97: 판정 표시는 글자 (✔ ⚠ ✖ ○ –, 글꼴마다 크기가 제각각) 대신 **같은 크기의 색 원 그림** (`LampIcon` — 체크 · 느낌표 · ×),

  칸으로 두면 "봤는데 아무것도 없다" 와 가릴 수 없습니다).

  **DB 를 한 번도 읽지 않았으면 이 칸은 비어 있습니다** (`?? / 100` 도 아니고
  `PASS` 도 아닙니다). 아직 아무것도 견주지 않은 0 개를 `PASS` 로 적으면
  "통과했다" 는 뜻이 되어 버립니다.
- 위 줄은 **두 칸**입니다.

  ```
  LogScope v0.46  [메인][로그 비교][분석 2][분석 3] │ [대시보드][그래프][히트맵]  [이전 로그 열기][이후 로그 열기][비교 다시 하기]  [설정]
  ```

  **왼쪽은 "어디를 볼까"** — 네 화면 단추가 어느 화면에서든 다 보입니다.
  지금 보고 있는 화면이 눌린 모양으로 표시됩니다. 단추에 적히는 이름은
  **`config.txt` 에 적은 그대로**입니다 (`분석 1` 같은 번호를 앞에 붙이지
  않습니다 — 정한 이름이 어디에 쓰이는지 보여야 합니다).

  **오른쪽은 "무엇을 할까"** — 분석 1 의 안쪽 화면(대시보드·그래프·히트맵)과
  **로그 열기는 분석 1 에서만** 보입니다. 메인 화면에는 이전/이후 칸이 있어
  거기에 끌어다 놓으면 되고, 분석 2·3 에는 아직 아무것도 없습니다.
  **[설정]** 만 어느 화면에서든 보입니다.
- `F1` `F2` `F3` 은 어디에 있든 분석 1 의 대시보드 / 그래프 / 히트맵으로
  데려갑니다. `Esc` 는 메인으로 돌아갑니다 (분석 1 그래프에 커서가 있으면 먼저 커서를 지웁니다, 1.86).

아래 설명은 대부분 **분석 1** 이야기입니다.

### 분석 결과 저장

[지금 결과 저장] 을 누르면 그때의 결과를 한 건 남깁니다. 다음에 분석했을 때
목록에 **지난번과의 차이**가 같이 뜹니다 — `달라진 IO +8개` 처럼요.
달라진 IO 가 늘면 빨강, 줄면 초록입니다.

- **로그 값은 담지 않습니다.** 점수와 몇 개의 수만 남깁니다. 표본이 수백만
  개인데 그대로 복사해 두면 파일이 원본만큼 커지고, 정작 견줄 때 쓰는 것은
  몇 개의 수뿐입니다.
- 파일은 **이름 전체와 경로**를 남깁니다. 발생시간(앞 10 글자)만 남기면 같은
  날 두 번 딴 로그를 나중에 가릴 수가 없습니다.
- 점수는 **분석 1·2·3 셋 다** 남깁니다. 아직 없는 분석은 `??` 입니다.
- 목록은 **세 줄까지만 보이고 그 다음부터는 칸 안에서 굴러갑니다.** 기록이
  쌓여도 메인 화면이 길어지지 않습니다.
- **줄을 누르면** 그때의 기록을 다 펼쳐 보는 창이 뜹니다 (파일 전체 이름과
  경로, 점수 셋, 기준). 그 안의 [현재 분석과 비교] 는 아직 자리만 잡아 둔
  것입니다.
- **어떤 기준으로 나온 수인지**도 같이 남깁니다 (허용 오차 · 절대 오차 ·
  시간 맞추기). 기준이 지금과 다르면 **수를 빼지 않고** `기준 다름`
  이라고 적습니다. 허용 오차를 0.1% 에서 1% 로 넓혀 놓고 "달라진 IO 가
  줄었다" 고 읽으면 안 되기 때문입니다.
- 저장 위치는 설정 파일 옆의 `history` 폴더입니다. 설정이 가는 곳을 그대로
  따라가므로, USB 에 담아 들고 다녀도 기록이 같이 갑니다.
- **기록 하나에 파일 하나**입니다. 한 파일에 몰아 담으면 저장하다 죽었을 때
  지난 기록까지 통째로 날아갑니다. 읽다 깨진 파일을 만나면 그것만 건너뜁니다.
- 이름은 비워 둘 수 있습니다 — 그러면 저장 시각으로 적힙니다.

자세한 이야기는
[claude-log/28-analysis-history.md](claude-log/28-analysis-history.md).

## 4. 어느 것을 빌드하고, 실행 파일은 어디에 생기나

솔루션에 프로젝트가 **둘** 있습니다 (1.23).

| 프로젝트 | 무엇 | 결과물 |
|---|---|---|
| **LogScope** | **프로그램 전부. 이게 시작 프로젝트입니다** | `LogScope.exe` 하나 (out 폴더에서는 `config.txt` 의 `name`) |
| LogScope.Tests | 콘솔 자체 시험 (LogScope 를 참조, 창은 안 띄움) | `LogScope.Tests.exe` |

DLL 이 따로 없습니다 — `out` 폴더에는 exe 하나(와 config.txt 등)만 들어갑니다. 1.22 까지
있던 `LogScope.Core.dll` · `LogScope.Analysis1.dll` · `LogScope.Analysis2.dll` 이 예전 `out`
폴더에 남아 있으면 지워도 됩니다.

### 실행 파일 위치

```
out\LogScope.exe                           <- build.bat 을 돌린 뒤. 이 폴더째 복사하면 됩니다
src\LogScope\bin\Release\LogScope.exe   <- Release 로 빌드한 자리
src\LogScope\bin\Debug\LogScope.exe     <- Visual Studio 에서 F5 로 돌릴 때
```

### Visual Studio 는 성공인데 build.bat 은 실패한다면

`build.bat` 이 두 가지를 더 합니다.

| | VS (F5 · 프로젝트 빌드) | build.bat |
|---|---|---|
| `LogScope.Tests` 를 **빌드** | **안 함** | 함 |
| 테스트를 **돌림** | **안 함** | 함 (실패해도 멈추지 않습니다) |

VS 는 **시작 프로젝트와 그것이 참조하는 것만** 빌드하고, `LogScope`
는 `Tests` 를 참조하지 않습니다. 그래서 `Tests` 가 컴파일되지 않는
상태여도 VS 는 성공으로 보입니다. VS 에서 같이 보려면 **[빌드] →
[솔루션 빌드]** 입니다.

**테스트가 실패해도 `build.bat` 은 멈추지 않습니다** (0.84). exe 는 그대로
만들어지고, 빨간 글로 알리고 끝에서 한 번 더 적습니다. 그러니 `build.bat`
이 **실패로 끝났다면 그건 컴파일 오류**입니다 — 오류 줄에 어느 파일인지
적혀 있습니다.

```
빌드 실패. 오류 줄만 추려 보면:     ← 컴파일 오류. 멈춥니다
[알림] 테스트가 실패했습니다.        ← 알리고 계속합니다
```

테스트를 아예 건너뛰려면 `build.bat Release nt` 입니다.

> **테스트는 누구를 위한 것인가.** 대부분 이 저장소를 고치는 쪽(에이전트)의
> 안전망입니다 — 윈도우와 WPF 를 돌릴 수 없어서, 값 다루는 코드를 고쳤을
> 때 무엇이 깨졌는지 알 수 있는 유일한 수단입니다. 그건 저장소 주인이
> exe 를 받는 것을 막을 이유가 못 됩니다. 그래서 알리기만 합니다.

### Visual Studio 에서 F5 가 엉뚱한 걸 실행한다면

솔루션 탐색기에서 **LogScope 를 오른쪽 클릭 → "시작 프로젝트로 설정"**.
(`LogScope.Tests` 가 시작 프로젝트로 잡혀 있으면 콘솔 창만 뜹니다.)

### build.bat 의 인코딩

`build.bat` 은 **CP949(ANSI / EUC-KR)** 로 저장돼 있고, `chcp` 를 부르지
않습니다.

전에는 반대로 했습니다 — UTF-8 로 저장하고 `chcp 65001` 로 콘솔을 바꿨는데,
그게 바로 한글이 깨지던 원인이었습니다.

- 코드 페이지 65001 에서 옛 콘솔이 한글을 찍으려면 **한글이 들어 있는
  TrueType 글꼴**이 있어야 합니다. 한국어 윈도우의 기본 콘솔 글꼴은
  비트맵 글꼴이라 네모나 깨진 글자가 나옵니다.
- 윈도우 7 은 더 나쁩니다. cmd.exe 는 배치 파일을 **돌리면서 다시 읽는데**,
  65001 에서는 자기 바이트를 잘못 읽어 `goto` 대상을 놓치기도 합니다.

한국어 윈도우 콘솔은 **이미 CP949 로 시작합니다.** 콘솔이 기다리는 바이트를
그대로 써 주고 코드 페이지를 건드리지 않는 것이 실제로 통하는 방법이고,
윈도우 7 · 10 · 11 에서 똑같이 됩니다.

그리고 모든 메시지를 **두 벌** 넣었습니다. 콘솔이 949 가 아니면 한글 대신
ASCII(영어) 쪽을 찍습니다. 그래서 어떤 컴퓨터에서도 깨진 글자가 나올 수
없습니다.

> **파일을 고칠 때는 CP949 / ANSI / EUC-KR 로 저장해 주세요.**
> VS Code 라면 오른쪽 아래 인코딩 단추 → `Save with Encoding` →
> `Korean (EUC-KR)`. BOM 은 붙이지 말고, `chcp` 도 넣지 마세요.
>
> GitHub 웹에서는 이 파일의 한글 줄이 깨져 보입니다 — GitHub 은 UTF-8 로
> 가정하기 때문입니다. 파일 첫머리 설명을 ASCII 로 써 둔 것이 그래서입니다.

#### 중간부터 한글이 사라진다면

코드 페이지는 **프로세스가 아니라 콘솔 창의 성질**입니다. 그래서 자식
프로그램이 코드 페이지를 바꾸면, 그 프로그램이 끝난 뒤에도 **창에 그대로
남습니다.**

`.NET` 의 `Console.OutputEncoding = Encoding.UTF8` 이 바로 그 일을 합니다.
예전 `LogScope.Tests.exe` 가 그 줄을 갖고 있었습니다. 그래서 빌드까지는
한글이 멀쩡하다가, **테스트가 돌아간 순간부터** 그 뒤의 한글만 사라졌습니다
— 한글은 CP949 바이트라 UTF-8 로 읽으면 버려지고, ASCII 인 `:` 나 경로는
남으니까 줄이 "잘린" 것처럼 보입니다.

두 군데를 고쳤습니다.

- `LogScope.Tests.exe` 는 **윈도우에서 콘솔 인코딩을 건드리지 않습니다.**
  한국어 콘솔은 어차피 CP949 라 .NET 이 알아서 맞춰 줍니다. 리눅스(Mono)
  에서만 UTF-8 로 잡습니다 — 거기엔 "콘솔 코드 페이지" 가 없어서
  남의 뒷정리를 망칠 일이 없습니다.
- `build.bat` 은 **자식 프로그램을 부른 뒤마다 코드 페이지를 되돌립니다**
  (`:cp`). 앞으로 어떤 프로그램이 바꿔 놓든 그 뒤 줄은 멀쩡합니다.
  되돌리는 값은 **스크립트를 시작할 때 콘솔이 갖고 있던 그 값**입니다 —
  위에서 하지 말라고 한 `chcp 65001` 과는 반대 방향입니다.

### 어느 판본을 빌드했는지

`build.bat` 은 시작할 때 커밋 해시와 버전을 찍습니다.

```
  MSBuild : C:\Program Files (x86)\...\MSBuild.exe
  로그     : C:\...\build.log
  커밋     : 66b456a1c2d3
  버전     : 0.16
```

"고쳤다는데 오류가 그대로다" 싶을 때 여기를 먼저 보세요. 찍힌 커밋이
고친 커밋보다 앞이면 **받아오지 않은 것**입니다.

```
git log --oneline -1        지금 내 사본의 커밋
git pull                    최신으로 받아오기
```

고친 내용이 커밋 안 된 채로 섞여 있으면 그 사실도 한 줄 적습니다.
git 이 PATH 에 없으면 이 줄들은 그냥 나오지 않습니다.

> **Visual Studio 의 오류 목록은 따로 놉니다.** 오류 목록에는 빌드 결과가
> 아니라 IntelliSense 가 실시간으로 낸 오류도 섞여 나오고, 그건 솔루션
> 전체(빌드하지 않은 프로젝트 포함)를 대상으로 합니다. 그래서 파일을
> 고친 뒤에도 옛 오류가 남아 보일 수 있습니다. **[빌드] → [솔루션
> 다시 빌드]** 로 확인하고, 그래도 남으면 VS 를 닫았다 여세요.

### 빌드가 실패하면

로그를 **두 개** 남깁니다. 쓰임새가 달라서입니다.

| 파일 | 인코딩 | 쓰임새 |
|---|---|---|
| `build.log` | UTF-8 | 전체 기록. 메모장·VS Code 어디서 열어도 한글이 보입니다 |
| `build.err.log` | 콘솔 인코딩 | 오류 줄만. 실패했을 때 창에 그대로 찍는 용도 |

둘로 나눈 이유는, UTF-8 파일을 CP949 콘솔에 그대로 찍으면 **컴파일러가 낸
한글 오류 메시지가 깨지기** 때문입니다. 화면에 찍을 것은 콘솔 인코딩으로,
편집기로 열 것은 UTF-8 로 따로 남깁니다.

창이 닫혀 버려도 `build.log` 를 열어 보면 됩니다. 더블클릭으로 실행한
경우에는 끝나고 창을 붙들어 두므로 오류를 그 자리에서 읽을 수 있습니다.

## 6-1. 손으로 고치는 설정 — `config.txt` 한 파일

**프로그램 이름과 분석 이름은 `config.txt` 한 파일에서 바꿉니다.** 실행 파일
옆(`out\config.txt`)에 있고, 고친 뒤 프로그램만 다시 켜면 됩니다 — 빌드하지
않아도 됩니다.

```
# name      창 제목과 왼쪽 위에 적히는 이름.
# fullname  위 줄의 아랫줄과 창 제목에 들어가는 긴 이름. 길이는 마음대로.
# analysis1 분석 화면의 이름. "이름 | 한 줄 설명" 으로 적습니다.

name = LogScope
fullname = Log 비교 · 분석 도구

analysis1 = 로그 비교 | 이전 Log 파일과 이후 Log 파일을 비교합니다. 대시보드 · 그래프 · 히트맵.
analysis2 = 분석 2 | 아직 정해지지 않았습니다.
analysis3 = 분석 3 | 아직 정해지지 않았습니다.
```

| 열쇠 | 바뀌는 곳 |
|---|---|
| `name` | 창 제목, 왼쪽 위 글자, 오류 창 제목, 설정 파일 안의 `savedBy`, **실행 파일 이름** |
| `fullname` | 왼쪽 위 **이름 바로 아래 줄**(판 번호와 함께) 과 **창 제목**. 300 픽셀을 넘으면 `…` 로 자르고 마우스를 올리면 전체가 나옵니다. 창 제목(작업 표시줄 · Alt+Tab)에는 **안 자른 전체**가 나옵니다. 비워 두면 아래 줄에 판 번호만 남고, 제목에는 `— IO 로그 그래프 뷰어` 가 붙습니다 |
| `analysis1·2·3` | 위 줄의 화면 단추, 메인 화면의 칸 제목과 설명, 분석 2·3 의 빈 화면 글자 |

> **`fullname` 을 적었는데 안 보이면** `out\config.txt` 에 그 줄이 없는
> 것입니다. `build.bat` 은 **이미 있는 `out\config.txt` 를 덮지 않습니다**
> (거기서 고쳐 놓았을 수 있어서). 예전에 만든 `out` 폴더에는 `fullname` 줄이
> 아예 없으니, 그 파일에 한 줄을 더하고 프로그램만 다시 켜면 됩니다.
> 왼쪽 위 이름에 마우스를 올리면 그 안내가 나옵니다.

규칙은 셋입니다.

1. `열쇠 = 값`. 열쇠는 **대소문자를 가리지 않습니다.**
2. 분석 이름의 **세로줄(`|`) 뒤는 설명**입니다 (없어도 됩니다).
3. **없는 줄은 기본값**입니다. 파일을 지워도 프로그램은 그대로 돕니다.

- 저장소 루트에도 같은 파일이 있고 `build.bat` 이 `out` 폴더로 넣어 줍니다.
  **이미 있으면 덮지 않습니다** — 거기서 고쳐 놓았을 수 있어서입니다.
- 모르는 열쇠, 열쇠 없는 줄, 값이 빈 줄은 **건너뜁니다.** 뒤 버전에서 생긴
  열쇠가 적힌 파일로 옛 프로그램을 켜도 터지지 않습니다.
- 메모장이 UTF-8 로 저장하든 ANSI(CP949) 로 저장하든 읽습니다.
- 전에 쓰던 `appname.txt` / `screens.txt` 가 옆에 있고 `config.txt` 가 없으면
  **그 둘을 읽습니다.** 적어 둔 것을 파일 이름이 바뀌었다는 이유로 잃지
  않습니다. (`config.txt` 가 있으면 그쪽이 이깁니다.)

### 실행 파일 이름만 조금 다릅니다

`name` 을 바꾸면 `out\<이름>.exe` 가 됩니다. 다만 그건 **`build.bat` 이
복사할 때 붙이는 이름**이라, 바꾸려면 **다시 빌드**해야 합니다. 빌드 자체는
늘 `LogScope.exe` 를 만듭니다.

MSBuild 가 `config.txt` 를 읽게 하지 않은 이유가 있습니다. 어셈블리 이름은
빌드가 시작되기 <b>전에</b> 정해져 있어야 해서 MSBuild 가 줄을 갈라 읽어야
하는데, 그 한 줄이 잘못되면 **빌드 전체가 멈춥니다.** 복사할 때 붙이면
최악의 경우에도 이름만 틀린 exe 가 나옵니다.

파일 속성 창에 보이는 이름(`AssemblyInfo.cs`)도 `LogScope` 로 고정입니다 —
어트리뷰트 인자는 컴파일할 때 값이 박혀야 해서 실행할 때 읽는 값을 쓸 수
없습니다.

### 따라가지 **않는** 것 — 일부러 그렇게 뒀습니다

| 무엇 | 왜 |
|---|---|
| 설정 파일 `LogScope.settings.json`, `%APPDATA%\LogScope`, `history` 폴더 (`SettingsStore` / `HistoryStore`) | 이름을 바꿨다고 그때까지 쌓인 설정과 저장된 분석을 못 찾으면 안 됩니다 |
| 네임스페이스 · 프로젝트 파일 · `LogScope.sln` · `src/LogScope.*` 폴더 이름 | **코드 안의 이름은 내부 코드명으로 둡니다.** 111 개 파일, 410 군데에 퍼져 있어서 바꾸면 `git blame` 이 그 커밋 하나로 다 덮이고, 이름을 또 바꾸면 또 해야 합니다. 화면에 나오지 않는 이름입니다 |

정말 코드 안의 이름까지 바꿔야 하면 기계적인 치환이라 한 번에 할 수 있습니다
(식별자 치환이라 컴파일러가 빠짐을 잡아 줍니다). 다만 위의 값을 생각하면
권하지 않습니다.

## 6-1-1. 켤 때 읽는 값들은 어디에 저장되나

**두 파일과 한 폴더입니다.** 손으로 고치는 것과 프로그램이 쓰는 것을 나눠
뒀습니다.

| 파일 | 누가 고치나 | 어디 |
|---|---|---|
| **`config.txt`** | **사람만.** 프로그램은 읽기만 합니다 | **실행 파일 옆에만** |
| **`LogScope.settings.json`** | **프로그램이** 씁니다 | 실행 파일 옆, 거기에 못 쓰면 `%APPDATA%\LogScope\settings.json` |
| **`history\*.json`** | 프로그램이 씁니다 (한 건 한 파일, 최대 200) | `settings.json` 이 있는 곳 옆 |

### 무엇이 어디에

**`config.txt`** — 프로그램 이름, 분석 1·2·3 의 이름과 설명,
없습니다 — DB 쪽 값은 전부 화면과 설정 창에서 정합니다.

**`LogScope.settings.json`** — 테마(밝게/어둡게), 허용 오차 기본값(% 와 값),
**IO 별 허용 오차 규칙**(최대 500 개), **그룹**(이름 · 담긴 IO · 펼침 여부),
목록 정렬 기준과 방향, 히트맵을 값으로 볼지 % 로 볼지, 시간 맞추기(기준 IO ·
기준 값 · 몇 번째 변화), 마지막에 쓴 폴더와 파일 경로(6 벌).

**그룹은 고치는 그 자리에서 저장됩니다** (0.61). 만들기 · 이름 바꾸기 ·
차례 바꾸기 · 지우기 · IO 넣고 빼기 · 펼치고 접기 전부입니다. 0.60 까지는
이 저장이 빠져 있어서, 로그를 다시 열거나 창을 닫을 때까지 파일에 안 적혀
있었습니다 — 그 전에 프로그램이 죽으면 묶어 둔 것이 사라졌습니다.

**`history\`** — 저장해 둔 분석 결과. 파일 이름이 저장 시각입니다
(`20260922-143207-881.json`).

### 왜 두 파일인가

**섞으면 사람이 적은 것이 날아갑니다.** 한 파일에 두고 프로그램이 저장하면,
주석과 손으로 맞춘 줄 차례가 저장할 때마다 지워집니다. 그래서 `config.txt` 는
**프로그램이 절대 쓰지 않습니다.** 반대로 테마나 정렬처럼 화면에서 바꾸는 값은
사람이 파일을 열어 고칠 것이 아니니 `settings.json` 에 둡니다.

### 왜 실행 파일 옆인가

`out` 폴더를 USB 나 공유 폴더에 복사해 들고 다닐 때 **설정도 같이
따라갑니다.** 설치가 없는 프로그램이라 이게 맞습니다.

`Program Files` 처럼 쓸 수 없는 자리에 두면 거기에 못 씁니다. 그래서 켤 때
**한 번 써 보고**(`.logscope-write-test`), 안 되면 `%APPDATA%\LogScope\` 로
물러섭니다. `history` 폴더는 `settings.json` 을 따라갑니다 — 설정은 USB 에,
기록은 PC 에 남는 식으로 갈라지면 안 됩니다.

### 두 가지 덧붙임

- **마지막에 연 파일 경로는 저장되지만, 켤 때 열지 않습니다** (0.41). 파일 열기
  창이 지난번 폴더에서 시작하는 데만 씁니다.
- **`version.txt` 는 빌드할 때만 읽습니다.** `build.bat` 이 그 번호를 실행
  파일에 박습니다. 실행 중에는 읽지 않으니, `out` 의 `version.txt` 를 고쳐도
  화면의 판 번호는 바뀌지 않습니다.
- 저장은 **임시 파일에 먼저 쓰고 바꿔치기**합니다. 저장하다 죽어도 반쪽짜리
  설정이 남지 않습니다.

## 6-1-2. 그룹을 파일로 정해 두기 — `groups.txt` (0.66)

그룹(IO 묶음)은 지금까지 `LogScope.settings.json` 에만 있었습니다. 그건
프로그램이 쓰는 파일이라 **빌드 전에 미리 넣어 둘 수가 없었습니다.** 설비마다
IO 를 수십 개씩 묶는데, PC 마다 손으로 다시 하는 것은 할 일이 아닙니다.

저장소 뿌리의 **`groups.txt`** 에 적어 두면 `build.bat` 이 `out` 으로 넣어
줍니다 (`config.txt` 와 같은 규칙입니다 — **이미 있으면 덮지 않습니다**).

```
가열부 = TEMP_1, TEMP_2, HEATER_ON
압력   = PRS_MAIN, PRS_SUB
예비   =
```

- IO 이름은 **로그에 적힌 그대로**. 쉼표 · 세미콜론 · **탭**으로 가릅니다
  (엑셀에서 한 줄 복사해 붙여넣어도 됩니다).
- **같은 이름이 또 나오면 앞의 그룹에 더합니다.** 긴 목록을 여러 줄로 나눠
  적을 때 씁니다.
- 이름만 적고 비워 두면 **빈 그룹**이 만들어집니다 (화면에서 IO 를 끌어다 넣을
  자리).
- `#` 로 시작하는 줄과 빈 줄은 건너뜁니다. 등호가 없는 줄도 건너뜁니다 —
  틀린 줄 하나 때문에 나머지를 못 읽으면 안 됩니다.
- 인코딩은 `config.txt` 와 **같은 길**입니다 (BOM → UTF-8 → CP949).

### 누가 이기나

| 상태 | 그룹의 주인 |
|---|---|
| `groups.txt` 가 **그룹을 하나라도 정함** | **그 파일.** 켤 때 그 그룹으로 맞춥니다 |
| 파일이 없거나 **전부 주석** | `LogScope.settings.json` (화면에서 묶고 저장하는 지금까지의 방식) |

**전부 주석이면 아무것도 하지 않는 것**이 중요합니다. "파일이 있으면 주인" 으로
했다면, 설명만 적힌 빈 틀이 들어 있는 것만으로 그때까지 묶어 둔 그룹이 전부
지워집니다.

파일이 주인일 때 화면에서 그룹을 고치면 **그 자리에서는 바뀌지만 다시 켜면
파일 쪽으로 돌아갑니다.** 그룹 칸에 그렇다고 적힙니다 — 말없이 되돌아가면
고친 사람은 저장이 고장 난 줄 압니다.

### 화면에서 묶은 것을 파일로 옮기기

그래프 화면 왼쪽 아래 **`[groups.txt 글 복사]`** 를 누르면 지금 묶어 둔 그룹이
이 파일 꼴로 클립보드에 담깁니다. 저장소의 `groups.txt` 에 붙여넣고 빌드하면
그 그룹으로 켜집니다.

파일로 바로 저장하지 않는 이유: 저장할 자리는 **저장소의** `groups.txt` 이고
그건 프로그램이 돌고 있는 폴더가 아닙니다. 어디에 쓸지 짐작하면 엉뚱한 자리에
씁니다.

`out\groups.txt` 를 바로 고쳐도 됩니다 — 그때는 **빌드할 필요가 없습니다**
(프로그램만 다시 켜면 됩니다).

## 6-1-3. 단계(Step) — 공정 차례로 보기 (0.91)

로그에 **단계**가 적혀 있으면 (준비 → 가열 → 유지 → 냉각) 시간 대신
**공정 차례**로 볼 수 있습니다.

- **히트맵**: 도구 줄의 [가로를 단계로] — 칸 하나가 단계 하나입니다.
  "가열에서 벌어졌나" 를 시각을 세지 않고 바로 읽습니다.

  **칸마다 그 단계의 밀기 값으로 견줍니다** (0.96). 0.95 까지는 칸만 단계로
  자르고 밀기 값은 하나였습니다 — 그러면 그 하나에 맞는 단계만 제대로
  견주고 **나머지 칸은 어긋난 채 견줍니다**. 공정이 중간에 조금 늘어진
  로그가 늘 그 모양이라(뒤 단계가 더 밀립니다), 차이가 없는데 있다고
  나오거나 있는데 묻혔습니다.

  이 단추를 끈 상태에서는 밀기 값 하나로 전체를 견줍니다. 그래프에서 단계
  하나를 골라 두었으면 **그 단계의 밀기 값**이 전체에 걸리므로 다른 단계는
  어긋나 보일 수 있고, 요약 줄에 그렇다고 적힙니다.

  **대시보드와 점수는 아직 밀기 값 하나로 셉니다** (DiffEngine). 히트맵만
  칸마다 맞춥니다.
- **그래프 — 도구 줄 [정렬] [단계마다] [전체 구간 ▼]** (1.15, 1.16). [단계마다] 는
  켜고 끄는 단추, [전체 구간 ▼] 는 목록(전체 구간 · 1 · 2 · …)입니다.
  - 단추 글자: `src/LogScope/Analysis1/Graph/GraphTexts.cs` 의 `StepCaption` · `StepEach` ·
    `StepWhole` (1.18 부터, 화면 글자 파일 — 아래 "화면 글자" 참고)
  - 단계 이름 앞뒤에 붙는 글: `src/LogScope/Analysis1/LogFile/LogSteps.cs (StepText)`

  ```csharp
  public const string LabelBefore = "";         // 단계 이름 앞 ("S" → S1, S2)
  public const string LabelAfter = "";          // 단계 이름 뒤 ("단계" → 1단계, 2단계)
  ```

  **두 로그 단계 길이가 다를 때** (1.18): 예를 들어 1 단계가 이전 10 초 · 이후 12 초면
  1 단계 칸은 긴 쪽(12 초)만큼 넓고, 0~10 초는 두 선을 다, **10~12 초는 이후 선만**
  그립니다 (이전 선은 제 단계 끝인 10 초에서 끊김). 1.17 까지는 이전 선이 12 초까지
  이어져 그 2 초에 이전 로그의 **2 단계 값**이 그려졌습니다.
  커서를 그 꼬리(10~12 초)에 두면 레인 머리의 값도 짧은 쪽은 `— (단계 끝)` 으로
  적힙니다 (1.19, 글자는 `GraphTexts.NoValue`).

- **그래프 — [단계마다]** (0.93, 0.95 에 확대 추가, 1.14 까지 이름 [단계마다 칸으로]): 가로를 **단계 칸
  여러 개**로 쪼개 나란히 놓습니다. 1 단계 시작으로 맞춘 칸이 맨 왼쪽,
  2 단계 시작으로 맞춘 칸이 그 다음 … 이런 식입니다. 칸마다 **그 단계의
  밀기 값**으로 맞추므로, 공정이 중간에 늘어진 로그도 단계마다 맞아 보입니다.

  ```
  ┌ 준비 ┐ ┌─── 가열 ─────┐ ┌ 유지 ┐ ┌─── 냉각 ──┐
  └───────┘ └───────────────┘ └───────┘ └───────────┘
  ```

  단계 이름은 **이름 그대로**입니다 (1.13, 전에는 `1. 준비` 처럼 순번이 붙었음).
  같은 이름이 두 번째부터는 `가열 (2)` 처럼 몇 번째인지 붙어서 목록에서 가릴 수
  있습니다.

  칸 폭은 **단계 길이에 비례**합니다 (똑같이 나누면 같은 기울기가 칸마다 다른
  기울기로 보입니다). 너무 짧은 단계는 최소 폭을 받고, 그만큼은 넉넉한
  칸에서 떼어 옵니다. **칸 사이는 띄워 둡니다** — 그 자리는 시간이 건너뛴
  자리인데, 금 한 줄로만 가르면 두 칸의 선이 이어진 하나로 읽힙니다.
  세로 눈금은 레인에 하나뿐이라 **칸끼리 높이를 그대로 견줄 수 있습니다.**

  **확대도 됩니다.**

  | 손놀림 | 무엇이 |
  |---|---|
  | 휠 (칸 위에서) | **그 칸만** 확대·축소 (1.83 — 그래프를 먼저 눌러 고른 뒤. 안 골랐으면 화면 굴리기) |
  | 휠 (칸 밖에서) | **모든 칸을 같이** (틈·눈금 자리에서 굴렸을 때) |
  | Ctrl + 휠 (1.87) | **모든 칸을 같이** (어느 칸 위에서든) |
  | 끌기 (칸 위에서) | 그 칸만 좌우로 |
  | 오른쪽 끌기 | 네모가 한 칸 안에 있으면 그 칸을 그 구간으로 |
  | `+` `-` · `←` `→` | **모든 칸을 같이** (단계마다 같은 자리를 보게) |
  | `Home` | 칸들을 단계 전체로 되돌리기 |

  **칸 하나만 크게 볼 수도 있습니다** (1.01). 이 모드에서 옆 목록에서 한
  단계를 고르면 **그 칸 하나가 화면 폭을 다 씁니다** — 칸이 여섯이면 한 칸이
  육분의 일이라 들여다볼 수가 없습니다. 하나만 볼 때도 칸 모드 그대로입니다
  (그 단계의 밀기 값, 단계 이름 눈금, 칸 안에서 확대). `[전체 구간]` 으로
  돌리면 모든 칸이 돌아옵니다.

  칸은 **그 단계 밖으로는 안 나갑니다.** 나가면 그 칸에 옆 단계의 그림이
  들어오는데, 그러면 "이 칸 = 이 단계" 가 깨집니다.

  **커서를 찍으면 아래 띠에 "그 단계 시작에서 몇 초" 가 같이 적힙니다**
  (`09:12:42  (가열 시작 +12.300)`). 칸으로 나눠 보면 가로가 시각이 아니라
  공정 차례라서, 시각만 적어 두면 그 자리가 어느 단계의 어디인지 다시 세어
  봐야 합니다.

  **그래프만** 그렇게 그립니다. 견준 수(대시보드 · 히트맵 · 점수)는 밀기 값
  하나로 센 것입니다 (1.15 부터 그래프 아래 줄에는 이 말을 적지 않습니다).

- **한 단계만 보기** (1.16): 두 길이 있습니다.
  - 목록 [전체 구간 ▼] 에서 단계를 고르기 — 나눠 보지 않을 때는 그 단계 구간만,
    [단계마다] 를 켠 채면 그 칸 하나만.
  - [단계마다] 를 켠 채 **그림 위 칸 머리(단계 이름)를 누르기** — 그 칸 하나만.
    한 번 더 누르면(머리에 `◀ 전체` 가 붙어 있음) 모든 칸으로 돌아갑니다. 그림을
    누르는 것(커서 찍기)과 자리가 따로라 섞이지 않습니다.
- 단계로 나눠 볼 때 **단계 이름은 그림 위** 칸 머리 줄에, 그 칸이 보여 주는 시간
  구간은 아래 눈금 줄에 적힙니다 (1.16, 전에는 이름도 아래).
- [◀][▶] · [눈금 0 = 단계 시작] · [?] 는 1.15 에 뺀 그대로입니다.

  **칸마다 무엇을 맞추나** — 칸 N 에서는 **이전 로그는 제자리**, 이후 로그를
  `이전의 N 단계 시작 − 이후의 N 단계 시작` 만큼 밀어서 **두 로그의 N 단계 시작이
  칸 왼쪽 끝에서 겹칩니다.** 칸마다 따로 밀므로 1 단계 칸 · 2 단계 칸이 저마다
  맞춰집니다. 단계 **길이**는 늘리거나 줄이지 않습니다 — 한쪽 단계가 더 길면
  끝은 어긋나 보이고, 칸은 더 긴 쪽 끝까지 그립니다.

전에는 단계를 보려면 **단계마다 손으로 맞춰야** 했습니다 — 기준 IO 를
고르고, 값을 고르고, "몇 번째 사건" 을 세어 넣고, 구간을 끌어다 맞추고.
단계가 여섯이면 그걸 여섯 번 합니다. 단계를 한 번 읽어 두면 그 셈은 이미
다 되어 있습니다.

### 단계를 넣는 법 — 둘

**1. 단계를 담은 IO 가 로그 안에 있으면 (코딩할 것 없음)**

설정 창 [비교] 탭의 **단계 IO** 칸에 그 IO 이름을 적습니다. 그 IO 의 값이
바뀌는 자리가 단계 경계가 됩니다. 글자 IO 면 그 글자가 단계 이름이고
(`"가열"`), 숫자면 값이 그대로 이름입니다 (`"3"`). 값이 빈 구간은
**단계 밖**입니다 (기록 전이나 공정이 멈춘 구간).

적고 **설정을 닫으면 바로 들어갑니다** (0.99). 이미 열어 둔 로그를 한 번
훑어 단계를 다시 찾습니다 — 파일을 다시 읽지 않습니다. 이름을 한 번에 맞게
적는 일이 드물어서(대소문자·밑줄·공백), 그때마다 10M 칸을 다시 읽게 두면
못 씁니다. 못 찾으면 그 이유를 띄웁니다.

**단계 IO 자신은 차이로 세지 않습니다 (1.66).** 단계 IO 는 "지금 몇 단계인지"
를 알려 주는 기준이라, 그 값이 이전과 다르다는 것은 단계 길이 · 차례 검사
(맨 위 "공정 단계" 줄) 가 이미 잡습니다. 그래서 대시보드 목록 · 히트맵 줄 ·
그래프 차이 칠하기 · 정상 판정 어디에도 그 IO 의 차이를 따로 내지 않습니다
(그래프에는 선으로 그대로 보입니다).

**2. 로그 모양이 달라 IO 하나로 안 되면 (여기만 코딩)**

`src/LogScope/Analysis1/LogFile/LogSteps.cs (StepRead)` 의 `Mine()` 한 곳입니다. 지금은 `null` 을
돌려줘서 아무것도 안 넣습니다.

```csharp
private static StepTable Mine(LogDataset ds)
{
    // 가) 표본마다 단계 이름이 있는 경우
    int ch = ds.FindChannel("STEP_NAME");
    if (ch < 0) return null;
    var names = new string[ds.SampleCount];
    Channel c = ds.Channels[ch];
    for (int i = 0; i < names.Length; i++)
        names[i] = c.TextAt(i);          // 빈 글자 = 단계 밖
    return StepTable.FromLabels(ds, names, "STEP_NAME 글자");
}
```

구간을 직접 적어 넣는 길도 있습니다 — `StepTable.FromRanges(ds, list, "내 파서")`
에 `new LogStep("가열", 1200, 4999)` 처럼 **표본 번호**로 넣습니다. 시각만
알고 있으면 `StepRead.RangesFromStarts(ds, 이름들, 시작시각들)` 이 표본
번호로 바꿔 줍니다 (시간 격자가 고르지 않아도 맞습니다).

어느 길로 넣어도 **차례 세우기 · 겹침 밀기 · 상한 자르기**는 `StepTable` 이
똑같이 해 줍니다. 넣는 길마다 따로 재면 어느 길로 넣었는지에 따라 단계가
달라지는데, 그건 화면만 봐서는 알 수가 없습니다.

### 왜 시각이 아니라 표본 번호인가

시각은 맞추기·축 바꾸기 같은 기능이 건드릴 수 있는 값입니다. 단계를 시각으로
적어 두면 그런 기능이 들어온 날 **단계가 엉뚱한 자리를 가리킵니다.** 표본
번호는 그런 일이 없고, 그 번호의 시각은 쓸 때마다 읽습니다.

### 안 하는 것 — 짐작

- 이름이 다른 단계는 **짝짓지 않습니다.** 양쪽에 하나씩 남았어도 붙이지
  않습니다 (DB 에서 같은 짐작을 했다가 상관 없는 표 둘이 짝지어진 일이
  있습니다 — 0.86). 그래프는 더 나쁩니다: 틀린 짝으로 맞춰 놓으면 두 로그가
  나란히 그려져서 **맞는 것처럼 보입니다.**
- 같은 이름이 여러 번 나오면 (가열 → 냉각 → 가열) **n 번째끼리** 맞춥니다.
- 짝이 없는 단계도 **목록에는 남습니다** (그래프의 고르는 목록에서는 빠지고,
  몇 개가 빠졌는지 아래 줄에 적힙니다). 조용히 사라지면 "이전에는 있던
  단계가 왜 없지" 를 알 수 없습니다.
- 단계가 없는데 [가로를 단계로] 를 켜면 시간으로 그리고 **그렇다고 말해
  줍니다.** 조용히 돌아가면 가로가 단계인 줄 알고 읽습니다.
- 단계가 2000 개를 넘으면 자르고 말해 줍니다 — 단계가 아닌 IO (매 표본
  흔들리는 아날로그)를 단계로 집었을 때 나는 모양입니다.

### 밀기 값은 누가 이기나

**단계 > 사건 맞추기 > 시작 시각 자동 맞춤** 입니다. 단계를 고른 사람은 그
단계를 겹쳐 보려고 고른 것인데, 다른 맞추기가 그 위에 또 걸리면 단계 시작이
어긋납니다. 사건 맞추기가 걸려 있으면 그래프 아래 줄에 **비켜섰다고
적힙니다** ([전체 구간] 으로 돌리면 돌아옵니다).

손으로 넣은 밀기 값(설정의 `손으로 밀기`)은 어느 쪽이든 그 위에 더해지는
미세 조정이라 그대로 둡니다.

### 고칠 때 여는 파일

| 무엇 | 어디 |
|---|---|

## 6-2. 분석 2 — DB 분석

### 화면에 보이는 글자를 바꿀 때

글자는 **쓰는 쪽과 견주는 쪽이 있는지**로 나뉩니다.

| 글자 | 어디서 바꾸나 | 다시 빌드 |
|---|---|---|
| **DB 목록 칸 머리글 (`IO명` · `이전 value` …)** | **`src/LogScope/Analysis2/DbNames.cs` 한 줄** | 예 |

아래 셋은 **설정 파일로 바꾸지 않습니다.** 화면에 보이기도 하지만
**코드가 견주는 값**이라, 설정으로 바꾸게 하면 그 순간 견주기가 깨집니다.
XAML 쪽도 `{x:Static ...}` 으로 그 상수를 읽으므로 글자가 한 곳에만 있고,
이름을 잘못 적으면 `check_sources.py` 가 잡습니다.

### `.sql` 을 직접 읽게 하려면 (1.82)

`src/LogScope/Analysis2/SqlUserReader.cs` 의 `SqlUserReader.Read(path, into, maxRows)` 한 곳입니다.
.sql 파일을 읽을 때마다 **이것이 먼저** 불리고, `true` 를 돌려주면 그 결과를, `false` 면 내장 읽기
(`SqlDumpReader` — mysqldump 꼴) 를 씁니다. 지금은 `false` 라 예전과 같습니다. 표 만드는 예시가 파일 안에
주석으로 있습니다 (`DbTable` · `DbColumn` · `DbRow`). 거기서 예외가 나면 그 파일만 "SqlUserReader 오류" 로 적고 넘어갑니다.
이 파일은 사용자 몫이라 이후 버전에서 고치지 않습니다.

### `.csv` 를 어떻게 읽나 — 3 번 열쇠 · 4 번 값 (0.87)

쓰는 `.csv` 가 이렇게 생겼습니다.

```
1,2,3,4,5,6         ← 첫 줄은 열 이름
…,…,IO 이름,값,…,…   ← 둘째 줄부터 자료
```

**3 번 열로 행을 짝짓고, 4 번 값이 달라진 것을 찾습니다.** 나머지 열은
읽지 않고, **안 봤다는 것을 화면에 적습니다.**

```
old_2026-03-14.csv — 6 개 열 중 3 번(io)으로 행을 짝짓고 4 번(value) 값을
견줍니다. 안 본 열: no · addr · unit · note
```

자리를 바꾸려면 `src/LogScope/Analysis2/DbNames.cs` 의 **두 줄**입니다.

```csharp
public const int CsvKeyColumn = 3;
public const int CsvValueColumn = 4;
```

> `.csv` 값은 **적힌 글자 그대로** 읽습니다. 가려 읽으면 `ON` 과 `1` 이
> 둘 다 참이 되어 **서로 다른 값이 같아 보입니다** (0.87 에서 고쳤습니다).

### 어디를 읽나 — 파일 하나씩 (1.90)

메인 화면의 로그 칸과 **같은 모양**인 칸 둘이 있습니다. 칸에 **끌어다 놓거나**, **타 넣거나**,
`[파일]` 로 고르면 됩니다. **한 칸 = 파일 하나**입니다 (놓은 칸만 바뀝니다). 칸 아래 작은 글이 그 자리가
있는지 말해 줍니다. 한 번 정한 자리는 `settings.json` 에 저장되어 다음에 켤 때도 그대로입니다.

| 넣는 것 | 읽는 것 | 읽는 곳 |
|---|---|---|
| **`.sql`** (mysqldump 등) | 모양 + 값 | `SqlUserReader.Read` (직접 만드는 자리) → `false` 면 내장 `SqlDumpReader` |
| **`.csv`** (그 밖의 파일도 .csv 로) | 3 번 열 (IO 이름) · 4 번 열 (값) | `CsvTableReader` (`DbNames.CsvKeyColumn` · `CsvValueColumn`) |
| 폴더 · `.frm` · `.ibd` | **읽지 않습니다** — 그렇다고 화면에 적습니다 | — |

`.sql` 에서 표가 하나도 안 나오면 그것도 적습니다 (조용히 "차이 없음" 으로 보이지 않게).

> **1.90 에 뺀 것** (사용자 결정): 폴더 통째 읽기 (하위 폴더 · 표 이름 앞 폴더 이름), MySQL 내부 파일
> 읽기 (`.frm` 표 모양 · `.ibd` 안내), 바깥 프로그램 실행 (설정 창 [DB 도구] — `mysqldump` · `ibd2sdi`),
> `[SQL 문 출력]` (맞추는 ALTER · UPDATE · INSERT 글). 바깥 프로그램을 띄우거나 DB 서버에 접속하는 길이
> 이제 프로그램 안에 없습니다. 옛 설정 파일에 그 경로가 남아 있어도 읽지 않습니다.

### 무엇을 알려 주나 — 세 단계

```
1. 표    한쪽에만 있는 표
2. 열    추가·삭제·타입/NULL/기본값/자리 변경, 이름 변경 짐작
3. 행    키 기준 추가·삭제·값 변경 (바뀐 열만 집어냅니다)
```

**이름 변경은 짐작으로만 적습니다.** 사라진 열과 새로 생긴 열이 모양과 자리가
같고 그런 짝이 하나뿐일 때만 `이름이 "x" 로 바뀐 듯` 이라고 덧붙입니다.
단정하면 그걸 믿고 `ALTER ... CHANGE` 를 돌리는데, 틀렸으면 **값이
사라집니다.**

**기본 키가 없는 표**(특히 `.csv`)는 어느 행이 어느 행이 되었는지 알 방법이
없습니다. "모든 열이 같은 행끼리" 묶으므로 값이 하나 바뀐 행은
`없어진 행 1 + 생긴 행 1` 로 보입니다. 화면에 그 이유를 적습니다.

값은 **글자 그대로** 견줍니다 — `1.10` 과 `1.1` 은 DB 에서 다르게 적힌
것입니다. 다만 이스케이프(`\'` → `'`)는 되돌립니다. 같은 값을 다르게 적어 둔
두 덤프를 차이로 세면 안 됩니다.

### 차이 목록 — 칸마다 값 하나 (0.55)

차이는 **목록**으로 나옵니다. 글 한 덩이로 적던 것을 칸으로 쪼갰습니다.

| 표 | 갈래 | 구분 | 행 | 열 | 이전 | 이후 | 설명 |
|---|---|---|---|---|---|---|---|
| mydb.users | 열 | 생김 | | email | | VARCHAR(200) NULL | 새로 생김 |
| mydb.users | 행 | 달라짐 | id=7 | name | 김 | 김철수 | |
| mydb.users | 행 | 달라짐 | id=7 | age | 30 | 31 | |
| mydb.users | 행 | 없어짐 | id=3 | name | 이 | | |
| other.log | 알림 | | | | | | 기본 키가 없어 모든 열이 같은 행끼리만… |

- **값이 바뀐 행은 바뀐 열마다 한 줄**입니다. 한 행을 한 줄로 묶으면 "이전"
  칸에 여러 값이 들어가 다시 글이 되고, 그러면 **같은 열이 몇 군데서
  바뀌었는지 셀 수가 없습니다.**
- **생기거나 없어진 행도 열마다 한 줄**입니다. 없는 쪽 칸은 **빈 칸**입니다 —
  `NULL` 과 다릅니다. NULL 은 값이 NULL 인 것이고, 빈 칸은 그 행이 없는
  것입니다.
- **표 자체가 한쪽에만 있을 때는 행을 펼치지 않습니다.** 행 1 만 개가 전부
  "생김" 으로 깔려도 아는 것은 "이 표가 새것" 하나뿐입니다. 열 모양만 적고
  행 수는 알림에 적습니다.
- **`[전체 표]` / `[고른 표만]`** 으로 범위를 고릅니다. 기본은 전체입니다.
- 칸이 좁아 잘린 값은 **줄을 마우스로 짚으면** 다 나옵니다.
- 상한은 **표 하나 5,000 줄 · 목록 5 만 줄**입니다. 닿으면 `알림` 줄로
  그렇다고 적습니다 — 조용히 끊으면 "차이가 이것뿐" 으로 읽힙니다.

**[.CSV로 저장]** 은 보이는 목록을 칸 그대로 내보냅니다. 거르고 정렬하는
일은 엑셀이 이 화면보다 훨씬 잘합니다. 한글이 깨지지 않게 BOM 을 붙입니다.
**값은 손대지 않고 그대로 나갑니다** — 그래서 `=` 로 시작하는 값은 엑셀이
수식으로 읽을 수 있습니다. 앞에 따옴표를 붙여 막을 수도 있지만 그러면 `-5`
같은 흔한 값까지 글자로 바뀌어, 차이를 보려고 뽑은 목록의 값이 원래와
달라집니다. 바꾸는 쪽이 더 나쁩니다.

### 라이브러리

**더한 것이 없습니다.** `.sql` 은 글자를 직접 훑고, `.csv` 는 로그를 읽는
`CsvReader` 를 그대로 씁니다. 바깥 프로그램도 띄우지 않습니다 (1.90).

**덤프의 SQL 을 실행하지 않습니다.** 글자를 읽어 표로 만들 뿐이고, 모르는
문장은 건너뜁니다.

## 7. 허용 오차 (차이로 셀지 말지의 기준)

**그 순간의 값끼리 견줍니다.**

```
오차(%) = |이후 − 이전| / |이전| x 100
```

설정에 적는 퍼센트가 **바로 이 값**입니다. 화면에 적히는 퍼센트도 같은
값입니다. 그래서 "허용 오차 1%" 와 "이 칸은 3%" 를 눈으로 바로 견줄 수
있습니다. 기본값은 어느 채널이든 같은 잣대입니다 — 채널마다 기준을 저절로
만들지 않습니다. 다만 **IO 별로 따로 걸어 둘 수는 있습니다** (아래).

| 이전 | 이후 | 오차 |
|---|---|---|
| 100 | 101 | 1% |
| 6466 | 6467 | 0.015% |
| 5000 | 5050 | 1% |
| 5 | 5.05 | 1% |
| 200 | 100 | 50% |
| 0 | 1 | 100% |
| 0 | 0 | 0% |

마지막 두 줄이 특별합니다. **이전 값이 0 이면 나눌 수가 없습니다.** 0 에서
벗어난 것은 값이 통째로 달라진 것이므로 **100%** 로 봅니다. 상태(문자열)
채널도 이름이 다르면 100% 이고, 이쪽은 허용 오차와 상관없이 늘 차이입니다.

### 0 언저리가 걱정되면 — 절대 오차

0 근처에서는 작은 흔들림도 퍼센트가 크게 나옵니다 (0.001 → 0.002 는 100%).
그럴 때 **절대 오차**를 함께 걸어 두세요. 그 값 이하로 벌어진 것은 퍼센트와
상관없이 같은 것으로 봅니다.

```
차이로 셈  ⟺  |이후 − 이전| > 절대 오차   그리고   오차(%) > 허용 오차(%)
```

### IO 별로 따로 걸기

기본값 하나로 다 보는 것이 맞지 않을 때가 있습니다. 온도처럼 원래 조금씩
흔들리는 값과, 밸브 열림처럼 조금도 달라지면 안 되는 값에 같은 잣대를 대면
**한쪽은 늘 빨갛고 다른 쪽은 놓칩니다.**

**[설정] → [비교] 탭 → IO 별 허용 오차** 에서 IO 마다 따로 걸 수 있습니다. IO 이름 칸은 **펼쳐서 고르거나 직접
적습니다** (1.84 — 그 전에는 공용 콤보 모양에 글 칸이 없어 이름이 안 보였습니다).

```
IO 이름                퍼센트 (%)    값 (절대)
흔들리는 온도 TT-01    20
밸브 OPEN                            0
압력 PT-01             5             0.1
```

- **두 칸 다 쓸 수 있습니다.** 퍼센트만, 절대값만, 혹은 둘 다.
- **비워 두면 그 자리는 기본값**입니다. 위 예에서 온도는 퍼센트만 20% 로
  바뀌고 절대 오차는 기본값 그대로입니다.
- **0 과 빈 칸은 다릅니다.** 절대값 0 은 "절대 오차를 끈다", 퍼센트 0 은
  "조금이라도 벌어지면 차이" 라는 뜻입니다. 둘 다 실제로 쓰는 값이라
  "안 정함" 을 0 으로 적을 수 없습니다.
- IO 이름은 **느슨하게 맞춥니다** — 띄어쓰기나 `_ - .` 가 달라도 같은 IO 로
  봅니다. 두 로그에서 같은 IO 가 `밸브_OPEN` 과 `밸브 OPEN` 으로 적히는 일이
  흔하고, 비교 자체가 이미 그 규칙으로 짝을 짓기 때문입니다.
- 로그를 열어 두면 **이름을 목록에서 고를 수 있고**, 안 열었으면 손으로 적어
  미리 걸어 둘 수도 있습니다.
- 대시보드 · 그래프 · 히트맵이 **모두 같은 표**를 씁니다.
- 저장해 둔 분석과 견줄 때, IO 별 규칙이 다르면 **"기준이 다르다"** 로 봅니다
  — 기본값만 같다고 나란히 놓으면 거짓말이 됩니다.

바꾼 뒤에는 위 메뉴의 **[비교 다시 하기]** 를 눌러야 반영됩니다.

#### 파일로 정해 두기 — `tolerances.txt` (1.86)

그룹의 `groups.txt` 와 **같은 방식**입니다. 저장소 뿌리의 **`tolerances.txt`** 에 적어 두면 `build.bat` 이
`out` 으로 넣어 주고 (이미 있으면 덮지 않음), 프로그램은 실행 파일 옆의 것을 읽습니다.

```
# IO이름 = 퍼센트, 절대값      (빈 칸은 기본값)
TT-01  = 20          <- 퍼센트만
VALVE  = , 0         <- 절대값만
PT-01  = 5, 0.1      <- 둘 다
```

| 경우 | 누가 정하나 |
|---|---|
| `tolerances.txt` 가 **규칙을 하나라도 정함** | **그 파일.** 켤 때 그 규칙으로 맞춥니다. 설정 창에서 고친 것은 지금은 먹지만 다시 켜면 되돌아갑니다 (설정 창에 그렇다고 적힘) |
| 전부 주석 (저장소의 빈 틀) | 지금까지처럼 설정 창 → `LogScope.settings.json` |

- 퍼센트 0 ~ 100 (끝에 `%` 를 붙여도 됨), 절대값 0 이상. 숫자가 아니거나 범위 밖인 칸은 빈 칸 (기본값).
- 이름은 느슨하게 맞추고, 같은 IO 가 또 나오면 뒤의 줄이 이깁니다 (설정 창과 같음).
- 설정 창 **`[tolerances.txt 글 복사]`** — 지금 건 규칙을 이 꼴로 클립보드에 담습니다. 저장소의 파일에
  붙여넣고 빌드하면 됩니다. `out\tolerances.txt` 를 바로 고쳐도 됩니다 (그때는 빌드할 필요 없음).

봐준 IO 도 **오차 퍼센트는 그대로 적힙니다.** 잣대를 바꾼 것이지 값이 바뀐
것이 아니라서, 화면에 10% 로 적히고도 "차이 아님" 인 것이 맞습니다.

### 화면에서 보는 곳

세 화면이 전부 같은 함수(`ToleranceRule`)를 쓰고, **같은 잣대의 퍼센트**를
보여 줍니다.

| 화면 | 어디에 |
|---|---|
| 대시보드 | 목록 맨 앞 **[최대 오차 %]** 칸 — 제목을 누르면 그 기준으로 정렬 |
| 그래프 | 도구 줄의 허용 오차 옆 글 (마우스를 올리면 자세히) |
| 히트맵 | 칸에 적히는 퍼센트, 마우스를 올리면 아래 띠에 허용 오차와 나란히 |

"왜 이게 차이로 떴지" 는 그 IO 의 최대 오차 %와 허용 오차를 견주면 바로
답이 됩니다.

### 히트맵 칸 폭 (1.89)

도구 줄의 **칸 폭**: `자동 (시각 1분 · 숫자 60칸)` · **`0.1초`** (2.04) · **`1초`** · **`5초`** · `10초` · `1분` · `5분` · `10분` · `30분` · `1시간`.

- **고르면 바로 다시 셉니다** (1.89 — 전에는 다시 계산 전까지 옛 폭의 칸이 남아, 위에 고른 폭과 보이는 칸이 달랐습니다).
- 칸 경계는 **정각** (00 초 · 00 분 — 폭의 배수) 에 맞춥니다. 첫 칸은 겹치는 구간 시작부터 다음 정각까지, 끝 칸은
  마지막 정각부터 끝까지라 둘은 짧을 수 있습니다.
  ```
  1 분:  |27.4초~04:00| 04:00~05:00 | 05:00~06:00 |06:00~10초|
  ```
- 칸이 너무 많으면 폭을 두 배씩 넓히고 아래 줄 칸 폭 글에 "(칸이 너무 많아 폭을 넓혔습니다)" 라고 적습니다. 상한은
  IO 수에 따라 4000 ~ 20000 칸 (IO 60 개면 20000 칸 — 1 초 칸으로 5 시간 반).
- **칸이 기록 간격보다 좁을 때 (2.06)** — 0.1 초 칸에 0.1 초 기록이면 시각이 조금씩 흔들려 (…0.099 · …0.201) 이전 표본이
  하나도 안 들어간 칸이 생기고, 예전에는 그 칸이 "기록 없음" 이었습니다. 이제 두 로그가 다 그 시각을 덮으면 칸 가운데 시각의 값
  (아날로그는 이웃 표본 사이 보간, 디지털 · 상태는 직전 값) 으로 견줍니다. 한쪽 로그 밖은 그대로 "이전 없음 · 이후 없음".
- 히트맵 칸은 **점수 · 대시보드의 100 칸과 상관없습니다** (그 100 칸은 공정 일치율 셈에만 씀).
- 시간 열이 **숫자** 면 (예: 0, 0.1, 0.2 …) 그 숫자를 **초**로 보고 칸 폭을 고를 수 있습니다 (1.99 — 1.89 ~ 1.98 에는
  60 칸에 고정되고 고르기가 꺼져 있었습니다). 시간 열 머리에 단위가 있으면 바꿔 셉니다 (`ms` → 1000, `min` → 1/60, `h`).
  `자동` 은 숫자 축이면 전체를 60 칸으로.
- 시간 열이 없는 로그 (표본 번호) 만 60 칸 고정이고 칸 폭 고르기가 꺼집니다. 가로를 단계로 볼 때도 꺼집니다.

### 초기 오차 무시 (1.99)

설정 → 비교 탭: **초기 오차 무시** `[v] 처음 [ 10 ] 초 동안 오차 무시`.

- 켜면 **이전 로그 시작부터 그 초 동안**의 값 오차를 세지 않습니다 — 판정 (분석 1 · 메인 칸 · 최종 판정), 공정 일치율 ·
  대시보드, 히트맵 (칸 색 · 차이 줄), 분석 1 IO 목록 (차이 IO), 그래프 "차이 영역 표시". 값 자체는 그래프 · 히트맵에 그대로 보입니다.
- 단계 없어짐 · 생김 · 차례 · 공정 시간 (로그 길이) 판정은 그대로입니다.
- 시각 로그는 초 그대로, 숫자 시간 열은 위 칸 폭과 같은 규칙으로 초를 셉니다. 표본 번호 축에는 안 먹습니다.
- 바꾸면 설정 창을 닫을 때 다시 견줍니다 (비교 서명에 들어감).

### 히트맵의 그룹 · 검색 (1.07)

```
차이가 난 IO  4개   │ 10:00 │ 10:01 │ …
▼ 온도         2개  │       │       │      ← 그룹 이름 줄 (누르면 접힘 ▶)
  TEMP_C        3칸 │ 1.2%  │ 정상  │
  TEMP_A        1칸 │ 정상  │ 0.4%  │
▼ 압력         1개  │       │       │
  PRES_B        2칸 │ …
▼ 그룹에 없는 IO 1개 │       │       │
  X_LONE        1칸 │ …
```

- **그룹은 그래프 화면의 그것 그대로**입니다 (설정에 든 하나). 그래프에서
  그룹을 만들거나 IO 를 옮기면 히트맵도 바로 다시 나뉩니다 (다시 계산 없이).
- 나누는 규칙도 그래프 목록과 같습니다 — 그룹 차례대로, IO 가 그룹 둘에
  있으면 앞 그룹에만, 어느 그룹에도 없으면 맨 아래 "그룹에 없는 IO".
- 다른 점: **차이 난 IO 가 하나도 없는 그룹은 이름 줄도 안 보입니다.**
  히트맵에는 차이 난 IO 만 오므로, 빈 그룹 이름이 줄줄이 깔리면 볼 줄이
  밀립니다.
- 그룹 안의 차례는 **히트맵 차례**(많이 벌어진 것이 위)입니다.
- 그룹 이름 줄을 누르면 접혔다 펴집니다. 그래프 목록의 접기와는 **따로**입니다.
- **[차이 없는 IO도 보기]** 는 누르면 **바로 다시 셉니다** (1.17, 전에는
  [히트맵 다시 계산] 을 따로 눌러야 했음).
- **검색** 칸은 **IO 이름 칸 바로 위**에 있습니다 (1.10, 전에는 도구 줄).
  그래프 검색과 같습니다 (이름에 그 글자가 들면, 대소문자 안 가림). 치는 대로 바로 걸러지고, 맞는 IO 가 없는 그룹은 사라집니다.
- 규칙은 `src/LogScope/Analysis1/Heatmap/HeatmapBuilder.cs (HeatLayout)` 한 곳입니다.

### 히트맵 칸의 숫자

칸에 적히는 값은 그 구간에서 **가장 크게 벌어진 순간**입니다. 퍼센트로 보면
그 순간의 오차 %, 값으로 보면 그 순간의 차이 — **같은 표본의 두 가지 표현**이라
보기를 바꿔도 가리키는 자리가 달라지지 않습니다.

**2.01 — "가장 크게" 는 값 차이 (최대 오차) 기준입니다.** 예전에는 % 가 가장 큰 순간을 골라서, 이전 값이 0 가까이인
표본의 큰 % (예: 1 → 3 = +200 %) 가 실제 최대 오차 (100 → 150 = +50 %) 대신 적혔습니다. 줄 차례에 쓰는 줄의 최대 % 도
같은 규칙 (값 차이가 가장 큰 순간의 %).

**허용 오차를 바꿔도 이 숫자는 변하지 않습니다.** 바뀌는 것은 빨간지 초록인지,
그리고 "넘은 표본 수" 뿐입니다. 재는 값이 재는 잣대에 딸려 있으면 안 됩니다
([claude-log/17](claude-log/17-relative-to-before.md)).

그리고 빨간 칸의 숫자는 **언제나 허용 오차보다 큽니다** — 판정도 이 숫자로
내리기 때문입니다.

**부호 · 100 % 넘는 값 (1.93).** 칸의 % 는 **이전 값 기준** `(이후 − 이전) / |이전| × 100` 이고 부호가 붙습니다
(+ 높아짐 · − 낮아짐). 100 % 를 넘어도 그대로 적습니다. 값으로 볼 때도 부호 있는 차이입니다.

| 이전 → 이후 | 칸 (%) | 칸 (값) |
|---|---|---|
| 2 → 8.8 | `+340%` | `+6.8` |
| 10 → 4 | `−60%` | `−6` |
| 0 → 5 | `Δ+5` (이전 값이 0 이라 % 를 낼 수 없어 값 차이) | `+5` |
| 이름 (상태) 다름 | `≠` | `≠` |

전에 100 % 까지만 보였던 것은 **이전 값이 0 인 경우** (디지털 IO 등) 를 100 % 로 적었기 때문입니다. 색 진하기 · 줄 차례는
예전처럼 부호 없는 크기로 매깁니다. 마우스를 올리면 "이전 2 → 이후 8.8, +6.8" 처럼 두 값을 적습니다.

**로그 길이가 다를 때 (1.93).** 판정에 "로그 길이" 가 있으면 (아래 6-1 정상 판정) 히트맵도 두 로그가 겹치지 않는
시간까지 칸으로 보이고, 이후 로그가 끝난 뒤는 **`이후 없음`**, 이후 로그에만 있는 시간은 **`이전 없음`** 칸 (진한 색) 입니다.
그런 칸이 있는 IO 는 값 차이가 없어도 줄에 넣습니다. 전에는 이후 로그가 끝난 뒤를 **마지막 값으로 견줬습니다** (고침).

허용 오차를 바꾸면 요약 위에 안내 줄이 떠서, 지금 보이는 히트맵이 아직 예전
기준으로 그려져 있다는 것을 알려 줍니다. [히트맵 다시 계산] 을 누르면 사라집니다.

**1.66 부터 그래프 · 히트맵의 허용 오차는 한 값입니다.** 그래프 도구 줄에서
바꾸든 히트맵에서 바꾸든 (설정 창에서 바꿔도) 다른 쪽 칸 글도 같이 바뀌고,
대시보드 · 그래프 · 정상 판정을 다시 견줍니다. 히트맵은 **보고 있을 때만** 바로
다시 셉니다 (안 보고 있으면 넘어올 때 셈 — 큰 로그에서 몇십 초 걸릴 수 있어서).
히트맵의 [히트맵 다시 계산] 도 그래프 쪽 비교까지 같이 다시 합니다.

상태(문자열) 채널은 이름이 다르면 오차 100% 이고, 허용 오차와 상관없이
늘 차이입니다.

### 어느 IO 가 "차이 난 IO" 인가 (1.68)

정상 판정이 있으면 **판정에서 허용 안 된 값 오차가 있는 IO** 입니다 — 메인 칸
"차이 발생 N 개" 와 같은 규칙이라 메인 칸 · 대시보드 · 히트맵 · 그래프 목록의 수가
같습니다. 칸의 색 · 퍼센트는 예전처럼 칸마다 센 값이지만, 줄로 올라오는지는 판정이
정합니다. 그래서 시간 여유 안에서 조금 늦은 IO (예전에는 차이) 는 빠지고, 메인에서
오차를 허용한 IO 도 빠집니다. 메인 칸 수에는 **한쪽에만 있는 IO** 도 들어가서, 그런
IO 가 있으면 히트맵 요약에 몇 개인지 적습니다 (히트맵에는 줄이 없음).

### 줄 차례

위에서부터 **크게 벌어진 IO** 순입니다. 기준은 그 줄에서 가장 크게 벌어진
순간의 **오차 %** 이고, 같으면 허용 오차를 넘은 표본이 많은 쪽, 그 다음은
이름순입니다.

셋 다 **칸 폭과 무관한 값**이라 1 분으로 보든 5 분으로 보든 IO 차례가
같습니다 ([claude-log/10](claude-log/10-heatmap-row-order.md)).

**1.67 부터 그룹으로 나눠 보면 그룹 안은 그룹에 적힌 차례입니다** (그룹에 없는
IO 는 로그 열 차례). 차이 크기 차례로 두면 단계 맞춤 · 허용 오차 · 시간 맞추기를
바꿀 때마다 그룹 안 IO 차례가 뒤바뀌어서, 보던 IO 를 다시 찾아야 했습니다.
메인 화면에서 그룹을 펼쳤을 때의 IO 줄도 같은 규칙입니다 (오차 있는 IO 는 색과
"오차 N" 으로 구분).

### 값이냐 퍼센트냐

히트맵 도구 줄의 [값 그대로] / [% (이전 값 대비)] 로 고릅니다. 둘은 **같은
순간**(가장 크게 벌어진 표본)의 두 가지 표현이라, 보기를 바꿔도 가리키는
자리가 달라지지 않습니다.

퍼센트 쪽이 설정한 허용 오차와 같은 잣대라, 칸에 `0.09%` 라고 적혀 있으면
기본 기준(0.1%) 아래라고 그대로 읽으면 됩니다.

칸에 마우스를 올리면 아래 띠에 허용 오차와 나란히 나옵니다.

```
압력 PT-01   09:12 ~ 09:13   차이 발생
가장 크게 벌어진 순간 0.15% (6 bar)   허용 오차 0.1%
(허용 오차를 넘은 표본 3 / 60)   구간 최대 차이 7 bar   구간 평균 차이 0.3 bar
```

고른 값은 설정에 저장됩니다.

### 그래프 세로축

**[Value] 와 [Difference] 둘 중에 고릅니다** (1.20, 전에는 [기존 값] · [차이]).

| 눈금 | 그리는 것 |
|---|---|
| Value | 이전 로그와 이후 로그를 **각각** 그립니다. 선 두 개 |
| Difference | **두 로그의 차이**(이후 − 이전)를 그립니다. 선 **하나** |

```
차이 = 이후 로그의 값 − 이전 로그의 값
```

같으면 `0`, 이후가 1 크면 `+1`, 1 작으면 `-1`.

이전과 이후를 나란히 그려 놓고 눈으로 견주는 대신 **벌어진 만큼만** 봅니다.
6466.3 과 6466.6 은 값 눈금에서 겹쳐 보이지만, 여기서는 `+0.3` 으로 또렷이
섭니다.

```
기존 값                        차이
 6466.6 ┤ ╭──── 이후           +0.3 ┤   ╭───
 6466.3 ┤━╯──── 이전            0.0 ┤━━━╯
        두 선이 거의 겹침            벌어진 만큼만
```

- **시간 격자가 달라도 됩니다.** 이전이 0.1 초마다, 이후가 0.25 초마다
  찍혔어도 됩니다. 한쪽 격자에 맞추지 않고 **두 격자를 합쳐** 훑어서,
  한쪽에만 있는 표본에서도 반대쪽 값을 읽어 견줍니다. 이전 격자만 쓰면
  이후 로그에서만 튄 자리를 통째로 놓칩니다.
- **[시간 맞추기] 를 따릅니다.** 맞춘 결과대로 겹쳐 놓고 뺍니다.
- **겹치는 구간에서만** 그립니다. 한쪽 기록이 없는 자리에서는 없는 값을
  지어내지 않습니다 — 그러면 로그가 짧은 쪽 끝에 가짜 차이가 생깁니다.
- **한쪽 로그에만 있는 IO** 는 견줄 상대가 없어 비어 있습니다. 왜 비었는지는
  `Lane` 머리글의 `이전에만` / `이후에만` 이 말해 줍니다.
- **상태(문자열) 채널**은 이름이 같으면 `0`, 다르면 `1` 입니다. 상태 번호는
  로그마다 따로 매겨져서 빼 봐야 뜻이 없습니다. 대시보드·히트맵과 같은
  규칙입니다.
- 눈금에는 **0 이 반드시 들어갑니다.** 안 그러면 어디가 "차이 없음" 인지
  알 수 없습니다. 0 선도 같이 긋습니다.
- 커서를 놓으면 값과 차이를 같이 적습니다 — `이전 6466.3  이후 6466.6  차이 +0.3`.
- [차이 영역 표시] 는 이 눈금에서 **차이 선과 0 선 사이**를 칠합니다.
  "다르다" 는 판정은 **어느 눈금에서든 값으로** 합니다 — 그래야 허용 오차의
  뜻이 대시보드·히트맵과 같고, 눈금을 바꿨다고 칠해지는 자리가 달라지지
  않습니다.

> 예전에는 `0–1 정규화` 가 하나 더 있었습니다. **없앴습니다** — `Lane`
> 보기에서는 값과 눈금에 똑같은 변환이 걸려 그림이 하나도 안 바뀌었고,
> `Overlay` 에서도 "이 채널의 최소~최대 안에서 몇 %" 라는 숫자는 로그를
> 읽을 때 쓸 데가 없었습니다.

세로 눈금 왼쪽 위에 그 눈금이 무엇인지 적습니다 — 단위(`bar`), `상태`,
`Δ bar`(= 이후 − 이전) 중 하나입니다. `Overlay` 에서 단위가 서로 다른 채널이 한 눈금을
같이 쓸 때는 어느 하나를 적으면 거짓말이 되므로 비웁니다.

단위는 엑셀에서 가져옵니다.

| 어디 | 생김새 |
|---|---|
| 머리 행 바로 아래의 단위 줄 | `Time / sec`, `PT01 / bar` |
| IO 이름 끝의 괄호 | `압력 PT-01 [bar]`, `AI_TEMP(degC)` |

IO 이름은 엑셀에 적힌 그대로 둡니다. 단위를 떼어내 이름을 줄이지 않습니다.

눈금 글자도 채널에 맞춥니다.

| 채널 종류 | 눈금 |
|---|---|
| 상태 (문자열) | 번호 대신 **상태 이름** (`IDLE`, `RUN` …) |
| 디지털 (0 / 1) | `0` 과 `1` 에만 |
| 아날로그 | 보기 좋은 간격의 숫자 |

자세한 이유는 [claude-log/07-units-and-percent.md](claude-log/07-units-and-percent.md).

### 도구 줄

| 묶음 | 들어 있는 것 |
|---|---|
| 보기 | `Lane` / `Overlay` / `갤러리` (1.60) |
| 세로 눈금 | `Value` / `Difference` |
| `Time Scale` | **[+] [−]** 확대·축소, **[초기화]** 전체 구간으로 |
| `Value Scale` | **[+] [−]** 확대·축소, **[초기화]** 배율 되돌리기, [구간 맞춤], [계속 맞춤] |
| 비교 | [차이 영역 표시], [파형 분리 보기], 허용 오차 |
| 정렬 | [단계마다] [전체 구간 ▼] (6-1-3 장) |
| 시간 맞추기 | 누르면 판이 내려옵니다 (9 장) |

도구 줄은 **두 줄로 고정**입니다 (1.20): 1 줄 = 보기 · 세로 눈금 · Time Scale ·
Value Scale, 2 줄 = 비교 · 정렬 · 시간 맞추기. 창이 아주 좁으면 그 줄 안에서만
더 접힙니다.

IO 목록에서는 타입(디지털 · 아날로그 · 상태) 글자와 타입 고르기 목록을 1.20 에
뺐습니다. 거르기 목록은 `전체 IO` · `고른 IO만` · `차이 발생 IO` 입니다.

#### Lane 과 Overlay

**IO 를 하나만 골랐을 때는 둘이 같은 그림입니다.** 여러 개 골랐을 때만
갈립니다 — 그래서 묶음 이름에 그렇게 적어 뒀습니다.

| | 세로 눈금 | 언제 |
|---|---|---|
| `Lane` | IO 마다 **따로** | 값 크기가 서로 다를 때. 0/1 짜리와 6466 짜리를 같이 봐도 각각 꽉 차게 보입니다 |
| `Overlay` | 모두 **같이** | 값 크기가 비슷한 IO 끼리 겹쳐 놓고 모양을 견줄 때 |
| `갤러리` (1.60) | IO 마다 **따로** — 칸마다 왼쪽에 | IO 를 많이 골랐을 때. **가로 3 칸씩** 작은 그래프로 늘어놓아 한 화면에 많이 봅니다 |

**갤러리**는 칸마다 IO 하나, 칸 아래에 시작 · 끝 시각을 적습니다. 칸 높이는 **180 고정** (1.65 — IO 수와 상관없이 같은 크기),
많으면 아래로 굴립니다. **칸을 두 번 누르면 그 IO 하나만 Lane 으로** 봅니다 (1.83 — 전에는 한 번). 그때 위에
**[◀ 갤러리로]** 단추가 생겨, 누르면 **들어가기 전에 고른 IO 들 그대로** 갤러리로 돌아옵니다. 보기를 손으로 갤러리로 바꾸면
단추는 사라집니다. **IO 하나에서 확대 · 이동한 것은 그 IO 칸에만 남고** 다른 칸 · 공통 구간은 들어가기 전 그대로입니다
(1.87). 들어갈 때는 그 칸이 보던 구간 · 세로 배율로 시작합니다.

**고른 그래프** (1.83): 그래프 (Lane 줄 · 갤러리 칸 · 겹쳐보기 판) 를 한 번 누르면 **파란 테두리**가 둘리고 그것이 고른
그래프가 됩니다. **휠은 고른 그래프 위에서만 확대 · 축소**, 그 밖 (고르지 않은 그래프 · 아무것도 안 골랐을 때) 에서는
**화면을 굴립니다** — 갤러리 · Lane 이 길어 굴려야 할 때 확대가 먼저 걸리지 않게. 그래프 밖 (칸 사이 틈 · 눈금 자리) 을
누르면 고른 것이 풀립니다.

**끌기 · 오른쪽 네모는 마우스가 있는 줄 (Lane 줄 · 갤러리 칸) 만** 시간을 바꿉니다 (1.77). 그 줄은 자기 구간을 갖고
오른쪽 아래에 "이 줄만 a ~ b" 를 적습니다 (갤러리는 칸 아래 시각이 그 칸의 것). **휠도 고른 그래프 하나만** 확대 · 축소합니다
(1.85 — 1.78 ~ 1.84 는 모든 줄이 같이). 모든 줄을 같이 바꾸려면 **Ctrl + 휠** (1.87, 그래프 위면 고르지 않아도) ·
`Time Scale` [+] [−] · `+` `-` · `←` `→`.
**Home** · [전체] · 히트맵 · 오차에서 넘어오면 모든 줄이 다시 같은 구간. 겹쳐보기 (줄 하나) 와 단계로 나눠 보기 (칸마다 따로)
는 예전 그대로입니다.

#### [구간 맞춤] 과 [계속 맞춤]

둘 다 "지금 보이는 시간 구간에 세로 눈금을 맞춘다" 는 같은 계산을 합니다.
다른 것은 **그 뒤에 손을 떼느냐** 입니다.

| | 언제 맞추나 | 그 뒤 |
|---|---|---|
| **[구간 맞춤]** (단추) | **누른 그 순간 한 번** | 그대로 둡니다. 시간축을 밀어도 세로 배율이 그대로라, 내가 잡은 배율이 유지됩니다 |
| **[계속 맞춤]** (토글) | **시간축을 움직일 때마다** | 계속 따라다닙니다. 어디로 밀든 그 구간에 꽉 차게 보입니다 |

```
[구간 맞춤] 한 번 누르고 시간축을 오른쪽으로 밀면
  ├─ 세로 배율 그대로 → 값이 작아진 구간은 납작하게 보임 (그게 사실이니까)

[계속 맞춤] 켜 두고 같은 일을 하면
  └─ 밀 때마다 다시 맞춤 → 늘 꽉 차 보임. 대신 "커졌다/작아졌다" 를 못 느낌
```

그래서 **값이 얼마나 커졌는지 비교하려면 [구간 맞춤]**, **모양만 들여다보려면
[계속 맞춤]** 입니다. [계속 맞춤] 은 위아래 움직임이 심한 채널에서 눈금이
계속 출렁여 어지러울 수 있습니다.

#### 같이 켜지지 않는 것

**[차이 영역 표시] 와 [파형 분리 보기] 는 같이 켜지지 않습니다.** 하나를
켜면 다른 하나가 꺼집니다. 벌려 놓고 그 사이를 칠하면 칠해진 넓이가
"값 차이" 가 아니라 **"값 차이 + 벌린 간격"** 이 되어, 눈으로 재는 넓이가
눈금과 안 맞기 때문입니다. 둘 다 끌 수는 있습니다 — 켜져 있는 것을 다시
누르면 꺼집니다.

### 한쪽 선만 보기

두 선이 거의 같은 자리에 겹쳐 있으면 **뒤에 그려진 쪽이 앞의 쪽을 덮습니다.**
**왼쪽 IO 칸의 [그릴 로그] — ☑이전 ☑이후** 로 한쪽을 끄면 가려졌던 선이
그대로 보입니다.

- **도구 줄이 아니라 왼쪽 칸**에 있습니다. "무엇을 그릴까" 는 IO 를 고르는
  일과 같은 종류라 그쪽이 제자리이고, 도구 줄은 두 줄을 넘지 않아야 합니다.
- 끈 쪽은 **세로 눈금 계산에서도 빠집니다.** 안 보이는 선 때문에 눈금이
  넓어지면 보이는 쪽이 납작해져서, 끈 보람이 없습니다.
- 한쪽만 켜 두면 **[파형 분리 보기] 는 벌리지 않습니다.** 벌릴 상대가 없는데
  비켜 그리면 그 선만 눈금에서 어긋나 보입니다.
- **둘 다 끌 수 있습니다.** 그때는 그래프에 그렇게 적힙니다. 다만 설정 파일에
  둘 다 꺼진 상태로 남지는 않습니다 — 다음에 켤 때 빈 그래프로 시작하면
  고장으로 보이기 때문입니다.
- `차이 (이후−이전)` 눈금에서는 선이 하나뿐이고 두 로그가 다 필요한 값이라
  이 칸들이 **꺼져 보입니다**.

### 선 색 — 이전은 파랑, 이후는 빨강 (0.60)

```
── 파란 선 = 이전
── 빨간 선 = 이후
```

**그래프 그림의 오른쪽 위**(레인 머리글 아래)에 적힙니다. 옆의 선 조각은
**그 화면에서 실제로 쓰는 펜**이라 글과 선이 어긋날 수가 없습니다. 선에
가려지지 않게 판을 살짝 투명하게 깔아 둡니다.

0.60 에 왼쪽 IO 칸에도 같은 설명을 뒀다가 **0.67 에 뺐습니다** — 같은 말이 두
군데에 적혀 있었고, 왼쪽 칸이 그만큼 좁아졌습니다.

색맹에게도 가장 안전한 짝이고, 흑백으로 뽑아도 밝기가 달라 구분됩니다.

**한 가지 예외가 있습니다.** `[겹쳐]` 로 보면서 IO 를 여럿 고르면 **색이
IO 를 가리킵니다** — 모두 파랑·빨강으로 그리면 어느 선이 어느 IO 인지 알 수
없기 때문입니다. 그때는 같은 IO 의 이전/이후가 **같은 색의 옅고 짙음**으로
나뉘고, 범례에서 **색 이름이 사라집니다** (`파란 선 = 이전` → `이전`).
거짓말하는 범례는 범례가 없는 것보다 나쁩니다. 대신 "IO 마다 색이 짝을
이룹니다" 가 붙습니다 — 파랑·빨강으로 보려면 `[레인]` 으로 보거나 IO 를 하나만
고르면 됩니다.

`[레인]` 으로 보면 IO 마다 칸이 따로라 색으로 IO 를 가릴 일이 없습니다 —
거기서는 늘 파랑·빨강입니다.

이 규칙은 `src/LogScope/Analysis1/Graph/GraphSeries.cs (TraceColors)` 한 곳에 있습니다. 선을 그리는
쪽과 범례를 적는 쪽이 각자 판단하면, 조건을 한쪽만 고친 날부터 범례가 거짓이
됩니다.

### 어느 선이 이전이고 어느 선이 이후인가

그래프 **오른쪽 위에 작은 범례**가 붙습니다. 글로 적는 대신 **그 화면에서
실제로 쓰는 선을 그대로** 보여 줍니다.

| 지금 보기 | 범례 |
|---|---|
| Lane | 파랑 선 `이전` / 주황 선 `이후` — 어느 IO 든 같습니다 |
| 한쪽만 켜 둠 | 그 선 하나와 `이전만 보기` / `이후만 보기` |
| Overlay | 첫 IO 의 두 선. IO 마다 색이 **짝을 이룹니다** (IO 가 둘 이상이면 그 말도 적힙니다) |
| 차이 (이후−이전) | 선이 하나뿐이라 `차이 (이후 − 이전)` 한 줄 |

레인 머리글 오른쪽에는 커서 값이 적히므로, 범례는 **그 줄 아래**에 놓입니다.
살짝 투명해서 뒤로 선이 지나가도 아주 가려지지는 않습니다.

## 9. 시간 맞추기

### 1 열 PC 시간 · 2 열 동작 시간 (1.66)

로그 맨 앞 두 열이 **둘 다 시간** 이면 (1 열 = PC 시간, 2 열 = 장비 동작 시간)
**2 열을 시간축으로** 쓰고 1 열은 IO 목록에서 뺍니다. 2 열을 시간으로 보는 조건은
셋 다입니다 — 값이 시간으로 읽힘 · 줄어들지 않고 한 번 이상 늘어남 · 머리 글에
시간 낱말 (Time · 시간 · 시각 …) 이 있거나 값이 모두 시각 모양 (`09:15:00.1`).
그냥 늘어나기만 하는 카운터 같은 숫자 IO 는 머리 글에 시간 낱말이 없으면 IO 로 남습니다.
1 열만 시간이면 예전처럼 1 열이 시간축입니다. 어느 열을 썼는지는 읽기 안내 글에 적힙니다.

그래프 화면과 히트맵 화면의 도구 줄에 있는 **[시간 맞추기]** 단추를
누르면 판이 내려옵니다. **두 화면이 같은 설정 하나를 씁니다** — 한쪽에서
맞춰 놓으면 다른 쪽에도 그대로 걸립니다.

### 사건으로 시간 맞추기

이전 로그와 이후 로그는 **기록을 건 시각이 다를 수 있습니다.** 시작 시각끼리
맞추면 같은 사건이 서로 다른 자리에 놓입니다. 그래서 **IO 하나를 골라 그
IO 가 어떤 값이 되는 순간**에 두 로그를 겹칩니다.

```
밀기 값 = 이전 로그의 사건 시각 − 이후 로그의 사건 시각
```

**기준 값은 0 과 1 만이 아닙니다.** 그 IO 에 실제로 나온 값을 모아 올립니다.

| 채널 | 고를 수 있는 값 |
|---|---|
| 디지털 | 0, 1 |
| 단계 신호 | 0, 1, 2, 3, 4, 5 … (최댓값까지) |
| 상태(문자열) | `IDLE`, `RUN`, `STOP` … 이름 그대로 |
| 값이 64 가지를 넘는 진짜 아날로그 | 0 / 1 (값 범위 한가운데를 문턱으로) |

**어느 순간을 잡을지**도 고릅니다.

| 고르기 | 뜻 |
|---|---|
| 그 값이 될 때 | 그 값이 되는 순간. **처음부터 그 값이면 시작 지점** |
| 그 값에서 벗어날 때 | 그 값에서 다른 값으로 가는 순간 |
| 값이 바뀔 때 | 아무 변화나 |

"처음부터 그 값이면 시작 지점" 이 중요합니다. 기록을 늦게 건 로그는 그 IO 가
**이미 1 인 채로** 시작합니다. 그 로그에서는 첫 표본이 곧 그 순간입니다 —
이걸 안 세면 맞출 수 있는 로그를 못 맞춥니다.

같은 일이 여러 번 일어나면 **몇 번째**로 맞출지 고릅니다.

그 밖에:

- 목록에는 **양쪽 로그에 다 있고, 한쪽에서라도 값이 바뀌는** IO 만 올라옵니다.
- 이 로그에 없는 값을 기준으로 고르면 **조용히 다른 값으로 바꾸지 않고**
  실패하고 이유를 말합니다. 두 로그가 서로 다른 사건에 맞는 것보다 낫습니다.
- 맞추는 동안은 **시작 시각 자동 맞춤이 비켜섭니다.** 둘 다 걸면 서로를 밀어
  엉뚱한 자리로 갑니다.
- **[맞추기 해제] 하면 자동 맞춤이 그대로 돌아옵니다.** 설정 창의 밀기 값도
  덮이지 않습니다 — 그 값은 어느 쪽이든 위에 더해지는 미세 조정입니다.

### 가로축 바꾸기는 걷어냈습니다 (0.92)

가로축을 로그의 시간 대신 다른 IO 의 값으로 두는 기능이 있었습니다 (경과
시간 레지스터, 스캔 번호). 쓰이지 않아 걷어냈습니다 — 설정 칸 하나, 콤보
하나, 그리고 "값이 뒤로 가면 안 된다 / 너무 크면 안 된다" 를 가리던 200 줄쯤이
같이 사라졌습니다.

되넣을 자리는 `LogDataset` 의 "가로축" 주석 자리 한 곳입니다. 그리는 쪽도
견주는 쪽도 눈금 글자도 전부 `Times` 만 보기 때문에, 그때도 그 밖에는 손댈
곳이 없었습니다. 코드는 git 기록의 0.91 에 있습니다.

## 10. 알아 둘 점 / 아직 못 한 것

- 모니터별 DPI 는 `App.config` 의 스위치로 켭니다. 그 PC 에 .NET Framework
  4.6.2 이상이 깔려 있어야 동작합니다 (윈도우 10/11 은 4.8 이 기본).
  윈도우 7 에 4.6.1 만 있으면 조용히 시스템 배율로 돕니다.
- `.xls` (예전 엑셀 이진 형식) 는 읽지 못합니다. 엑셀에서 `.xlsx` 로 저장해 주세요.
- 히트맵은 이전 로그와 이후 로그가 **둘 다** 있어야 나옵니다.
- 그래프는 화면 배율(DPI)에 맞춰 장치 픽셀 수만큼 접어 그립니다. 표본이
  픽셀보다 성긴 구간(크게 확대했을 때)에서는 접지 않고 표본을 그대로 잇고,
  디지털·상태 채널은 계단으로 그립니다.
- 이 저장소의 코드는 리눅스 컨테이너에서 작성했습니다. **윈도우에서 컴파일해 본
  적이 없습니다.** 처음 `build.bat` 을 돌릴 때 오류가 나오면 그 내용을 알려 주세요.

  다만 이제 **C# 은 실제로 컴파일해서 확인합니다.** 리눅스에서도 Mono 의
  컴파일러로 `LogScope` · `LogScope.Tests` 를 모두
  컴파일하고, **테스트도 실제로 돌립니다**(168개 통과).
  `sh scripts/check_compile.sh` 한 줄입니다.

  아직 확인하지 못하는 것은 **XAML 컴파일**과 **진짜 WPF 타입**뿐입니다
  (리눅스에 WPF 가 없어 껍데기로 대신합니다). 그래서 `build.bat` 이 여전히
  정답이고, 저 검사는 그 앞에서 거르는 체입니다.
  자세한 것은 [scripts/README.md](scripts/README.md).
