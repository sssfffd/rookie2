# 구조

## 왜 DLL 하나 + EXE 하나인가

요구사항 0번의 "파일 파싱/데이터 부분과 UI 부분이 나뉘어" 를 지키는 가장 단순한
모양입니다.

```
LogScope.exe  ──참조──▶  LogScope.Core.dll
   (WPF)                   (파싱 / 데이터 / 비교 / 히트맵 / 설정)
```

`LogScope.Core` 는 WPF 어셈블리를 하나도 참조하지 않습니다.
그래서 다음이 가능합니다.

- 콘솔에서 테스트를 돌릴 수 있습니다 (`LogScope.Tests`). 창을 띄우지 않습니다.
- 나중에 화면을 갈아엎어도 파싱 코드는 그대로 씁니다.
- "이 버그가 파싱 쪽이냐 화면 쪽이냐" 를 어셈블리 경계로 가를 수 있습니다.
- **화면 기술을 통째로 바꿀 수 있습니다.** 실제로 WinForms 에서 WPF 로
  옮기면서 `LogScope.Core` 는 한 줄도 고치지 않았습니다.

C++ 때와 달리 **C ABI 를 따로 만들지 않았습니다.** .NET 어셈블리끼리는 타입을
그대로 주고받아도 힙이 어긋나지 않기 때문에, `extern "C"` 로 납작하게 펴는
작업이 필요 없습니다. 그만큼 코드가 줄었습니다.

## 로그를 여는 흐름

```
LogReader.Open(path)
      │
      ├── .xlsx/.xlsm ──▶ XlsxReader   ┐
      └── .csv/.tsv   ──▶ CsvReader    ├─ IRowSource (한 줄씩 흘려보냄)
                                       ┘
                    │
                    ▼
            TableBuilder.Build()
                    │
      1. 앞부분 붙들기 (Probe, 최대 200줄 또는 200만 칸)
      2. 표가 시작하는 자리 찾기  (머리말 건너뛰기)
      3. 배치 판별  (행이 IO / 열이 IO)
      4. 흘려 읽으며 채널 배열에 바로 쓰기
                    │
                    ▼
              TimeAxis.Build()
                    │
      빈 칸 채우기 / 반복 시각 펴기 / 자정 넘김 / 전부 같으면 샘플 번호
                    │
                    ▼
                LogDataset
```

### 표를 통째로 복사하지 않습니다

C++ 때는 시트를 `Grid`(2차원 셀 배열)로 다 읽은 뒤, "행이 IO" 면 전치까지
했습니다. 1000만 칸이면 그것만으로 수백 MB 를 쓰고, 여는 시간의 절반이
복사였습니다.

지금은:

- `IRowSource.NextRow()` 가 **내부 버퍼를 다시 쓰면서** 한 줄씩 넘깁니다.
- 배치 판별에 필요한 앞부분만 붙들어 둡니다. 그 붙드는 양도 **줄 수와 칸 수
  둘 다**로 제한합니다. "행이 IO" 배치는 한 줄이 표본 5만 칸이므로, 줄 수만
  제한하면 여전히 1000만 칸을 붙들게 되기 때문입니다.
- 판별이 끝나면 남은 줄은 바로 채널 배열(`FloatBuffer`)에 씁니다.
- 전치는 아예 하지 않습니다. "행이 IO" 면 한 줄이 곧 한 채널이라 자연스럽게
  채널 배열이 됩니다.

### 값은 float

`double` 이면 1000만 칸에 80 MB, `float` 면 40 MB 입니다. 이전/이후 두 개를
동시에 열면 차이가 80 MB 가 됩니다. 로그 값은 소수점 몇 자리 수준이라
float 의 유효자리(약 7자리)로 충분합니다.

빈 칸은 `NaN` 이고, "여기서 선이 끊긴다" 는 뜻입니다.

## 그리기

```
GraphCanvas.OnRender
      │
      ├─ Decimator.Build(...)    픽셀 열마다 min/max/first/last 만 뽑기
      │
      └─ StreamGeometry          선 하나를 한 덩어리로 (점마다 DrawLine 아님)
```

WPF 라고 `Polyline` 같은 요소로 수만 점을 올릴 수는 없습니다. 요소 하나하나가
시각 트리에 남아 메모리와 레이아웃 시간을 잡아먹기 때문에, `FrameworkElement`
하나에 `OnRender` 로 직접 그립니다. 히트맵(`HeatmapCanvas`)도 같은 이유로
같은 방식입니다.

표본 5만 개를 1000 픽셀에 그릴 때 선 긋기가 5만 번에서 1000 번으로 줄어듭니다.
`Decimator` 는 화면에 기대지 않는 순수 계산이라 `Core` 에 있고, 테스트에서
"한 번뿐인 꼭짓점이 살아남는지" 를 확인합니다.

### 언제 접고 언제 안 접나

크게 확대하면 화면 안의 표본이 열보다 적어집니다. 그때는 **접지 않고 표본을
그대로** 잇습니다.

```
화면 안 표본 수 <= 열 수  →  표본을 그대로 (DrawSamples)
화면 안 표본 수 >  열 수  →  접어서      (DrawColumns)
```

접어서 그릴 때 "값이 없는 열" 은 기록이 끊긴 자리를 뜻하므로 선을 끊습니다.
성긴 쪽에서는 빈 열이라는 개념 자체가 없어 끊길 일이 없습니다. 이 구분을 하지
않으면 확대했을 때 표본마다 점 하나짜리 도형이 되어 아무것도 보이지 않습니다
(실제로 났던 버그입니다 — `claude-log/06-graph-and-sorting.md`).

열 수는 **장치 픽셀** 기준입니다. WPF 좌표는 DIP(1/96 인치)라, 배율 150% 화면
에서 DIP 로 세면 실제 픽셀의 2/3 만 쓰게 됩니다.

### 세로 눈금이 어긋나지 않는 이유

눈금 숫자를 찍는 자리와 선을 긋는 자리가 **같은 함수** (`ValueToY`) 를
거칩니다. 눈금용 변환과 그리기용 변환을 따로 두지 않았습니다.

### 세로 배율이 갑자기 풀리지 않는 이유

레인마다 기준 범위(`BaseRange`)를 **채널 전체 범위**에서 가져옵니다.
시간축을 밀어도 이 값은 바뀌지 않습니다. "보이는 구간에 맞춤" 을 켰을 때만
지금 보이는 구간으로 다시 잡습니다.

Shift+휠(값 확대)은 `LaneY.Zoom` 과 `LaneY.Center` 만 바꿉니다. 커서가
가리키던 값이 제자리에 남도록 Center 를 다시 계산합니다.

## 왼쪽 목록과 그리기 순서

`ChannelView.Rows` 가 "화면에 보이는 줄" 의 순서입니다. 그래프에 그리는
순서(`DrawOrder()`)도 이 목록을 그대로 훑어서 만듭니다. 그래서:

- 그룹 순서를 바꾸면 그래프 순서도 같이 바뀝니다.
- Shift 범위 선택이 "보이는 순서" 를 따릅니다 (`SelectRangeByRow`).

그룹 구성원은 채널 번호가 아니라 **IO 이름**으로 저장합니다. 그래서 다른
파일을 열어도 같은 이름의 IO 에 그대로 붙습니다.

## 허용 오차가 한 곳에만 있는 이유

```
              ToleranceRule.For(이전채널, 이후채널, 절대오차, 비율)
                      ▲            ▲            ▲
                      │            │            │
                 DiffEngine   HeatmapBuilder  GraphCanvas
              (대시보드·목록)   (히트맵 칸)    (차이 음영)
```

처음에는 세 화면이 각자 기준을 들고 있었고, 그래서 같은 로그인데 대시보드는
"차이 40개", 히트맵은 "3개" 가 나올 수 있었습니다. 지금은 셋 다 같은 함수를
부르므로 그런 어긋남이 생길 수 없습니다.

기준값을 채널마다 다르게 잡는 이유는 `ToleranceRule` 의 주석에 적어 두었습니다.

## 히트맵

```
HeatmapBuilder.Build()
      │
      ├─ 칸 폭 정하기        시각 로그면 1분, 아니면 전체를 60칸
      ├─ 채널마다 BuildRow()  이전 표본을 훑으며 이후 자리를 같이 앞으로 밈
      └─ 많이 벌어진 순으로 정렬
```

`BuildRow` 가 이진 탐색을 쓰지 않는 것이 핵심입니다. 이전 로그의 표본은
시간 순서대로 들어오므로, 이후 로그의 자리도 뒤로 갈 일이 없습니다. 그래서
채널 하나가 O(표본 수) 로 끝납니다. 표본마다 탐색하면 채널 200 x 표본 5 만
= 1000 만 번의 이진 탐색이 됩니다.

칸에 적는 값으로 **절대 차이의 평균**을 쓰는 이유는
[claude-log/04-heatmap.md](../claude-log/04-heatmap.md) 에 적었습니다.

## 배경 스레드

로그 읽기와 비교, 히트맵 계산은 `BackgroundJob` 이 배경 스레드에서 돌립니다.
진행 상황은 `LoadProgress` 로 올라오고, 화면 갱신은 `Dispatcher.BeginInvoke`
로 UI 스레드에 넘깁니다. 취소는 `LoadProgress.Cancel()` 로 깃발을 세우고,
파싱 쪽이 `ThrowIfCancelled()` 에서 멈춥니다.
